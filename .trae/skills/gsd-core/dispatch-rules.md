# GSD Core 调度规则

本文档定义 GSD Core 调度器的触发条件、回退规则、子 Agent 生成规则以及保留模块的调用方式。

---

## 一、何时触发 GSD Core 调度

### 1.1 自动触发条件（满足任一即触发）

| 条件 | 阈值 | 判断方法 |
|------|------|----------|
| 任务数量 | >= 2 | 用户请求中可识别出 2 个及以上独立子任务 |
| 预估复杂度 | medium 及以上 | 基于涉及文件数、模块数、变更类型综合评估 |
| 涉及文件数 | >= 3 | 修改或创建 3 个及以上文件 |
| 涉及模块数 | >= 2 | 跨 2 个及以上模块/子系统 |
| 用户明确调用 | — | 用户提到 "gsd-core"、"任务调度"、"子agent调度" 等关键词 |

### 1.2 复杂度评估标准

**low 复杂度（不触发）：**
- 单文件修改
- 逻辑简单，无副作用
- 风险低，回退容易
- 示例：修改常量值、调整文案、修复单行 bug

**medium 复杂度（触发）：**
- 2~5 个文件修改
- 需要理解模块内关系
- 有明确的接口边界
- 示例：新增一个 API 端点 + 对应测试

**high 复杂度（触发）：**
- 跨模块变更（5+ 文件）
- 涉及架构调整或设计决策
- 需要协调多个子系统
- 示例：新增完整功能模块、重构核心流程

**critical 复杂度（触发）：**
- 核心系统变更
- 高风险，影响面广
- 需要多轮审查和验证
- 示例：安全架构重构、数据库迁移方案

### 1.3 触发判断流程

```
用户请求到达
    ↓
是否明确调用 gsd-core？ ──是──→ 触发 GSD Core
    ↓否
是否已有 2+ 个明确任务？ ──是──→ 触发 GSD Core
    ↓否
预估复杂度是？
  ├─ low → 不触发，使用原生能力
  ├─ medium → 触发 GSD Core
  ├─ high → 触发 GSD Core
  └─ critical → 触发 GSD Core
```

## 二、何时回退到 superpowers 原生调度

### 2.1 回退场景

GSD Core 在以下场景应主动回退到 superpowers 原生调度器，而不是强行适用：

| 场景 | 回退目标 | 原因 |
|------|---------|------|
| 单任务 + low 复杂度 | executing-plans 或直接执行 | 调度开销 > 收益 |
| 紧密耦合的多任务 | subagent-driven-development | 任务间强依赖，无法有效并行 |
| 纯调试/排查任务 | dispatching-parallel-agents | 调试任务适合并行调查模式 |
| 需要 SDD 专属特性 | subagent-driven-development | 如 task review loop、fix round 机制 |
| 简单并行调查 | dispatching-parallel-agents | 纯调查类任务，无需完整调度流程 |
| 单任务但高复杂度 | subagent-driven-development | SDD 的单任务审查循环更精细 |

### 2.2 回退判断原则

**不要为了用调度器而用调度器。** GSD Core 的价值在于多任务编排和质量门禁，当这些价值不显著时，应果断回退。

回退判断在任务分解阶段完成后进行：
1. 如果分解后只有 1 个任务且复杂度 low → 回退到直接执行
2. 如果分解后任务间全部强依赖（无法并行）→ 回退到 SDD
3. 如果任务性质是纯调查/调试 → 回退到 dispatching-parallel-agents
4. 否则 → 使用 GSD Core

### 2.3 回退时的资源保留

回退不是完全放弃 GSD Core 的工作成果：
- 任务分解结果可以传递给 SDD 作为计划
- 依赖分析结果可用于调整执行顺序
- 质量门禁中的 TDD 和代码审查要求仍然适用

## 三、子 Agent 生成规则

### 3.1 Agent 角色与任务类型映射

| 任务类型 | Agent 角色 | 核心能力 | 模型层级 |
|---------|-----------|---------|---------|
| implementation | Implementer | 代码实现 + TDD | 根据复杂度选择 |
| research | Researcher | 技术调研、方案分析 | standard |
| refactor | Refactorer | 代码重构、架构优化 | standard ~ most-capable |
| test | Tester | 测试编写、测试修复 | cheap ~ standard |
| docs | Doc Writer | 文档编写、技术文档 | cheap ~ standard |
| config | Config Engineer | 配置变更、环境调整 | cheap |
| review | Reviewer | 代码审查、质量把关 | most-capable |
| bug-fix | Debugger + Fixer | 问题定位 + 修复 | standard ~ most-capable |

### 3.2 模型选择规则

**按复杂度选择：**

| 复杂度 | 实现任务 | 审查任务 | 说明 |
|--------|---------|---------|------|
| low | cheap | cheap | 单文件、机械性改动 |
| medium | standard | standard | 多文件、需要理解模块 |
| high | most-capable | most-capable | 跨模块、需要设计判断 |
| critical | most-capable | most-capable | 核心系统、高风险 |

**按任务特征调整：**
- 有完整 spec 的机械实现 → 降低一级
- 需要探索/设计的任务 → 提高一级
- 小范围修复 (fix loop) → 保持原级别或降低一级
- 最终代码审查 → 始终使用 most-capable

**模型层级定义（参考 superpowers SDD）：**
- **cheap tier：** 快速、廉价模型，适合机械性任务
- **standard tier：** 平衡速度和能力，适合大多数任务
- **most-capable tier：** 最强可用模型，适合复杂判断任务

### 3.3 Dispatch Prompt 结构

每个子 Agent 的 dispatch prompt 必须包含以下部分：

```
1. 角色定位
   - 你是谁（角色名称）
   - 你的任务目标（一句话）
   - 你在整体项目中的位置

2. 任务说明
   - 任务 ID 和名称
   - 详细的需求描述
   - 任务类型和复杂度
   - 预期产出物

3. 上下文
   - 相关文件路径列表
   - 前置任务的接口/数据约定
   - 全局约束和项目规范
   - 已有的设计决策

4. TDD 要求（仅 implementation 类型）
   - 必须遵循 TDD 流程
   - 测试覆盖要求
   - 参考 superpowers:test-driven-development

5. 验证标准
   - 功能验收标准
   - 测试通过要求
   - 代码质量要求

6. 输出契约
   - 完成标记（如 ## TASK COMPLETE）
   - 报告文件路径
   - 提交规范
   - 状态码定义（DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED）
```

### 3.4 Agent 隔离原则

- **上下文隔离：** 每个子 Agent 拥有独立上下文，不继承调度器会话历史
- **任务隔离：** 每个 Agent 只负责一个任务，不跨任务工作
- **资源隔离：** 并行任务尽量避免操作相同文件（冲突检测见结果聚合阶段）
- **禁止子子 Agent：** 子 Agent 不得再创建自己的子 Agent（审查除外，由调度器统一调度）

### 3.5 状态契约

子 Agent 必须返回以下四种状态之一：

| 状态 | 含义 | 调度器处理 |
|------|------|-----------|
| DONE | 任务完成，所有验证通过 | 进入结果聚合 |
| DONE_WITH_CONCERNS | 任务完成，但有疑虑或风险 | 记录 concerns，评估是否需要额外审查 |
| NEEDS_CONTEXT | 缺少必要信息，无法继续 | 补充上下文后重新调度 |
| BLOCKED | 遇到无法解决的阻塞 | 评估根因，决定升级模型、拆分任务或人工介入 |

## 四、保留模块调用方式

### 4.1 TDD 模块 (test-driven-development)

**调用位置：** 子 Agent 内部，由 GSD Core 通过 prompt 注入触发

**注入方式：**
1. 在 dispatch prompt 中明确声明 TDD 要求
2. 提供 test-driven-development skill 的核心规则摘要
3. 将 TDD 执行质量纳入任务验证标准

**具体注入内容：**
```
## TDD 要求

你必须遵循测试驱动开发流程：

1. 红：先写失败的测试用例，验证测试能正确失败
2. 绿：编写最少的代码让测试通过
3. 重构：在测试保护下优化代码结构

参考 superpowers:test-driven-development skill 的完整规范。

任务完成时，你必须能够证明：
- 测试是在实现之前编写的（通过提交历史）
- 所有测试都通过了
- 测试覆盖了核心逻辑和边界条件
```

**验证方式：**
- 任务审查时检查提交顺序（测试提交是否早于实现提交）
- 代码审查时评估测试质量
- 运行测试套件验证通过率

### 4.2 代码审查模块 (requesting-code-review)

**调用位置：** GSD Core 质量门禁阶段

**调用时机：**
- 所有子任务完成
- 结果聚合通过（无冲突）
- 测试门禁通过

**调用方式：**
1. 准备审查包（review package）
   - 收集本次调度的所有代码变更 diff
   - 整理任务列表和验收标准
   - 汇总子 Agent 的 concerns 和风险点
2. 调用 `superpowers:requesting-code-review` skill
3. 使用 most-capable 模型
4. 审查范围为完整的变更集

**结果处理：**

| 审查结果 | 处理方式 |
|---------|---------|
| 全部通过 | 质量门禁通过，交付用户 |
| Minor 问题 | 记录问题，有条件通过，交付时告知用户 |
| Important / Critical 问题 | 进入修复循环 |

**修复循环：**
1. 第一轮：指派一个 fixer Agent 处理全部问题（不是每个问题一个 Agent）
2. 修复完成后进行 scoped re-review（范围限定为修复变更）
3. 第二轮：如仍有问题，升级模型再修复一次
4. 超过 2 轮：由调度器裁决残留问题，记录裁决理由，升级到人工介入

### 4.3 接收审查反馈模块 (receiving-code-review)

**调用位置：** 子 Agent 内部，处理审查反馈时

**应用方式：**
1. 子 Agent 的 dispatch prompt 中包含 receiving-code-review 的行为准则
2. 审查反馈通过文件（而非对话）传递给子 Agent
3. 子 Agent 按规范：
   - 逐条响应审查意见
   - 修复代码和测试
   - 更新报告文件
   - 记录未采纳的意见及理由

### 4.4 保留模块与 GSD Core 的边界

```
┌─────────────────────────────────────────────────┐
│                  GSD Core                        │
│  ┌─────────┐  ┌──────────┐  ┌──────────────┐   │
│  │ 任务分解 │→│ 依赖分析  │→│ 并行分组      │   │
│  └─────────┘  └──────────┘  └──────┬───────┘   │
│                                     │           │
│                              ┌──────▼───────┐   │
│                              │ 子 Agent 调度 │   │
│                              └──────┬───────┘   │
│                                     │           │
│  ┌──────────────┐  ┌──────────┐  ┌──▼───────┐  │
│  │ 质量门禁     │←│ 结果聚合  │←│ 执行      │  │
│  └──────┬───────┘  └──────────┘  └──────────┘  │
│         │                                       │
└─────────┼───────────────────────────────────────┘
          │ 调用
    ┌─────▼──────┐    ┌──────────────────────┐
    │ requesting │    │ test-driven-         │
    │ -code-     │    │ development          │
    │ review     │    │ (子 Agent 内部遵循)   │
    └────────────┘    └──────────────────────┘
    ┌──────────────────────┐
    │ receiving-code-      │
    │ review               │
    │ (子 Agent 内部遵循)   │
    └──────────────────────┘
```

**GSD Core 负责：** 调度编排、任务分解、依赖管理、并行控制、结果聚合
**保留模块负责：** 具体的方法论执行（TDD 流程、代码审查标准）

## 五、并行调度安全规则

### 5.1 允许并行的条件

多个任务可以并行执行，当且仅当：
1. 任务间没有文件级依赖（不修改相同文件）
2. 任务间没有接口级依赖（不定义对方使用的接口）
3. 任务间没有数据依赖（不消费对方产出的数据）
4. 任务不会竞争同一资源（如数据库表、配置文件）

### 5.2 并行冲突检测

**调度前检测：**
- 静态分析任务的文件列表，检测重叠
- 分析接口定义和消费关系
- 如有重叠，调整分组或合并任务

**执行后检测：**
- 结果聚合阶段检查 git 提交的文件冲突
- 验证接口一致性
- 运行集成测试检测逻辑冲突

### 5.3 共享资源处理

对于必须共享的资源（如公共类型定义、配置文件）：
1. 指定一个任务负责修改共享资源，其他任务只读
2. 共享资源修改任务放在最早的波次
3. 后续波次任务基于已修改的共享资源工作

## 六、调度器状态管理

### 6.1 Ledger 文件

GSD Core 使用 ledger 文件追踪调度进度，确保上下文压缩后可以恢复。

**Ledger 位置：** `.trae/gsd-core/ledger-<timestamp>.md`

**Ledger 内容：**
- 调度会话标识
- 任务列表和状态
- 波次分组
- 子 Agent 标识和提交记录
- 所有 Ruling（决策记录）
- 风险和 concerns
- 审查结果

### 6.2 恢复机制

上下文压缩后：
1. 读取 ledger 文件
2. 根据 ledger 重建任务状态
3. 跳过已完成的任务
4. 从最近的未完成任务继续

### 6.3 决策记录 (Rulings)

所有重要决策都必须记录在 ledger 中：
- 任务分解的关键决策
- 依赖分析的判断依据
- 并行分组的调整理由
- 回退决策及原因
- 质量门禁的裁决结果
- 异常处理的决策

格式：`Ruling: <决策内容> — <原因> — <如果错误的代价>`
