# Compound Engineering 知识复利层

## 概述

Compound Engineering 是一个全局后置处理技能，在所有开发任务完成后自动触发，将本次开发过程中的经验、决策、踩坑记录结构化沉淀到知识库，形成知识复利效应，避免在未来的项目中重复造轮子。

核心原则：**每一次开发都让下一次开发更快。**

## 后置处理触发条件

在以下场景自动触发本技能：

1. **开发任务完成后** — 功能开发、Bug 修复、重构等任务提交前，自动检查是否有可沉淀的知识
2. **代码审查完成后** — 审查过程中发现的共性问题、设计模式、反模式
3. **架构决策确定后** — 重大技术选型、架构设计决策需要记录
4. **用户显式调用** — 通过 `/compound-engineering` 或关键词手动触发

触发判断标准（满足任一即可）：
- 本次改动涉及非平凡的设计决策或技术选型
- 解决了一个非显而易见的问题（最终方案不能仅从代码直接看出原因）
- 发现了可复用的模式或反模式
- 踩了一个未来可能重蹈的坑
- 代码审查中出现了值得记录的发现

## 知识收集范围

### 1. Superpowers 开发计划
- 开发计划中的架构决策
- 需求分析中的关键洞察
- 方案对比中的取舍逻辑

### 2. GStack 交付产物
- 代码审查发现（review 技能）
- QA 测试报告中的模式
- 性能基准数据（benchmark 技能）
- 安全审计发现（cso 技能）
- 设计审查结论（design-review 技能）

### 3. 架构决策记录
- 技术选型决策及理由
- 架构模式选择
- 被否决的方案及其原因
- 关键依赖的选择依据

### 4. 代码审查发现
- 常见错误模式
- 可复用的设计模式
- 性能反模式
- 安全漏洞模式
- 可维护性问题

### 5. 修复记录
- Bug 根因分析
- 修复方案及替代方案
- 回归预防措施
- 同类问题识别方法

## 结构化沉淀格式

每条知识条目包含以下字段：

| 字段 | 说明 | 必填 |
|------|------|------|
| `id` | 唯一标识符（kebab-case） | 是 |
| `title` | 知识条目标题 | 是 |
| `category` | 分类（见下方分类列表） | 是 |
| `tags` | 标签数组，用于关键词检索 | 是 |
| `summary` | 一句话摘要（不超过 200 字） | 是 |
| `content` | 完整内容（Markdown 格式） | 是 |
| `source` | 来源（如：compound-engineering-plugin, project-local） | 是 |
| `date` | 记录日期 | 是 |
| `severity` | 重要程度（low / medium / high） | 否 |
| `applies_when` | 适用场景列表 | 否 |
| `related_entries` | 相关条目 ID 列表 | 否 |

## 知识分类

### architecture-patterns — 架构模式
系统架构设计模式、流程模式、跨平台架构方案、发布流程设计。

### best-practices — 最佳实践
编码规范、约定俗成、开发体验优化、工程最佳实践、工具使用技巧。

### bug-patterns — Bug 模式
已知缺陷模式、集成问题、常见陷阱、根因分析及修复方案。

### design-patterns — 设计模式
Skill 设计模式、Agent 交互模式、状态机、调度策略、可复用设计方案。

### integration-solutions — 集成方案
多平台集成、插件系统、跨工具链对接、API 集成方案。

### performance-optimizations — 性能优化
性能瓶颈分析、优化策略、资源效率提升、延迟降低方案。

## 知识检索机制

### 新项目启动时自动检索
当新项目启动或新功能开发开始时，自动从知识库中检索相关知识：

1. **关键词匹配** — 基于任务描述提取关键词，与知识条目标题、标签、摘要进行匹配
2. **分类过滤** — 根据任务类型过滤相关分类
3. **相似度排序** — 按相关度排序返回最相关的知识条目
4. **推荐展示** — 在开发计划阶段推荐可复用的方案和需要规避的坑

### 检索触发点
- 需求分析阶段（brainstorming 后）
- 方案制定阶段（writing-plans 后）
- 技术选型阶段
- 遇到问题时（investigate 前）

### 检索输出格式
```
## 知识检索结果

找到 3 条相关知识：

1. **[架构模式] POSIX 进程监管在原生 Windows 上的移植**
   - 相关度：高
   - 摘要：将 POSIX 专属的进程监管移植到 Windows 时的静默失败原语...
   - 标签：windows, cross-platform, process-supervision

2. **[最佳实践] Codex 委托令牌经济学**
   - 相关度：中
   - 摘要：委托给外部模型的令牌成本分析，何时委托 vs 直接实现...
   - 标签：codex-delegation, token-economics
```

## 工作流程

### 后置处理流程（自动触发）

```
1. 任务完成检测
   ↓
2. 知识候选提取
   ├─ 从 commit diff 中提取
   ├─ 从代码审查评论中提取
   ├─ 从计划文档中提取
   └─ 从修复记录中提取
   ↓
3. 耐久性判断（durable bar）
   ├─ 问题是否非显而易见？
   ├─ 从最终代码中能否直接看出原因？
   └─ 未来是否可能重蹈覆辙？
   ↓
4. 分类与标签化
   ↓
5. 结构化写入知识库
   ↓
6. 更新索引与统计
```

### 耐久性判断标准

一条知识值得被记录，当且仅当它包含**无法从最终代码、测试、类型、注释或现有文档中直接恢复的持久化项目推理**，并且丢失它可能导致问题重现、实质风险或大量重新调研。

反事实检验：如果这条知识消失了，未来阅读最终实现的工程师是否仍可能重复犯错或重新进行大量调研？

**不满足耐久性的情况：**
- 常规的 Bug 修复（原因和修复在代码中显而易见）
- 简单的功能添加（设计决策一目了然）
- 已经在文档或注释中充分说明的内容
- 一次性的临时问题

## 与其他技能的关系

| 技能 | 关系 | 说明 |
|------|------|------|
| `brainstorming` | 前置输入 | 需求分析中的洞察可作为知识候选 |
| `writing-plans` | 前置输入 | 方案决策记录为架构决策知识 |
| `executing-plans` | 触发点 | 计划执行完成后触发知识沉淀 |
| `review` | 前置输入 | 代码审查发现沉淀为知识 |
| `investigate` | 前置输入 | Bug 根因分析沉淀为 bug-patterns |
| `qa` | 前置输入 | 测试发现沉淀为最佳实践或 bug-patterns |
| `benchmark` | 前置输入 | 性能数据沉淀为 performance-optimizations |
| `ship` | 触发点 | 发布完成后触发最终知识沉淀 |
| `document-release` | 触发点 | 发版文档完成后同步知识 |

## 配置

配置文件路径：`.trae/skill-config/postprocess-config.json`

主要配置项：
- `enabled` — 是否启用后置处理
- `autoCollect` — 自动收集的知识来源
- `categories` — 启用的知识分类
- `durableBar` — 耐久性门槛设置

知识库路径：`.trae/knowledge/`

## 完成状态

知识沉淀完成后输出：
- **沉淀完成** — 成功记录 N 条新知识
- **无需沉淀** — 本次任务无可沉淀的持久化知识（说明原因）
- **部分沉淀** — 部分候选通过耐久性检验

每条沉淀的知识都必须通过耐久性检验，宁缺毋滥。
