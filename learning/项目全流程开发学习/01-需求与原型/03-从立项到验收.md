## 技术基础：断言、测试替身与验收边界

### 一条测试由什么组成

测试把一个承诺变成可重复实验。Arrange 准备数据，Act 执行动作，Assert 核对结果。例如准备一份两字正文，调用计数，断言结果等于 2。最后一步是“断言”；没有断言，程序正常退出也不能证明结果正确。

```typescript
import { expect, it } from 'vitest';

it('实验中的两字应被统计', () => {
  const text = '落盘'; // 准备
  const result = [...text].length; // 执行：仅演示测试结构
  expect(result).toBe(2); // 核对
});
```

这里的算法只是说明三段结构，不是本项目正式字数算法；正式算法还会排除标点、空白、书签，见第四卷。教学例子应说明简化边界，不能拿简化例子替换生产逻辑。

### 测试替身是什么

测试替身是可控制的依赖。例如给网络函数注入一个返回 401 的替身，不花钱也能验证认证错误处理。真实 SQLite 测试则使用临时磁盘文件，检验真实事务。两种实验回答不同问题：前者证明程序处理给定响应；后者证明真实存储关系正确。网络替身不能证明厂商兼容性和账单。

### 覆盖率与验收结果不同

行覆盖率是执行过的代码行占比；分支覆盖率检查条件的不同走向。执行了 `if` 的成功路径，失败路径未必被测到。即使覆盖率达标，也可能缺少正确断言，因此还必须核对测试是否能在行为出错时失败。

本项目先用 Vitest 检查纯函数和 SQLite 边界，再用 Playwright 驱动真实 Electron。测试输出的通过数属于一次特定源码与环境运行；不是以后所有修改的永久保证。

### 把范围写进结论

“本机临时数据下关闭重开通过”是可以复核的结论；“任何环境永不丢稿”超出了实验。以下实践要求你同时记下样本、动作和未覆盖项。到第七卷，你会把它们组成完整交付门禁。

## 1. 从形容词变成观察条件

“自动保存稳定”只表达期待，没有说明怎样判定。
把它展开，至少有以下几个条件：

- 停顿输入后触发保存。
- 持续输入也不能无限拖延落盘。
- 保存失败不丢失当前草稿。
- 失败后不会自动反复发送同一请求。
- 切换章节和关闭前必须等待保存成功。

每一条都对应不同风险，不能用一次正常输入全部覆盖。
例如断开网络并不能模拟本地磁盘写入失败。
而“数据库提交成功但回执丢失”又不同于“请求发送前校验失败”。
需求应该允许我们区分这些情况。

## 2. 读取三份文件的不同责任

```powershell
Set-Location E:\soulrain
Select-String -Path .\docs\Rain_Soul_项目立项方案_V2.0.md `
  -Pattern '自动保存|验收' -Context 0,2
Select-String -Path .\docs\Rain_Soul_PRD.md `
  -Pattern '500|5 秒|保存失败' -Context 0,2
Select-String -Path .\docs\Rain_Soul_技术方案.md `
  -Pattern 'operationId|SQLite|保存' -Context 0,2
```

立项告诉我们为什么要保护稿件。
PRD将作者会遇到的状态和操作门禁写清楚。
技术方案解释如何使用队列、版本与事务实现保护。

读到不同数字时，不要立刻改一个凑一致。
先查是否在说不同阶段：开始发起保存与提交完成有时间差。
本项目持续输入时较早开始刷新，为最终落盘留出预算。
准确解释数字，比简单照抄“最多五秒”更有价值。

## 3. 为同一故事写可执行场景

下面是自然语言用例，不是自动化代码。
你可以直接按顺序手动执行。

```text
前置：打开“雨落之后”的“雨夜来信”。
动作：在末尾新增“他终于认出了信封上的旧地址。”
动作：停止输入，等待保存成功。
动作：正常关闭，再次打开同一作品和章节。
断言：新增句子仍在，而且只出现一次。
断言：原有两段正文没有被替换。
```

“只出现一次”是在提醒我们注意重复操作。
“原有正文没被替换”是在检查追加行为而非覆盖行为。
精确断言能暴露隐藏错误，笼统的“页面正常”不能。

## 4. 从一个单元测试开始

先确认依赖已经按锁文件安装。
不需要每次运行测试前都重新 `npm ci`。

```powershell
npm run test:unit -- tests/unit/document.test.ts
```

预期退出码为0，文档校验与字数相关测试通过。
具体耗时由机器状态决定，不应把本书某次运行时间写成保证。

打开测试源码：

```powershell
Get-Content .\tests\unit\document.test.ts
```

找到“拒绝外来结构与重复段落 ID”的用例。
它通过构造非法对象验证边界，不需要启动整个桌面窗口。
再找到字数用例，观察期待结果为何是6。
理解断言的依据，比背下 `expect` 的语法更重要。

## 5. 为什么需要三种测试

单元测试像检查一个零件：文档校验、字数算法、保存状态机。
集成测试像检查连接：真实 SQLite 事务、Worker 请求和权限服务。
端到端测试像实际使用：点击、输入、关闭重开和恢复。

| 层次 | 本项目例子 | 容易发现的问题 |
| --- | --- | --- |
| 单元 | `document.test.ts` | 计数规则或非法结构 |
| 集成 | `database-worker.test.ts` | 桥接、事务和回执 |
| 桌面 | `writing.spec.cjs` | 用户动作与关闭保存 |

不能因为端到端测试更接近用户，就让所有边界都启动 Electron。
大量慢测试会使定位困难，也更容易受内存与调度影响。
同样，只测函数也无法发现按钮不可点击或焦点错误。
分层的目的，是用适当成本覆盖真实风险。

## 6. 完整交付验证怎样运行

下面不是本章要求立即全部执行的练习，而是项目交付门禁。
后续修改代码并准备交付时，必须查看每一步实际结果。

```powershell
npm run typecheck
npm run lint
npm run test:coverage
npm run test:desktop
npm run test:demo -- --workers=2 --reporter=line
npm run pack
```

桌面测试会启动真实应用，打包会生成 Windows 目录产物。
运行期间不要并行重建 `dist`，否则测试可能加载一半旧文件、一半新文件。
内存有限的机器应顺序执行这些命令。
某个命令仍在运行，不能把“出现输出”误判为成功。

## 常见问题与排查

| 现象 | 检查顺序 | 处理 |
| --- | --- | --- |
| 测试没有执行到目标文件 | 文件名与命令参数 | 核对实际路径后重跑 |
| Native 模块加载失败 | Node版本、架构、依赖安装 | 使用项目支持环境和锁文件 |
| 桌面超时而单元通过 | 内存、并发进程、焦点等待 | 先保留日志，再复现最小场景 |
| 覆盖率高但功能错误 | 断言是否检查行为 | 增加失败场景，不能只追百分比 |
