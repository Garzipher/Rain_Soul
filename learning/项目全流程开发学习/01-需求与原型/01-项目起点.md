# 第一章 从写作问题开始

本章状态：作品集、创建作品、卷章编辑与本地保存已交付。
完整 P0 中的云端 AI 等能力仍在开发，不能以入口存在作为完成证据。
本章的操作对象统一叫“雨落之后”，后续章节沿用它。

## 读完之后，你能做什么

你将把“我想做一个写作软件”改写成能验证的任务。
你还会在真实客户端完成一次创建、输入、关闭、重开的闭环。
最后，你应能解释为什么漂亮页面不等于完整功能。

## 前置知识与准备

不需要先学会 React。
需要会打开 PowerShell、切换目录、查看文件。
如果只想体验软件，可先运行已经构建的程序。
源码实践需要 Windows 10/11 64 位和 Node.js 24。
下面的命令都在 PowerShell 执行，代码框中的提示文字不用复制。

```powershell
Set-Location E:\soulrain
node --version
npm --version
Test-Path .\package-lock.json
Test-Path .\release\win-unpacked\RainSoul.exe
```

预期 Node 输出以 `v24.` 开头。
锁文件应存在；EXE 是否存在取决于你是否已经打包。
若 EXE 存在，可以直接启动：

```powershell
Start-Process -FilePath .\release\win-unpacked\RainSoul.exe
```

若首次从源码运行，先按第二卷说明执行 `npm ci`，再运行 `npm start`。
不要同时启动很多窗口来判断保存能力；项目采用单实例写入。

## 1. 从一个具体困难出发

假设作者写到第三章，突然需要回看前章的人物称呼。
他不希望联网才能打开稿件，也不希望软件退出后丢失刚写的两句。
这包含两种不同需求：回看定位和安全保存。
前者影响导航与搜索，后者影响编辑器、数据库和关闭流程。

把“做得像专业写作软件”作为任务，开发者无法据此判断成功。
把任务改成“关闭后重开仍能看到刚写的正文”，就有了可观察结果。
产品需求应描述作者要完成的事，以及失败时必须保护什么。
实现方式则回答由哪些代码承担这些责任。
两者相关，但应分开记录，避免把某个界面按钮误当成需求本身。

## 2. 先写一张最小实践卡

在自己的练习笔记中复制下面的表格，并填写实际结果。
不需要修改项目需求文档来做这项练习。

| 项目 | 本次实践 |
| --- | --- |
| 使用者 | 在 Windows 上写中文小说的作者 |
| 起点 | 作品集页面 |
| 动作 | 创建“雨落之后”，输入第一章正文 |

限制验证范围并不是限制作者能写多少字。

“任意长度作品都绝不出错”无法靠一次短稿体验证明。
以后需要另做长文、异常恢复和性能验证。

## 3. 在真实界面完成第一次写作

![图1：作品集实际运行截图](images/shelf.png)

图1用于识别作品集与作品卡片；截图中的作品数量是拍摄时的样本。
你的数据目录可能已有作品，不必与截图数量相同。
唯一作品集中也会默认显示本教材作品。

1. 点击“新建作品”。
2. 在名称框输入“雨落之后”。
3. 确认创建，进入作品正文区。
4. 将默认章标题改成“雨夜来信”。
5. 在正文输入下面两段，每段之间按一次 Enter。

```text
雨停以后，林舟在门口发现一封没有署名的信。
他没有拆开，只把湿透的信封放在桌角。
```

6. 停止输入，观察右上角保存状态变化。
7. 等到显示保存成功，再正常关闭窗口。
8. 重新启动，打开“雨落之后”。
9. 核对章标题和两段正文，不能只看作品卡片仍在。

预期结果：重开后的内容与关闭前一致。
这项操作同时触及界面输入、保存协调、进程通信和 SQLite。
所以它比“输入框能打字”的验证更完整。

## 4. 把看到的界面与源码连起来

先读组件边界，不要求马上读懂每个 Hook。
在 PowerShell 执行：

```powershell
Select-String -Path .\src\renderer\App.tsx `
  -Pattern 'createWork|openWork|作品书架'
Select-String -Path .\src\renderer\components\writing-workspace.tsx `
  -Pattern '章节标题|ChapterEditor|save-status'
```

`App.tsx` 负责页面与当前作品的组织。
`WritingWorkspace` 负责卷章区、标题和正文工作区。
`ChapterEditor` 负责把键盘操作变成受限文档。
真正写入数据库的逻辑在 Worker 的仓储层。
你此刻只需要记住：页面展示与磁盘保存不是同一件事。
第三卷会沿同一段正文追踪完整调用链。

## 5. 记录证据，而不是写“应该可以”

记录重开时间、作品名、章节名和核对结果。
如果失败，保留窗口草稿并写下实际提示。
不要为了得到绿色结论而删库重来。

项目已有真实桌面学习作品验收，可查看：

```powershell
Get-Content .\tests\desktop\learning.spec.cjs
Get-Content .\tests\desktop\writing.spec.cjs
```

阅读测试时找三个部分：准备状态、用户动作、结果断言。
测试文件是一份可执行的证据定义，不保证你当前修改后仍然通过。
真正结论要以运行结果为准。

## 常见问题与排查

| 现象 | 先检查什么 | 下一步 |
| --- | --- | --- |
| 双击 EXE 没有新窗口 | 是否已有 RainSoul 运行 | 查看并聚焦已有窗口 |
| 浏览器地址无法访问 | 是否误用了旧 Demo 端口 | 使用真实 EXE 或 `npm start` |
| 正文没有恢复 | 是否正常关闭、保存曾否失败 | 保留现场并核对实际数据目录 |
| 创建后只有一章 | 这是默认起始结构 | 后续用卷章管理添加，不是创建失败 |

## 练习与参考答案

练习1：把“搜索要好用”改成一个可验证的句子。
参考：在指定测试数据中输入“雨夜”，结果标明来源章节，点击后能定位。
响应时间应使用固定样本和测量方法另行验证。

练习2：作品卡片存在，能否证明刚输入的正文已保存？
参考：不能。卡片是摘要信息，正文可能尚未落盘。
需要打开章内容，最好正常退出并重开后核对。

练习3：记录你自己的第一次失败或不确定之处。
提示：写“我观察到什么”，再写“我下一步检查什么”。
不要先给原因定性；这会为第七卷的排错实验留下真实材料。
