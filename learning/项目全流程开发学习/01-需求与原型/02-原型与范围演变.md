# 第二章 原型与范围演变

本章状态：Demo 保留为视觉与交互参考，正式客户端已接通本地 P0 与云端 AI 适配；真实云端与安装兼容性验收须单独记录。
本章学习如何从原型读需求，同时避免把演示数据当成生产能力。
例子仍使用“雨落之后”，本章不会重新创建同名作品。

## 学习目标

你将亲手检查一个 Demo 入口和对应的正式组件。
你会把“看起来能用”分成已实现、演示和待开发三种状态。
最终产物是一张小型需求追踪表，而不是另一份相互冲突的立项方案。

## 前置知识

已经完成上一章的创建与重开操作。
知道文件夹、HTML 文件和桌面应用的区别。
不要求掌握 CSS，但要知道 CSS 主要控制外观。
JavaScript 可以模拟点击，却不一定真的持久化数据。

## 技术基础：原型、状态机与需求追踪

### 从一张图到可运行系统

静态画布描述位置；交互原型描述点了之后发生什么；生产实现还要描述失败、数据和退出重开。HTML 组织内容，CSS 决定排版，JavaScript 处理交互。三者做出的原型可以非常像真实程序，但不因此拥有数据库事务、系统权限或安装器。

本项目的单文件 Demo 包含演示数据与事件处理；正式 React 组件把界面拆成可测试单元，再通过受限桌面 API 持久化。这不是把 HTML 文件后缀改成 EXE，而是补齐可靠运行的责任。

### 用删除操作理解状态机

状态机用“状态＋允许的转换”描述交互，能比一串按钮文案更准确地暴露漏项。

```text
空闲 → 右键菜单 → 删除确认 → 正在删除 → 空闲
                         ↘ 删除失败 → 保留数据并提示
右键菜单 → 点击外部/取消 → 空闲
删除确认 → 取消 → 空闲
```

如果确认弹窗已打开，旧菜单还留在后面，就有两个状态同时占用交互。解决方法是进入确认状态时关闭菜单，而不是只把菜单盖住。`use-structure-menu.ts` 管菜单意图，`structure-dialog.tsx` 管确认，`App.tsx` 串联真实操作。

### 追踪关系为何有用

需求追踪不是多写一份文档，而是建立同一需求与界面、源码、测试的关联。例如“正文没有蓝色方框”：原型表示视觉意图；CSS 实现焦点外观；UI 验收检查实际聚焦后是否出现边框。保存失败保护则需要额外的状态机与磁盘测试，不能套用这一条视觉测试。

从现在开始，阅读每个入口都问三件事：数据从哪里来、动作是否写盘、失败如何返回。这三个问题会一直用到 AI 与归档章节。

## 1. 为什么原型会不断改变

最初的画布表达“有哪些区域”，不负责定义保存事务。
交互 Demo 再把区域变成按钮、卡片、弹窗和会话列表。
正式开发则要加入空状态、错误状态、权限、迁移和测试。

用户后来明确：唯一入口叫“作品集”，头像下显示姓名式笔名值。
正文固定样式，不出现碍眼的蓝色编辑方框。
知识卡片应展示内容摘要与出处，点击原位展开。
需求会话按作品组织，会话下才是对话。
这些都属于实际使用方式，不能随实现方便而随意改名。

与此同时，完整 P0 增加了基础 AI、剧情感受和正文回写。
所以“离线”现在指写作、保存、搜索与导出离线可用。
它不再意味着云端 AI 必须断网运行。
范围改变时需要更新统一基线，不能继续拿早期 MVP 排除后来确认的功能。

## 2. 找到唯一原型与需求基线

```powershell
Set-Location E:\soulrain
Get-Item .\docs\demos\rainsoul-writing-style.html

Get-Item .\docs\Rain_Soul_PRD.md

```

预期四个文件都存在。
立项解释目标和范围，PRD解释交互与验收，技术方案解释实现边界。
Demo主要帮助确认视觉和操作意图。
遇到不一致时，应结合用户最新确认修正统一文件。
不能偷偷新增一份“最终版2”让旧版继续误导后续开发。

可直接用浏览器打开本地 Demo 做静态参考：

```powershell
Start-Process -FilePath .\docs\demos\rainsoul-writing-style.html
```

某些浏览器对 `file:` 页面能力有限，这不代表正式客户端故障。
正式程序使用 Electron 的本地资源协议，见第三卷。
本章只比较布局、文案和操作意图，不在 Demo 中输入真实稿件。

## 3. 用同一个动作做两次观察

先在 Demo 中找到作品卡片和章节区，再打开真实客户端的“雨落之后”。
对比以下动作：

1. 作品卡片右键能否出现菜单。
2. 删除操作是否需要确认。
3. 取消弹窗后，旧右键菜单是否已经关闭。
4. 章节正文获得焦点时是否出现蓝色外框。
5. 左侧栏能否收起，收起后是否仍可辨认导航。

不要用“这个按钮能点”作为全部结论。
正式删除还应有软删除记录、版本保护和重开后的状态。
原型中的演示删除可能只改内存数组。
相同外观可以对应完全不同的数据可靠性。

## 4. 追踪一个具体样式决定

Demo Logo 是天蓝描边、浅蓝底、略微旋转的圆角方框，中间是蓝点。
正式程序的侧栏沿用这套几何和颜色，Windows 程序图标另有同源资产。

```powershell
Select-String -Path .\docs\demos\rainsoul-writing-style.html `
  -Pattern 'brand-mark' -Context 0,2
Select-String -Path .\src\renderer\styles.css `
  -Pattern 'brand-mark' -Context 0,2
Get-ChildItem .\assets\rainsoul.*
```

预期能找到样式声明，以及 SVG、PNG、ICO 资产。
CSS 决定侧栏 Logo，窗口图标和 EXE 图标由其他配置决定。
只改侧栏 CSS，不会自动替换 Windows 任务栏中的程序图标。
这是把“一个视觉需求”拆成多个交付点的例子。

## 5. 建立可用的追踪表

将下面表格复制到自己的学习笔记，补实际观察。
“代码位置”是检查入口，不是完成证明。

| 需求 | Demo 表现 | 正式代码入口 | 验证方法 |
| --- | --- | --- | --- |
| 唯一作品集 | 书架卡片 | `App.tsx` | 创建并重开作品 |
| 卷章右键删除 | 菜单与弹窗 | `use-structure-menu.ts` | 删除后恢复并重开 |
| 无蓝色正文框 | 编辑区域样式 | `styles.css` | 聚焦正文观察 |
| 剧情架构 | 可视参考 | 工作区剧情标签 | 看是否已有真实编辑与持久化 |

如果某入口只显示“开发中”，状态应写“待交付”。
如果只存在 Demo 的假数据，状态应写“原型演示”。
真实调用链、测试和用户操作都具备，才能写“已实现并验证”。

## 6. 做一次范围核对

```powershell
Select-String -Path .\docs\Rain_Soul_PRD.md `
  -Pattern 'P0|P1|P2|后置' -Context 0,1
Select-String -Path .\src\renderer\components\writing-workspace.tsx `
  -Pattern 'plot|foreshadow|Placeholder' -Context 0,1
```

观察剧情、伏笔标签对应的真实组件。
若仍使用 Placeholder，不能因为标签存在就宣称架构功能完成。
反过来，尚未交付也不代表它已被用户从 P0 删除。
范围定义回答“应交付什么”，代码状态回答“目前交付到哪里”。
后续开发必须同时维护这两种信息。

## 常见问题与排查

| 现象 | 原因线索 | 正确处理 |
| --- | --- | --- |
| Demo 有数据，客户端没有 | 原型与数据库彼此独立 | 在真实客户端创建样本 |
| 程序图标没变化 | 只改了网页 Logo | 检查打包与窗口资产 |
| 点击标签只有提示 | 入口已做、能力未交付 | 记录待开发，不能算验收通过 |
| 文档互相矛盾 | 范围演变没有同步 | 依据最新确认修正统一基线 |

## 练习与参考答案

练习1：Demo 的“导出成功”提示能证明 DOCX 正确吗？
参考：不能。至少需要真实文件、内容顺序与引用呈现检查。
还需验证失败不会覆盖原数据。

练习2：用户要求删除知识卡片标题，是否可以顺手删掉条目稳定 ID？
参考：不可以。卡片标题是展示方式，稳定 ID 是引用追溯机制。
界面不展示某字段，不等于存储层可以删除它。

练习3：为“剧情架构”补一行追踪记录。
提示：先写当前真实状态，再写预期验收，避免把计划写成完成。
