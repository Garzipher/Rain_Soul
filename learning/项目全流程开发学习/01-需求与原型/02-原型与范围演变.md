# 第二章 原型怎样推动需求统一

本章状态：原型与需求统一已发生，Demo 仍是参考，不是持久化客户端。学习目标是区分视觉反馈、产品语义和真实实现。

用户先用 Excalidraw 表达结构，再多轮修改 HTML Demo：作品集名称固定；头像下直接显示笔名，不加“笔名”标签；全白界面、天蓝色重点；侧栏默认收起；写作页不出现新建作品；正文不出现蓝色焦点框。知识卡不需要独立标题，最多显示两行，点击原位展开，右下标注出处。这里每个反馈都改变了可以验收的界面行为。

范围也发生过明确修订。早期选择让 AI 后置，后续评审统一为完整 P0：写作特点、剧情架构、伏笔、知识、基础 AI、剧情感受、一致性检查、正文回写和数据保护一起组成首版。需求会话、拆书/URL、XMind、向量检索和本地模型仍后置。不能用早期答案把 AI 再移出首版，也不能因为 Demo 有拆书按钮就说真实解析已经完成。

编辑器讨论同样需要看最后的确认：曾选过 Markdown 输入，之后统一为固定样式的所见即所得编辑。实现采用受限 Tiptap 文档，不能把两个互斥方案同时写成当前要求。系统只有一个作品集，全部普通作品在这里展示；当前学习作品正式命名为“项目全流程开发学习”。

实践步骤：

1. 为每条反馈写“页面、触发动作、预期结果”。
2. 判断反馈属于外观、交互还是数据规则。删除菜单属于交互；删除后能恢复属于数据规则。
3. 修改 Demo 后同步基线，清理已合并的重复立项稿。
4. 保留 Git 历史解释原因，避免让旧文件与当前方案并列指导开发。

例子：知识库的“人物描写”是可维护分类，某段文字的“雨夜、紧张”是多标签。把每张卡写同样标签，虽然布局相同，却无法满足筛选和素材参考。

阅读对接：`docs/demos/rainsoul-writing-style.html` 是当前外观与交互参考；立项第 11.1 节记录统一结论。Git `898ebaf` 对齐知识与会话，`5a31b75` 补剧情/伏笔，`4bccc18` 补关联多选，`39b4685`～`c665e8f` 收敛并清理旧资料。

练习：比较 Demo 的知识页与正式桌面入口。列出“已确定如何操作”和“尚无真实数据库实现”两列，再给一个按钮写验收；不要把视觉可点击当作功能交付。
