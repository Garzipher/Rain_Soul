# 停顿与持续输入保存

《雨落之后》的第一章叫“旧站台”。
作者输入一句话之后，应用什么时候才能说它已经保存？
本章把输入、冻结快照、数据库提交和收到回执分开解释。
完成后，你能从源码推导出保存时机，而不是背诵500ms这个数字。

**本章状态（2026-10-08）：**保存协调器与时序测试已实现。
持续输入4500ms触发提交，是给五秒目标预留处理预算。
它不能证明任意设备、任意正文规模都能在五秒内落盘。
真实性能验收还需要记录设备、数据量和提交耗时。

## 2. 为什么需要两个时钟

防抖表示：作者停顿500ms后，合并提交最新草稿。
输入“雨”后立刻补成“雨停了”，不需要为每个按键都写一次库。
可是连续输入时，防抖计时会不断重置。
如果只有防抖，写十分钟也可能没有提交过。
所以代码还保留从第一次变脏开始计算的最长等待预算。

真实代码中的剩余预算是：

```typescript
const remaining = (this.options.maxWaitMs ?? 4500)
  - (Date.now() - (this.dirtySince ?? Date.now()));
```

最终等待时间取500ms与remaining中较小者。
最外面的Math.max保证已经到期时使用0，而不是负延迟。
这里的定时器只决定开始提交的时间。
正文序列化、IPC排队和SQLite事务仍需要额外时间。

## 3. 四个保存状态

| 状态 | 已经知道的事实 | 作者的体验 |
| --- | --- | --- |
| clean | 当前草稿全部得到提交确认 | 没有待保存修改 |
| dirty | 有新输入尚未确认 | 等待保存机会 |
| saving | 一批快照已经发出 | 等待这批操作的结果 |
| failed | 校验或请求发生失败 | 保留内容并等待处理 |

dirty不是失败，saving也不是已经落盘。
状态必须来自操作结果，不能单凭计时器到期就显示成功。

## 4. 跟做：验证停顿保存

```powershell
npm run test:unit -- tests/unit/save-coordinator.test.ts
```

预期命令成功退出，看到“停顿500ms才提交最新草稿”用例通过。

它验证计时逻辑；真实磁盘另由仓储和桌面测试验证。

打开测试中的这段代码：

```typescript
coordinator.update('旧');
await vi.advanceTimersByTimeAsync(300);
coordinator.update('新');
await vi.advanceTimersByTimeAsync(499);
expect(saved).toEqual([]);
await vi.advanceTimersByTimeAsync(1);
expect(saved).toEqual(['新']);
```

第0ms输入“旧”，第300ms改成“新”。
因为第二次更新重置了停顿时钟，第799ms仍未保存。
第800ms才提交“新”，而不是依次提交两个草稿。
把三个时点画在纸上，便能检查自己的理解。

## 5. 跟做：推演持续输入

找到“持续输入不重置最长提交时限”测试。
它每400ms更新一次，普通防抖一直没有机会触发。
但4500ms的最大等待不会被后续输入推迟。

```text
0ms：草稿0，记录本批开始时间
400ms：草稿1，重置停顿计时
4400ms：草稿11
4500ms：提交草稿11
4800ms：草稿12，进入后续待提交状态
```

因此测试此时预期saved是[11]，不是[12]。
注意这里验证的是开始提交，不是磁盘耗时分布。
不要把4500改成5000后宣称五秒落盘达标。

## 6. generation解决迟到回执

generation是草稿代数，每次update都会递增。
committed是最后已确认的代数。
提交第3代期间，作者还可能继续输入第4代。
第3代回执只能确认第3代，不能把第4代也标成已保存。

真实成功分支包含：

```typescript
this.committed = generation;
this.failedFlight = null;
this.setStatus(this.generation === generation ? 'clean' : 'dirty');
```

右边局部generation是发请求时冻结的值。
this.generation则可能已经被新输入推进。
不相等时继续保持dirty，当前请求结束后安排下一批保存。
pending限制同一协调器只运行一个在途请求，避免乱序覆盖。

## 7. flush与普通计时的区别

flush用于切章和关闭前，不能再等作者停顿。
它清理计时器，并循环到committed不再小于generation。
等待期间又产生输入，flush还会继续提交后续批次。
只await一次save不能保证所有草稿都已确认。

按顺序阅读use-writing-session.ts的update和save回调：

1. 编辑器产生结构化正文。
2. Hook创建新草稿和operationId。
3. 协调器决定何时冻结快照。
4. api.saveChapter经过预加载层到主进程。
5. Worker仓储在事务内保存正文。
6. 成功回执回来，Hook更新已确认版本。

## 8. 故障诊断

| 现象 | 先检查 | 判断依据 |
| --- | --- | --- |
| 连续输入始终不保存 | dirtySince | 本批开始时间不能每键重置 |
| 新输入被旧回执标成功 | generation比较 | 回执只确认冻结的那一代 |
| 虚拟时钟测试卡住 | advanceTimersByTimeAsync | 真实等待不能推进虚拟时间 |
| 请求完成后不再保存 | finally后的schedule | 新草稿必须再次进入调度 |

不要把catch删除后看见控制台安静就当作修复。
保存异常必须保留为failed状态并交给作者处理。

## 9. 练习与答案提示

练习一：保存“雨”期间补成“雨落之后”，为什么通常有两批提交？
答案：第一批已冻结“雨”，后一批提交后来形成的完整草稿。

练习二：成功回执为什么不能无条件设置clean？
答案：等待回执期间可能发生新输入，旧回执无法证明那些输入已提交。

练习三：将迟到回执测试改成小说示例再运行。
提示：必须保留提交顺序和最终clean断言，不能只改用例名称。

## 延伸实验：测量不是猜测

若要测五秒目标，记录第一次输入、请求发出、事务回执三个时间。
不要只截取界面状态变化，因为状态是收到消息后才更新。
先固定正文规模和设备，再连续输入至少几轮，比较最长等待与实际提交延迟。
同样的用例在开发模式与目录包里都应检查，但不要混合统计两种运行条件。

本章检查点：你能画出输入、冻结、提交、回执四步及各步拥有的正文版本。
