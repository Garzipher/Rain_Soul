# 第一章 输入后何时真正保存

本章状态：保存协调器已实现并有自动化测试；持续输入五秒内完成落盘的整机性能专项仍待验收。

学习目标：区分编辑草稿、正在发送的快照与数据库已提交内容，理解自动保存为什么需要两个计时条件。

用户确认的体验是停顿约500ms保存，持续写作也不能无限推迟。代码在持续输入达到4500ms时发起保存，为主进程调度和SQLite提交预留预算。计时触发不等于磁盘提交完成，不能用“定时器执行了”证明五秒性能目标达标。

先阅读 `src/renderer/lib/save-coordinator.ts`。`update` 接收最新草稿、递增 `generation`，首次变脏时记录 `dirtySince`；`schedule` 选择500ms停顿和剩余最大等待时间中较短的一个。

再找 `submit`：它冻结本次的 `generation` 与 `snapshot`，只允许一个 `pending` 请求。请求期间的新输入继续更新草稿，而不是覆盖已经发送的快照。

一个例子：第1秒发送“雨”；等待回执时作者补成“雨停了”。第一个回执只确认“雨”已提交，不能把“雨停了”标成已保存；协调器随后还会提交最新草稿。

实践步骤：

1. 打开 `tests/unit/save-coordinator.test.ts`，找到停顿、持续输入和迟到回执相关用例。
2. 画出“输入 → dirty → saving → clean”的时间线。
3. 在saving期间增加一次输入，说明为什么回执后还需要dirty状态。
4. 对照 `src/renderer/hooks/use-writing-session.ts`，看界面如何接收保存状态。

核心条件可以读作下面的伪代码，实际实现以源码为准：

```text
如果 committed < generation：仍有未提交输入
如果 pending 存在：等待当前请求，不并行写入
如果失败：停止自动重试，等待作者处理
```

为什么不用每个按键都写库：频繁序列化、IPC和事务会增加负担；为什么也不能只用防抖：持续输入时防抖计时不断重置，可能很久都没有落盘。

`flush` 用于切章和关闭等关键操作。它循环等待当前草稿全部提交，不能只等一次保存，因为等待期间可能还出现更新。

证据入口：`tests/unit/save-coordinator.test.ts` 验证时序；`tests/unit/renderer.test.tsx` 验证真实编辑行为；`tests/desktop/writing.spec.cjs` 验证关闭重启后正文仍在。

练习：列出“输入发生在保存前、保存中、回执后”三种情况各有几个generation。设计一条测试，证明旧回执不会错误清除新草稿。

后续学习：用长篇正文和持续输入测量从按键到提交回执的真实耗时，记录设备与样本分布，再判断五秒预算是否满足。
