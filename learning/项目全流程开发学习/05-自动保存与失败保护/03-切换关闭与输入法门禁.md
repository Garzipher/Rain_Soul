# 第三章 离开页面前保护最后一笔

本章状态：切章、结构操作、正常关闭与输入法组词保护已实现；强杀或断电不属于正常关闭保障。

学习目标：理解保存门禁是一个完整交互过程，需要同时管理输入、页面切换、主进程关闭和异常恢复。

真实问题是：先flush，等待期间仍允许作者输入，然后关闭窗口，最后新增的字就可能丢失。只在按钮点击时调用save无法保证安全。

读取 `src/renderer/App.tsx` 和 `src/renderer/hooks/use-writing-session.ts`。开始切换或关闭时先建立操作锁，停止继续编辑，再等待正在执行的管理操作和保存队列；失败时保留草稿并解除可恢复的锁。

再读 `src/main/index.ts`：窗口close事件先被阻止，主进程生成随机token，通知页面处理。页面确认保存后回传同一个token，主进程等待 `StoreService.drain` 才真正关闭。

例子：作者输入“最后一句”后立即点窗口关闭。预期是窗口稍作等待，数据库确认后退出；重启正文仍在。保存失败时窗口保留，作者能看到原因并手动重试。

实践步骤：

1. 搜索 `rainsoul:close-request` 和 `rainsoul:close-confirm`，串起请求与确认方向。
2. 找到主进程来源检查和token匹配，说明旧确认为什么不能关闭新的请求。
3. 查看 `composing` 状态，理解输入法候选字尚未提交时为何拒绝切换或关闭。
4. 看 `before-input-event`，确认Ctrl+R和F5不能绕过草稿保护。

完整数据流是：

```text
窗口关闭 → 主进程请求确认 → 页面锁定输入
→ 等待操作和flush → 携token确认 → 排空命令队列 → 退出
```

结构操作也要走保存门禁。作者改章名后马上删卷，确认框必须显示当前草稿的名称；实际删除仍要等草稿成功持久化，不能只更新提示文本。

这个问题曾在目录包验收中暴露：开发入口较慢，自动保存刚好提前完成，掩盖了确认框读取旧名称的时序错误。回归测试故意让保存失败，验证提示使用最新草稿而数据库仍保持旧值。

证据入口：`tests/unit/renderer.test.tsx`、`tests/unit/renderer-structure.test.tsx` 覆盖延迟、失败、取消和IME；`tests/desktop/writing.spec.cjs` 与 `tests/desktop/structure.spec.cjs` 检查真实窗口行为。

练习：给保存函数加一个可控Promise。点击切章后，在Promise未结束时尝试输入和再次切换，记录允许与禁止的动作，再让Promise失败检查草稿是否还在。

边界：本机制保护正常退出，不承诺任务管理器终止后最后未落盘字符不丢失。未来崩溃恢复需另外设计并测试，不能以关闭测试代替。
