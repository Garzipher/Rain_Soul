# 未知回执与幂等重试

《雨落之后》的“旧站台”已经写入数据库，却没有把结果传回界面。
此时点击重试，怎样避免重复创建章节或重复增加版本？
本章用操作身份和数据库事务回答这个问题。

**状态说明（2026-10-08）：**正文、卷章写入已有回执与幂等测试。
操作日志不是完整版本历史，也不能替代已实现的手动快照；快照的关系图恢复见第八卷第七章。

## 技术基础：幂等、CAS 与事务

### 幂等意味着重做同一请求不重复产生业务效果

数学中 `f(f(x)) = f(x)` 是一种幂等形式；软件中更常见的是“重放同一逻辑请求，返回已完成结果，不重复创建对象”。网络或进程消息无法保证调用方总能知道提交结果，所以重复传输是正常故障恢复场景。

业务幂等必须绑定同一 ID 与同一请求内容。ID 相同但标题不同，不是合法重试。项目对请求 JSON 计算 SHA-256，再用 `operation_log` 保存 request_hash 与紧凑 result_json。SHA-256 是摘要，不可当成加密或权限证明。

### CAS 保护新的更新

Compare-and-swap 先比较预期版本，匹配才更新。例如读到版本 7，提交时要求库仍是 7。成功推进为 8；另一条还基于 7 的新修改应失败，防止把后来内容覆盖为旧稿。

幂等处理旧请求，CAS 处理新请求。重试旧请求时必须先查已提交回执，再做版本比较；否则旧请求已经使库变成 8，重试会错误地冲突。

### 为什么这些动作必须在同一个事务

```text
事务开始
  查 operation_log：已有同请求 → 返回旧回执
  新请求：比较 revision 并递增
  修改正文或结构
  写 operation_log
事务提交；任一步失败则回滚以上全部修改
```

事务原子性意味着不能留下“正文改了但日志没写”的状态。仅在 JavaScript 中顺序调用三个 SQL，不加事务，中间异常依然会留下部分提交。

跟做故障测试时要准确标出抛错发生在“提交前”还是“提交后、回执前”。后者必须保留原 operationId、原预期版本与原正文，重新获取完成结果后才提交新草稿。

## 2. 失败并非一种情况

| 情况 | 数据库可能变化吗 | 后续处理 |
| --- | --- | --- |
| 标题为空，请求尚未发送 | 不可能 | 修正后提交最新草稿 |
| 请求发出但回执未知 | 可能 | 先重取原操作结果 |
| 版本比较失败 | 本次未提交，但原库已有变化 | 保留草稿并处理冲突 |

“客户端报错”不能推出“数据库一定没改”。
未知结果必须保持未知，不能为了方便自动生成一个新操作。

## 3. operationId表示什么

operationId标识一次逻辑修改，不是一次发送动作。
新草稿有新ID；重发同一份在途快照仍使用原ID。
数据库通过主键记录它是否已经完成。

真实表结构位于project-schema.ts：

```sql
CREATE TABLE operation_log (
  operation_id TEXT PRIMARY KEY,
  request_hash TEXT NOT NULL,
  result_json TEXT NOT NULL
);
```

request_hash保存请求摘要。
result_json保存已提交回执，例如新revision。
摘要用于防止同一个ID被错误地用于另一种请求内容。
日志中不需要复制整部作品正文。

## 4. expectedRevision解决旧草稿覆盖

作者打开作品时读取版本7。
提交修改时携带expectedRevision=7，表示基于第7版编辑。
仓储的真实SQL如下：

```sql
UPDATE work_meta
SET revision = revision + 1, updated_at = ?
WHERE id = ? AND revision = ?
```

如果数据库已经是版本8，受影响行数是0，操作被拒绝。
这称为比较并交换，也可以理解成“版本吻合才允许改”。
它保护的是更新前提，与operationId保护重复执行互为补充。

## 5. 为什么先读回执

假设操作A基于版本7，提交后数据库升到版本8。
回执丢失，客户端仍以为版本7。
如果重试时先检查版本，必然误报冲突。
正确顺序是先搜索操作A的已提交回执。
已有回执的A直接返回原结果；新的操作才比较版本。

真实代码的关键分支：

```typescript
if (prior) {
  if (prior.request_hash !== hash) {
    throw new RepositoryError('INVALID_INPUT', '操作标识已用于不同内容。');
  }
  return JSON.parse(prior.result_json) as T;
}
```

正文修改、revision递增、回执记录在同一事务里。
如果分成三次独立写入，中途故障就可能留下不可重放的半状态。


预期saved只包含旧操作与新草稿各一次。
旧操作的第二次发送不增加业务写入次数。

## 7. 为什么重试还要保留原版本号

Hook使用WeakMap为每份快照记住第一次发送的expectedRevision。
同一快照重试时，仍取出那个版本号。
如果ID没变、版本却偷偷改了，请求摘要就会不一致。
仓储会拒绝它，这是保护而非程序太严格。

SaveCoordinator在失败后保存failedFlight。
里面记录冻结的快照与草稿代数。
retry先重放这批未知请求，再flush后来形成的新草稿。
确定未发送的SaveValidationError则不保留旧flight。
空标题改正后，可以直接保存最新合法标题。

## 9. 错误诊断

| 现象 | 可能原因 | 应检查 |
| --- | --- | --- |
| 重试多出一卷 | 重试生成了新ID | 原请求是否被冻结 |
| 同ID内容不一致 | 改了正文或expectedRevision | 请求摘要的输入 |
| 丢回执后立即冲突 | 版本比较先于回执查找 | commit内部顺序 |
| 改正标题仍发空值 | 校验失败被当作未知提交 | SaveValidationError分支 |

不要删除版本比较或清空操作日志来掩盖错误。
这样会移除保护，还会失去复盘证据。

## 10. 练习与答案提示

练习一：同一ID能否用于“创建第一卷”和“创建第二卷”？
答案：不能，逻辑操作的身份必须对应同一请求。

练习二：把测试的抛错放到记录操作之前，会有什么不同？
提示：原操作第一次没有提交，重试才会产生第一次真实业务写入。

练习三：operation_log能否恢复昨天的完整正文？
答案：不能；完整手动快照是另一项P0能力。

## 延伸检查：回执不是业务对象

结构操作日志只保存revision，重放之后重新读取当前作品。
这避免旧日志永久携带过时正文。
调试时应分开检查“原操作是否曾成功”和“现在作品是什么状态”。
前者由操作回执回答，后者由当前数据库读取回答；两者不能互相替代。
