# 第二章 保存失败不一定没有写入

本章状态：保存幂等、版本检查、未知回执重取与前置校验区分已实现；断电恢复专项还未完成。

学习目标：理解网络式调用即使发生在同一台电脑，也存在“数据库成功、调用方没收到结果”的不确定状态。

阅读顺序是 `src/renderer/hooks/use-writing-session.ts` → `src/renderer/lib/save-coordinator.ts` → `src/workers/database/repository.ts`。前端给一次保存分配 `operationId`，仓储把请求指纹和结果存进 `operation_log`。

例子：版本7的章保存为版本8，但Worker回执在传递时丢失。前端还认为是版本7；若直接分配新ID重试，数据库会拒绝旧版本，作者可能陷入永久冲突。

现有做法是保留失败时的同一份快照、同一operationId和同一expectedRevision，先重取原操作。仓储发现相同ID和相同请求，返回此前结果；拿到版本8后才提交后来新增的内容。

实践步骤：

1. 在仓储 `commit` 中找到 `request_hash` 和 `result_json` 查询。
2. 观察查询旧回执发生在CAS版本更新之前，解释为何重放不会再次增长版本。
3. 查找同一operationId用于不同内容的分支，它必须拒绝，而不是误返回旧结果。
4. 对照协调器 `failedFlight`，确认失败后没有悄悄自动重发。

版本检查的思想可以写为：

```sql
UPDATE work_meta
SET revision = revision + 1
WHERE id = ? AND revision = ?;
```

只有匹配预期版本才允许本次修改继续。SQL更新、正文变更与操作回执处于同一事务中，其中一步失败就回滚。

另一个边界是章节标题为空。这个校验在请求发出前失败，已经确定数据库没有写入；因此 `SaveValidationError` 不冻结旧的无效草稿，作者改正标题后可以保存最新内容。

这解释了为什么不能把所有异常都当成“重试最新草稿”，也不能把所有异常都当成“永远重试旧草稿”。需要依据请求是否可能已提交选择恢复方式。

证据入口：`tests/unit/save-coordinator.test.ts` 检查回执丢失和标题校验；`tests/unit/repository.test.ts` 检查重复操作与版本冲突；真实Worker测试覆盖进程桥接。

排错步骤：先确认请求ID是否稳定，再检查revision，最后检查事务日志。不要直接删 `operation_log` 或强制改版本来掩盖冲突。

练习：模拟“首次请求实际成功但返回异常”。断言重试没有产生第二次写入，且之后的新草稿仍能保存。

后续学习：把同一原则迁移到快照、归档导入与AI接受操作；这些功能尚未实现，不应复制一段重试循环后就宣称有事务保护。
