# 软删除与精确恢复

作者删掉一章后后悔了，希望完整取回原稿。
但作者先删过的另一章，不应因为恢复整卷被偷偷复活。
本章用《雨落之后》的两个章节解释软删和删除批次。

**状态说明（2026-10-08）：**作品、卷、章的软删和恢复已实现。
软删恢复取回被删除的现有对象，不是恢复任意过去版本。

知道null在数据库中表示尚无值。

用户作品仍保留在本机目录中。

## 2. deleted_at代表什么

deleted_at为空，表示对象当前活动。
有时间字符串，表示已经删除。
普通书架和章节查询过滤已删除对象。
恢复列表则读取这些被过滤的对象。

单章删除的真实SQL：

```sql
UPDATE chapter
SET deleted_at = ?, deletion_batch = ?
WHERE id = ?
```

正文、标题和稳定ID没有被清掉。
因此恢复时可以取回原内容，而无需重新猜测。
软删也意味着空间不会立刻释放，不能把它解释成清空磁盘。

## 4. 为什么删卷要有批次

假设第一卷有“旧站台”和“雨声”。
作者先单独删除雨声，再删除第一卷。
恢复第一卷时，只应恢复当时仍活动的旧站台。
否则之前故意删除的雨声也会被复活。

删卷时生成一个batch，同一次级联删除使用同一个batch。
真实卷和章更新：

```typescript
const batch = randomUUID();
db.prepare('UPDATE volume SET deleted_at = ?, deletion_batch = ? WHERE id = ?')
  .run(timestamp, batch, action.volumeId);
db.prepare('UPDATE chapter SET deleted_at = ?, deletion_batch = ? WHERE volume_id = ? AND deleted_at IS NULL')
  .run(timestamp, batch, action.volumeId);
```

章更新只包含当时未删除的章。
先前单独删除的章保留自己的batch。
恢复整卷就能区分哪些章属于这一次删除。

## 5. 精确恢复卷的查询

restoreVolume先恢复卷本身，再找同批章节。
查询条件来自真实源码：

```sql
SELECT id FROM chapter
WHERE volume_id = ? AND deletion_batch = ?
  AND deleted_at IS NOT NULL
ORDER BY sort_order, id
```

满足三个条件才恢复：原卷一致、批次一致、目前仍被删除。
如果某章已经被单独恢复，也不会被重复处理。
恢复后清空删除标记，重新追加合法排序位置。

## 6. 原卷未恢复，单章放哪里

作者可以只恢复旧站台，不恢复第一卷。
此时章节不能继续挂在一个不可见卷下。
restoreChapter检查原卷是否活动。
原卷活动则仍归属原卷；原卷删除则恢复到无卷区。

```typescript
const volumeId = parent ? chapter.volume_id : null;
```

之后再恢复原卷，不会把已恢复无卷章强制拖回原卷。
这尊重作者在恢复过程中的新选择。
保留稳定ID，不代表必须恢复原先所有结构属性。

## 7. 作品级软删有什么不同

删除作品只标记work_meta.deleted_at。
整个作品从catalog摘要里移除，但目录与project.sqlite仍在。
恢复作品时清除这个标记，书架再次汇总作品。
原有卷章的独立删除状态仍保留。

“恢复作品”不能代表“恢复作品里的所有历史删除章”。
各级删除状态独立，避免作者的旧决定被连带撤销。
同一旧删除请求重放，也不能再次删除后来已经恢复的作品。
operation_log保护的是操作身份，而非强制重复动作。

## 9. 故障诊断

| 现象 | 优先检查 | 正确规则 |
| --- | --- | --- |
| 恢复卷复活旧删章 | batch过滤 | 只恢复同一删除批次 |
| 恢复章后看不到 | 原卷是否活动 | 必要时放入无卷区 |
| 已删章仍计字数 | 活动查询条件 | 过滤deleted_at不为空 |
| 恢复作品清空旧删除 | 恢复粒度 | 不联动复活所有子对象 |

如果回收列表读取失败，应显示错误并允许重新读取。
不能把读取失败显示成“暂无已删除数据”。

## 10. 练习与答案提示

练习一：软删是否等于备份？
答案：不是；它仍在同一磁盘，磁盘损坏会一起丢失。

练习二：先删章、后删卷，恢复卷能否恢复先删章？
答案：不能；先删章不属于删卷那次batch。

练习三：单章恢复到无卷区后，再恢复原卷，应怎样？
提示：维持当前无卷归属，不擅自撤销作者后来的恢复选择。

## 延伸实验：恢复以后再次删除

先删除旧站台，恢复它，再用新的operationId删除一次。
新的删除属于新的作者操作，应产生新的删除批次。
如果随后重放第一次恢复的旧请求，不能把这次新删除又撤销。
仓储应返回当前删除状态，而不是把旧动作重新执行一遍。
这类时间顺序测试用于验证幂等与恢复的组合，不能只靠单次正常路径。

恢复前还要确保当前草稿已经确认。
否则界面可能拿旧标题组织恢复清单，或让当前待保存正文被切换丢弃。
保存门禁、结构事务与恢复列表并非三个互不相关的小部件。
它们围绕同一作品状态工作，教材和测试都应沿完整过程观察。

本章检查点：你能解释删除批次如何保留作者意图，以及它与版本快照的区别。
