# 作品隔离与数据库迁移

《雨落之后》和另一部作品可以同名，但不能互相覆盖正文。
本章先解释作品为什么以UUID分目录，再解释旧数据库怎样升级。
完成后，你能指出权威数据、可重建缓存和升级前备份各在哪里。

**状态说明（2026-10-09）：**每作品独立 SQLite，当前 schema4；schema1/2/3 的前向迁移、升级前备份和失败回滚已实现并有测试。
本章只描述这次已经存在的迁移，不保证未来任意版本互相兼容。

## 技术基础：关系数据库、WAL 与前向迁移

### 表、记录与约束

关系数据库以表保存记录，每行代表一个对象，每列代表属性。`chapter.id` 是主键，要求唯一；`chapter.volume_id` 是指向卷的外键；值为 null 表示无卷。SQL 查询描述要哪些记录，而不是逐个操作页面卡片。

```sql
-- 只读教学查询；在临时作品库中观察，不修改作者数据。
SELECT id, title, volume_id, word_count
FROM chapter WHERE deleted_at IS NULL
ORDER BY volume_id, sort_order, id;
```

这是字段观察用查询，不是全书正式排序：真实排序还要结合卷的 sort_order。数据库约束保证关系合法，业务代码再保证排序和当前作品意图合法。

### WAL 与一致备份

WAL（write-ahead log）先把已提交变化记入日志，再由 checkpoint 合并进主数据库。因此只拷贝 `project.sqlite` 可能遗漏 WAL 中的最新已提交内容。`VACUUM INTO` 从数据库一致视图生成独立副本，适合升级前备份。

事务的原子性、约束一致性、隔离和持久性常称 ACID。`synchronous=FULL` 加强提交持久化要求，但不能让坏硬件、磁盘丢失或系统级故障绝对消失。备份依然必要。

### 前向迁移改变结构而不丢内容

schema 是表结构与约束；`PRAGMA user_version` 保存数据库结构版本。项目版本如 1.0.1 与 schema4 不同：应用升级可能不改表，表升级也不必等同界面功能数量。

旧库迁移先验证一致备份，再在事务中改表、复制原对象、补资产和快照结构，最后更新 user_version。失败时回滚原库并保留备份，不把坏库伪装成“空新作品”。

下面沿 schema1 的结构重建读源码，再核对 schema2/3 直接补结构的路径。不要手动改 user_version 试图“跳过”迁移，这会使代码误判真实表结构。

## 2. 从书架走到磁盘

正式客户端默认数据位于Windows用户本地应用数据目录。
项目根与数据根是两件事；代码在E盘不代表用户作品也在E盘。

```text
%LOCALAPPDATA%\RainSoul\
  catalog.sqlite
  Projects\
    <作品UUID>\
      project.sqlite
```

catalog.sqlite保存书架摘要，可从各作品数据库重建。
project.sqlite保存正文、卷章、元数据与操作回执，是权威来源。
作品标题用于显示，不参与决定目录名称。
因此两个“雨落之后”仍拥有不同UUID与不同文件。

只读查看实际位置：

```powershell
Get-ChildItem -LiteralPath "$env:LOCALAPPDATA\RainSoul\Projects" -Directory
```

不要把教材中的占位UUID原样当作实际路径。
先从设置的本机数据路径确认当前应用用的是哪个目录。

## 3. 为什么缓存允许失败

正文事务成功后，仓储刷新书架摘要。
若摘要刷新失败，不能把已经成功的正文写入伪装成保存失败。
refreshCache会把作品加入pending集合，稍后重新刷新。
应用启动时reconcileCatalog扫描作品目录重建摘要。

数据流如下：

```text
正文事务提交
→ 尝试刷新书架摘要
→ 成功：摘要最新
→ 失败：正文仍成功，标记待刷新
→ 下次读取或启动：重新汇总
```

这是由“正文权威，缓存可重建”这个设计决定的。
如果两份数据都声称自己权威，失败后就无法确定哪份正确。

## 4. 跟做：阅读schema版本

schema.ts通过SQLite的user_version区分数据库版本。
它先启用数据库约束和写入设置：

```typescript
db.pragma('foreign_keys = ON');
db.pragma('journal_mode = WAL');
db.pragma('synchronous = FULL');
db.pragma('busy_timeout = 1000');
```

foreign_keys帮助防止章节指向不存在的卷。
WAL把提交变化先写入日志，稍后合并到主文件。
synchronous=FULL强调提交的持久化要求。
busy_timeout让短暂竞争有机会等待，而不是立即失败。
这些设置不是无限性能或绝对零丢失的保证。

## 5. 迁移前为什么先备份

schema1没有目前卷章管理需要的完整结构。
升级不能通过“删旧库重新创建”完成，因为里面有作者正文。
迁移函数先生成独立备份，再在事务中改表。

真实备份入口：

```typescript
const backupPath = `${db.name}.v1-backup-${randomUUID()}.sqlite`;
db.prepare('VACUUM INTO ?').run(backupPath);
```

VACUUM INTO读取已提交的WAL状态，生成一致的新数据库。
直接复制正在使用的project.sqlite可能遗漏WAL里的已提交数据。
备份随后以只读方式打开，quick_check必须返回ok。
验证失败就停止升级，不先修改原库。

## 6. 迁移事务具体做什么

打开migration.ts，按顺序核对：

1. 给work_meta增加deleted_at。
2. 建立volume表。
3. 将旧chapter改名为chapter_v1。
4. 创建含volume_id与软删字段的新chapter。
5. 复制旧章节的ID、标题、正文、字数、顺序。
6. 删除事务内的旧临时表。
7. 验证正文结构、外键和数据库完整性。
8. 建立资产、搜索与快照结构，校验后把 user_version 设为当前版本 4。

原章节ID不会因为升级改变。
保留ID，后续引用、排序和回执才不会失去对象身份。
上述操作在immediate事务内一起成功或一起回滚。

## 7. 跟做：在测试库中验升级

```powershell
npm run test:unit -- tests/unit/migration.test.ts
```

测试自行建立临时旧库，不在你的真实作品上试验。
打开测试文件，找旧正文保留、损坏正文回滚和备份失败场景。
预期成功迁移后 user_version 为 4，原正文与稳定 ID 仍在。
预期失败迁移不留下半套新表，并报告MIGRATION_FAILED。

本项目已实现的失败行为是事务回滚并保留原库与备份。
不要写成“遇到任何故障都会自动删原库再复制备份”。
人工恢复仍需先核对应用已经关闭和备份完整性。

## 8. 文件路径也要校验

projectDb先验证UUID，再组合路径。
已有目录和数据库不允许符号链接。
元数据必须恰好一行，并且id与目录一致。
否则标题相同、路径跳转或文件被换掉，都可能让应用写错对象。

这些校验在读取库后、使用库前进行。
“磁盘上有个sqlite文件”还不等于“这是合法作品”。
文件身份、schema版本和正文结构都需要分别验证。

## 9. 故障诊断

| 现象 | 可能原因 | 先做什么 |
| --- | --- | --- |
| 升级前备份失败 | 空间不足或权限限制 | 停止升级，保留原库 |
| UNSUPPORTED_SCHEMA | 数据来自更高版本 | 使用匹配版本，不降级改表 |
| 元数据不一致 | 文件或目录身份被改变 | 核对UUID与来源 |
| 书架统计旧但正文新 | 缓存刷新未完成 | 检查重建流程而非覆盖正文 |

不要删除唯一原库来“清掉缓存”。
删除权威数据和重建摘要缓存是两种完全不同的操作。

## 10. 练习与答案提示

练习一：为什么不用作品标题命名数据库目录？
答案：标题可改、可同名，还可能包含不合法路径字符。

练习二：为什么备份要包含已提交WAL状态？
答案：最近提交可能尚未合并回主文件，单独复制主文件不完整。

练习三：未来 schema5 迁移应先写什么？
提示：先写 schema4 样本保留、失败回滚、未知版本拒绝等测试，再写迁移。

本章检查点：你能指出哪份数据能重建、哪份必须保护，并解释迁移事务边界。
