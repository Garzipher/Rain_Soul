# 第一章 每部作品如何独立保存

本章状态：按作品SQLite、可重建目录缓存、schema v1到v2迁移已实现；后续知识与快照表尚未完成。

学习目标：认识正式数据与派生缓存的区别，理解数据升级为什么先备份、再事务迁移、最后验证。

阅读 `src/workers/database/repository.ts` 的构造、`createWork` 和 `openWork`，然后查看 `src/workers/database/schema.ts`、`project-schema.ts`。作品使用稳定UUID目录，每部作品保存自己的 `project.sqlite`。

目录库记录标题、字数、章节数等书架摘要，可从作品库重新扫描建立。正文是主数据，缓存写失败不能把已经成功的正文提交说成失败。

创建作品时先在临时目录建库，在事务中写作品与首章，关闭数据库后重命名为正式UUID目录。这样书架不会扫描到只创建了一半的正式项目。

实践步骤：

1. 使用测试创建两个同名作品，观察标题相同但ID和目录不同。
2. 修改其中一个正文，确认另一个没有变化。
3. 阅读 `refreshCache` 的pending集合，说明缓存暂时失败后怎样再刷新。
4. 对照 `tests/unit/repository.test.ts` 的隔离、重启和目录扫描用例。

数据库新增分卷字段时，旧v1库不会自动拥有新结构。`src/workers/database/migration.ts` 负责先创建升级前备份，再在同一事务中新增volume表、重建chapter表和设置user_version。

迁移前不能只复制主数据库文件：SQLite WAL中可能还有已提交内容。实现使用 `VACUUM INTO` 生成一致镜像，并独立打开备份执行 `quick_check`。

一个例子：正文已经提交到WAL但尚未checkpoint。如果只复制 `project.sqlite`，备份可能缺最后一段；一致镜像应能在没有原WAL的情况下读到完整原稿。

```text
一致备份 → 验证备份 → 开始事务
→ 变更结构并复制旧数据 → 校验正文/外键/完整性 → 更新版本 → 提交
```

如果备份失败，原库不修改；如果事务内验证失败，结构、正文和user_version一起回滚，同时保留可用的升级前备份供排查。

证据入口：`tests/unit/migration.test.ts` 使用真实SQLite并特意保留WAL；`tests/unit/repository-structure.test.ts` 检查升级后旧正文与新卷章能力。

练习：写出主数据、派生目录摘要和升级前备份三者各自能否删除、能否重建、由谁读取。不要在真实作品目录试删数据，使用临时测试库。

后续学习：未来每次schema升级必须新增迁移和旧数据夹具；当前完成v1到v2不代表以后所有迁移都会自然安全。
