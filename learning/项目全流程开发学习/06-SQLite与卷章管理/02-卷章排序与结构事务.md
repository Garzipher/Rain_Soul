# 卷章排序与结构事务

《雨落之后》可以直接有章节，也可以先建卷再放章节。
本章用“第一卷 旧站台”和“第二卷 雨声”解释归属与排序。
完成后，你能追踪一次“把章节移入卷”的完整提交过程。

**状态说明（2026-10-08）：**创建卷章、改名、同级移动、跨卷归属已实现。
卷章目录与已实现的剧情大纲树不是同一种数据，不能混为一谈。

## 技术基础：同级集合、排序与外键

### 先确定集合，再谈顺序

“上移一章”必须先说明在哪些章中移动。章节的同级集合由 volume_id 决定；null 是无卷区。第一卷中的 sort_order=0 和第二卷中的 sort_order=0 不冲突，因为它们位于不同集合。

正式展示先排卷，再排卷内章节；SQL 的全局排序若只看 sort_order，会把各卷的第一章混在一起。跨卷移动先改变归属，再追加到目标同级集合末尾。

### 外键约束与业务规则

外键可阻止章节指向不存在的卷，但不直接阻止指向“已软删除的卷”。目标对象仍在表中，外键认为它存在；`assertVolume` 还要要求 deleted_at 为空。关系合法不代表当前业务状态允许使用它。

SQL 中 `NULL = NULL` 不是 true；项目查询用 `volume_id IS ?` 同时处理无卷和有卷值。这是 SQL 三值逻辑与 JavaScript 相等判断的区别。

### 一次同级交换为什么要事务

```text
旧顺序：A=0，B=1，C=2
将 B 上移：把 B 设为 0，把 A 设为 1
结果：B=0，A=1，C=2
```

若第一条 SQL 成功后异常，可能出现两个 0。事务保证两次更新与 revision/回执一起提交或一起回滚；稳定 ID 与正文保持不变。

接下来同时看章节 ID、归属和 sort_order，而不是只看显示标题。标题可重复，ID 才能证明移动的是原章节。

## 2. 模型为什么允许无卷章节

chapter.volume_id为null表示章节不属于任何卷。
volume_id有值时，必须对应有效卷。
作品先写几章再决定分卷，不必提前建立空架子。

真实章节表中的有关字段：

```sql
sort_order INTEGER NOT NULL,
volume_id TEXT REFERENCES volume(id),
deleted_at TEXT,
deletion_batch TEXT
```

sort_order是同级位置，不是全局章号。
第一卷第一章和第二卷第一章都可以有sort_order=0。
排序必须结合volume_id看，而不能只按sort_order排序全书。

## 4. 同级邻居怎么找

structure.ts的move先取当前对象，再查同级活动对象。
章节使用volume_id限制同级范围。
卷则只在作品自己的volume表中排序。

真实章节查询：

```sql
SELECT id, sort_order FROM chapter
WHERE volume_id IS ? AND deleted_at IS NULL
ORDER BY sort_order, id
```

这里用IS可以处理null归属。
ORDER BY中的id为相同排序值提供确定性次序。
找到相邻对象后交换两个sort_order。
没有邻居时直接返回，不越过其他卷移动。

## 5. 跨卷移动不是同级交换

setChapterVolume先检查章节存在，再确认目标卷合法。
目标卷不可来自另一部作品，也不能处于已删除状态。
如果原卷与目标卷不同，更新volume_id并追加目标末尾。

```typescript
db.prepare('UPDATE chapter SET volume_id = ?, sort_order = ? WHERE id = ?')
  .run(action.volumeId, nextChapterOrder(db, action.volumeId), action.chapterId);
```

nextChapterOrder只统计目标归属下未删除章节的最大顺序。
再次移动到当前卷不会重复改变位置。
跨卷后稳定chapterId与document_json仍原样保留。

## 6. 一次结构请求的旅程

界面不是直接操作SQLite。
按钮或右键菜单形成StructureAction。
主进程严格校验StructureRequest并检查当前作品权限。
Worker调用repository.manageStructure。
仓储在commit中完成幂等判断、版本比较和结构修改。
最终返回最新WorkDetail供界面更新。

```text
菜单动作
→ 等待当前草稿flush
→ 生成operationId与expectedRevision
→ StoreService串行校验
→ Worker调用仓储
→ SQLite事务提交
→ 返回最新卷章与正文
```

先flush避免结构回执与尚未保存的标题互相覆盖。
读取最新WorkDetail也避免旧回执把新正文带回旧状态。

## 8. 为什么所有修改必须在事务内

移动要更新两个对象，不能只成功其中一个。
跨卷修改还会递增revision并记录operation_log。
这些信息如果分开提交，正文状态与回执就可能不一致。
仓储commit用immediate事务包住整个修改。

参数校验失败，应在合法写入前阻止操作。
数据库修改失败，事务自动回滚已有修改。
界面只接受完整成功结果，不自行猜测数据库最后状态。

## 9. 故障诊断

| 现象 | 优先检查 | 说明 |
| --- | --- | --- |
| 向上移动越到别的卷 | peers查询归属条件 | 同级必须受volume_id限制 |
| 跨卷后正文消失 | 是否重建章节 | 应修改属性而非重建对象 |
| 非法卷增加了版本 | 事务边界 | 拒绝应整笔回滚 |
| 连点创建多出两章 | 请求身份与忙状态 | 区分真实两次操作与同一次重试 |

不要让renderer传入任意表名或SQL来处理排序。
动作类型应受枚举与严格schema约束。

## 10. 练习与答案提示

练习一：无卷章与第一卷第一章都为sort_order=0，是否错误？
答案：不是，它们属于不同同级集合。

练习二：把第二卷“雨声”移入第一卷，应改哪些字段？
答案：volume_id与sort_order；稳定ID和正文不应变化。

练习三：同级第一章向上移动，为什么不报错？
提示：它是合法边界操作，没有邻居时保持顺序即可。

## 延伸实验：位置变化与身份不变

在测试中保存移动前的chapterId和全部document_json。
完成跨卷、同级上移、移出卷后，逐项比较原值。
允许变化的是归属和顺序，不允许变化的是正文内容与稳定身份。
如果测试只看标题，创建了另一份同名空章也可能蒙混过关。
章节标题不是对象主键，测试定位也不能只靠一段可能重复的文字。

结构请求还有作品级权限边界。
打开作品A后，尝试使用作品B的卷ID，应明确失败。
它既不应该让B发生修改，也不应该让A的revision增加。
数据库外键只能证明目标卷存在，无法单独证明这次请求属于当前授权作品。
因此主进程授权校验与作品隔离库都需要保留。
