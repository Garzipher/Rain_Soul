# 第二章 卷章管理也是数据修改

本章状态：可选分卷、新增改名、同级排序、章节移卷与结构回执已实现；剧情节点树是另一个待实现模型。

学习目标：把“移动一行UI”理解为带权限、版本和事务的结构修改，避免正文与章节树互相覆盖。

先读 `src/shared/contracts.ts` 的 `StructureAction`，再读 `src/shared/structure-schema.ts`。明确的命令联合描述创建卷、移动章、移卷、删除恢复等动作，运行时严格校验不接受额外任意字段。

继续读 `src/workers/database/structure.ts`：章节的 `volume_id` 可以为null，代表无卷；卷与章分别维护 `sort_order`，移章只在同一父级内交换顺序。

例子：无卷区有A、B，第一卷有C、D。移动C向上只影响第一卷；把B移入第一卷后，B追加到第一卷的现有末尾，不误改无卷区其他章节。

实践步骤：

1. 找 `move` 中peer查询的 `volume_id IS ?`，解释null父级如何比较。
2. 找 `setChapterVolume` 和 `nextChapterOrder`，记录移卷后如何确定末尾位置。
3. 看 `WorkRepository.manageStructure`，找到事务、expectedRevision与operationId。
4. 回到 `src/renderer/App.tsx`，检查结构回执如何更新当前作品。

为什么移动后也增长作品revision：结构和正文共同属于作品状态。若只改树而前端仍持有旧revision，下一次正文保存就会遇到版本冲突。

新增章节同样需要幂等。请求已经提交但回执丢失时，重试原operationId应返回原结果，不能再新增一个同名章节。

操作流程可以整理为：

```text
最新草稿保存 → 校验当前作品权限 → 校验版本
→ 事务修改卷章 → 写回执 → 返回新作品结构 → 同步页面revision
```

界面入口包括右键菜单和键盘操作，相关文件是 `chapter-tree.tsx`、`context-menu.tsx`、`structure-dialog.tsx` 与 `hooks/use-structure-menu.ts`。菜单只负责表达意图，不能自行写数据库。

证据入口：`tests/unit/repository-structure.test.ts` 覆盖边界顺序、移卷和幂等；`tests/unit/renderer-structure.test.tsx` 覆盖实际交互；真实Worker测试覆盖严格命令与权限。

练习：先把某章移到另一卷，再立即修改正文。断言保存成功、章ID不变、volumeId不回退。这个用例能发现“新正文回执覆盖旧结构”的错误。

后续学习：剧情树允许更深层级，要额外防循环、处理父子关系和关联；不能直接把两层卷章排序函数当成无限层树方案。
