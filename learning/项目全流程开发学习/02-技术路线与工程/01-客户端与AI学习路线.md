# 第一章 为什么客户端采用 Electron，而 Python 单独学习

本章状态：Electron + React/TypeScript + SQLite 已用于客户端；Python/FastAPI 尚属后续 AI 学习与验证路线。

用户比较技术路线后，确认先用 Electron 交付 Windows 客户端，把 Python/FastAPI 纳入 AI 学习实验。关键问题是启动依赖：普通作者应能直接运行客户端，不需要先启动 Python 服务。把 Python 引入正式启动链，会增加打包、端口、进程生命周期和错误排查成本，首批没有必要承担这些依赖。

Electron 主进程能调用系统文件、窗口和凭据能力；React 组织界面；TypeScript 约束 DTO 和状态；SQLite 提供离线事务。代价是程序体积、进程资源和原生模块打包需要检查。这种选择适合同时学习前端、桌面边界和数据一致性，但不能据此宣称它对所有项目都最优。

Python 的优势在于 AI 实验、文本分析和服务开发生态。后续可以在 `experiments/ai-python/` 独立验证知识检索、模型适配和评测，用 FastAPI 暴露一个实验接口。该目录在目标方案中，尚未因为写了计划就自动存在。实验通过后再决定是否有理由引入产品，不让学习实验阻断作者写作。

实践步骤：先画客户端闭环，再做可替换实验。客户端“选文 → 授权 → 服务适配 → 候选”使用清晰 DTO。Python 实验可以读取专门准备的脱敏样本，输出同类候选结构；比较正确性、耗时和费用，不能拿实验代码直接写正式 SQLite。

示例实验接口设计：请求包含 `operation`、`sourceRevision`、`paragraphs`；响应包含候选、证据和不确定性。这个例子是后续设计练习，当前应用没有此接口，也没有默认向外发送正文。

阅读对接：技术方案第 1 节和第 10～11 节；`package.json` 可核对当前客户端没有 Python 启动依赖。`src/main/index.ts` 建窗口和数据库客户端，没有 FastAPI 子进程。

练习：用一页纸比较“主进程直接适配云服务”和“本机 Python 代理”的启动步骤、失败位置、密钥存放与升级成本。说明什么实际证据会让你改变当前选择。
