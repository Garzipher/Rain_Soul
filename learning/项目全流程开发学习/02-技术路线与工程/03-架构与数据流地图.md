## 前置知识

已完成构建章节，知道三个桌面入口。

不要求会写并发程序，但要接受不同进程不能直接共享普通对象。

## 技术基础：分层、契约与异步结果

### 层次是责任边界

分层把一个动作分成可独立验证的责任。展示层知道用户想做什么，服务层检查能否做，仓储层决定如何安全写盘。把所有代码分成文件并不自动构成分层；如果页面能绕过服务直接执行 SQL，边界仍然破了。

`src/shared/contracts.ts` 是各层约定的参数和结果。契约类似函数的说明书：合法输入是什么、成功返回什么、失败由谁处理。它不携带 SQLite 连接或 DOM，因为这些对象不能安全跨层传输。

### Promise 的执行与等待

Promise 表示一个将来的结果；`await` 暂停当前异步函数的继续执行，不会阻塞整个浏览器事件循环。因此保存期间仍能展示“保存中”。如果底层 Worker 没有回传或拒绝，Promise 就可能一直悬而未决。

```typescript
// 只解释异步顺序，真实保存方法见后面的调用链。
async function observeSave(save: () => Promise<void>) {
  console.log('开始');
  await save();
  console.log('收到成功结果');
}
```

第二条日志代表结果已确认。若 `save` 拒绝，函数抛出错误，不会输出第二条。UI 要捕获错误、保留草稿并改变状态；不能把“函数调用了”当成“写盘完成”。

### 一次输入有哪些身份

作品 ID 决定哪部作品，章 ID 决定哪一章，段落 ID 决定哪一段。`revision` 决定我们基于哪个已提交版本，`operationId` 识别本次业务修改，`requestId` 关联一趟 Worker 消息。每个身份有不同寿命，理解它们比背下文件名更有用。

跟读下面的主线时，给每个箭头标明“带了哪些值”。然后检查回来的值是否足以让 UI 确认保存并继续下一次修改。

## 1. 先画主线，不先画所有文件

```text
作者输入
  ↓
ChapterEditor
  ↓ 受限文档
useWritingSession / SaveCoordinator
  ↓ saveChapter(...)
preload: rainSoul
  ↓ rainsoul:command
main: StoreService
  ↓ 校验、权限、串行队列
database client → database worker
  ↓
WorkRepository → SQLite事务
  ↑
保存结果：revision / wordCount
```

箭头表达数据和控制的流向，不代表每层都复制一个数据库。
UI 不直接调用仓储，仓储也不直接控制页面上的保存提示。
它们通过受限契约合作。

## 2. 找到最窄的公共契约

```powershell
Set-Location E:\soulrain
Select-String -Path .\src\shared\contracts.ts `
  -Pattern 'saveChapter|SaveResult|DesktopApi' -Context 0,2
```

保存参数包括作品、章节、标题、正文、预期版本和操作 ID。
结果包含新的版本与字数，而不是把整个数据库对象暴露给页面。

```ts
export interface SaveResult {
  revision: number;
  wordCount: number;
}
```

这是一个完整的返回值接口示例。
页面只需要知道本次保存是否被接受，以及下一次应基于哪个版本。
它不需要 SQL连接、文件句柄或任意磁盘路径。

## 3. 追踪“去”的方向

依次执行下面命令，每次只看一个文件入口。

```powershell
Select-String -Path .\src\preload\index.ts `
  -Pattern 'saveChapter' -Context 0,2
Select-String -Path .\src\main\store-service.ts `
  -Pattern 'saveChapter|activeWork|queue' -Context 0,2
Select-String -Path .\src\workers\database\worker.ts `
  -Pattern "case 'saveChapter'" -Context 0,2
```

预加载层把固定参数包装成明确命令。
权限服务先检验数据形状，再确认只能修改当前作品。
Worker 根据白名单命令调用仓储。
真正的 SQLite 改动发生在仓储事务中。

不要把 Worker 的类型断言 `as string` 理解为运行时验证。
它只是告诉 TypeScript 如何看待值。
真正外部边界的校验由 StoreService 与仓储再次承担。

## 4. 再追踪“回”的方向

```powershell
Get-Content .\src\main\database-client.ts
Select-String -Path .\src\workers\database\worker.ts `
  -Pattern 'postMessage' -Context 0,1
```

DatabaseClient为每次进程请求生成 `requestId`。
它把等待者放入 Map，收到对应回执后才 resolve 或 reject。
Worker 回传同一个 `requestId`，避免多个请求同时存在时串错结果。

保存业务里的 `operationId` 又是另一种身份。
它跨重试保持稳定，用于防止同一业务操作重复落盘。
`requestId` 关联一次传输，`operationId` 识别一次业务操作。
把两者混为一谈，会在回执丢失时错误重试。

## 6. 用表格记录每一层的责任

| 层 | 收到什么 | 负责什么 | 不应拿到什么 |
| --- | --- | --- | --- |
| React | 作者动作 | 展示与草稿状态 | SQLite连接 |
| preload | 固定方法参数 | 窄 API桥接 | 任意命令执行入口 |
| main服务 | 命令与payload | 来源、结构、当前作品权限 | 无限制renderer信任 |
| Worker | 已限定请求 | 同步数据库工作 | DOM与页面焦点 |
| 仓储 | 业务参数 | 校验、版本、事务、回执 | UI组件状态 |

每层都有可解释的存在理由。
如果发现某段新代码跨越两层直接访问资源，应先检查是否破坏边界。
并非文件越多越先进，而是责任能够被独立验证。

## 常见问题与排查

| 现象 | 优先观察 | 下一步 |
| --- | --- | --- |
| 点击后一直等待 | pending请求、Worker错误 | 看是否有exit/error传播 |
| 修改其他作品被拒绝 | activeWork检查 | 先明确打开目标作品 |
| 重试引起冲突 | operationId与revision | 检查是否保留原请求 |
| 保存成功UI没更新 | 返回结果与协调器 | 查回执是否正确接受 |
