# 第三章 用一次保存串起整个工程

本章状态：下述正文保存链已经实现；文件任务、搜索和 AI 是后续扩展。

学习架构最有效的方式是追踪一次具体动作。作者输入“雨停了”，编辑器产生受限文档；`use-writing-session.ts` 更新草稿；`SaveCoordinator` 安排提交；`window.rainSoul.saveChapter` 进入预加载层；主进程 `StoreService` 校验并排队；`DatabaseClient` 发给 Worker；`WorkRepository` 在事务中保存并返回新 revision；回执逐层返回，界面再更新已持久化状态。

这条链包含三种不同标识。`workId/chapterId/paragraphId` 定位实体；`operationId` 识别一次业务写入，重试保持不变；`requestId` 只关联一次主进程与 Worker 往返，重试运输时可以不同。把 operationId 当 requestId 每次重建，会破坏幂等保护。

简化数据流：

```text
编辑器 → 草稿/保存协调器 → preload窄API
      → 主进程校验与队列 → 数据库Worker
      → 作品SQLite事务 → revision回执 → 界面保存状态
```

实践步骤：从 `chapter-editor.tsx` 找 `onUpdate`，进入写作 Hook；再沿着共享 API 找 preload 的 `invoke`。在主进程找到 `rainsoul:command`，确认来源校验后才进入 StoreService。最后在 Worker 的 switch 找到 `saveChapter`，阅读仓储的 `commit`。

边界分工有实际意义：界面不能直接打开 SQLite；Worker 不负责弹窗；仓储不知道按钮长什么样。新功能沿边界增加 DTO、命令和领域行为，避免在 App 里拼 SQL，或让 Worker 回传完整内部数据库对象。

此图也为学习作品未来的“伏笔架构”提供素材：可以把“保存请求”“版本回执”“关闭握手”分别作为联系条目，将入口、接收方、错误返回和源文件写为证据。当前正式伏笔模块还未交付，因此先在文本里记录联系，不冒充已经创建了伏笔数据。

验证对接：`tests/unit/database-worker.test.ts` 与 `database-structure-worker.test.ts` 验证真实编译 Worker；`renderer.test.tsx` 验证草稿行为；桌面测试跨过全部边界检查重启结果。
