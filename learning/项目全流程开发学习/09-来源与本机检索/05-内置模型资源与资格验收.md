# 内置模型资源与资格验收

本章讲解把中文嵌入模型放进安装程序的工程过程。嵌入模型把知识和查询转换为向量，帮助找到相关描写；它不能续写或润色。本项目已实现资源准备、只读加载和作者偏好管理。2026-10-13作者批准固定公开仓库版本、许可和文件hash作为来源依据，精确转换链改为补充；本轮含模型实际包已完成底层和离线UI专项，下方分别保留旧无模型与新含模型证据。

## 1. 模型文件与运行库

ONNX 是描述计算图与权重的模型格式；ONNX Runtime 执行计算图。Tokenizer 将文本变成模型输入ID，配置文件说明词表、特殊token和参数。缺少任一配套文件或使用不同版本，可能改变向量维数、语义或分数。

RainSoul 使用固定 tokenizer、CPU/WASM、512维、CLS池化及L2归一化。模型窗口、查询前缀和分块策略也属于实现身份。每次行为改变都更新指纹并重建派生索引，不能把新向量与旧缓存混用。

候选五文件合计24,451,175字节，约23.32 MiB。这是资源大小，安装器压缩增量、首次加载时间和内存峰值必须通过实际包测量。

## 2. 为什么放在 resources 而不是 app.asar

Electron 的 app.asar 保存程序文件。模型作为 `extraResources` 放在安装目录的独立只读树，避免首启复制一份大权重，也便于核对真实运行文件。主进程从可信 `process.resourcesPath` 计算固定目录，渲染层不能提供任意本机路径。

```text
明确提供的本地输入
  → prepare-bundled-retrieval-model.mjs：路径、长度、hash、来源
  → dist/retrieval-model/<revision>/weights + notices
  → model-pack-policy.mjs：正式或无模型研究模式
  → electron-builder extraResources
  → check-bundled-model-package.mjs：实际resources复验
  → retrieval-model-store.ts：只读选源与资格
  → 独立检索Worker：CPU/WASM推理
```

`weights` 只允许manifest的精确五个文件，许可证和模型卡放进 `notices`。准备脚本使用临时目录、锁与原子发布；输入文件增长也受有界读取限制。检查来源目录后再检查真实包目录，不能让旧dist残留冒充本轮准备结果。

模型检查只负责模型资源，程序包还由 `desktop-package-audit.mjs` 单独审计。它在打包前后枚举构建白名单，再读取真实 ASAR 成员和解包旁树，核对文件长度、SHA-256 和成员集合。不能只相信归档头中的 hash；WASM 等解包文件也要读取实际字节。生成的审计报告保存在包目录的 `acceptance`，实际 EXE 测试再次独立计算并比较，避免把旧报告当成新包证据。

## 3. 文件hash与来源资格的区别

SHA-256 能证明“当前字节与预期一致”，不能独自证明转换过程或分发许可。因此资源身份需要同时记录公开仓库修订、模型卡、许可和五文件hash。RainSoul使用 `assets/retrieval-model-provenance.json` 固定这组材料；准备脚本核对模型身份摘要、材料字节和许可原文，临时CLI参数不能改写来源锚。来源摘要排除验收标志和校准阈值，保留权重、运行配置及许可；实际包报告再绑定完整清单，避免校准更新使来源身份失效。

本轮政策允许使用既有公开量化版本，不再要求取得精确输入revision/hash和转换工具链。BAAI参考版本仍只是参考，不冒充已证明的转换输入；从镜像取得材料不改称官方原站交叉核验。需要自转换时可以额外记录环境、参数和输入输出hash，但它不是本轮分发的必需前置。

| 门槛 | 当前方法与证据边界 |
| --- | --- |
| 固定公开来源 | 固定仓库、修订、两张模型卡、完整MIT原文及五文件hash |
| 离线运行 | 真实包中的WASM和本地权重；JS网络入口拦截只证明其观察范围 |
| 中文质量 | 100知识/30验收/20独立校准查询；标签是开发者预标注，不称真人审核 |
| 实际包运行 | 指定EXE、ASAR、运行库、WASM和权重前后hash一致，重新测量加载与质量 |
| 补充验证 | 官方交叉/精确转换、系统抓包、独立真人审核、干净Windows矩阵分别记录 |

先生成含权重但未激活的验收包，再测试和决定启用，避免“必须先启用才能证明可以启用”的循环。政策获批、文件准备成功与模型运行成功是不同事实：没有实际结果就保留待验。

## 4. 来源、启用、资格、索引是四种状态

`selection.json` 保存作者明确选择的 bundled/user 来源和 enabled 偏好。旧 `active.json` 只在新记录缺失时迁移，旧文件保留；旧false保持false并解释，不能自动推测作者想启用。

文件存在表示资源可读；资格通过表示允许正式运行；enabled表示作者偏好；索引状态表示知识的派生向量是否准备好。设置面板分别呈现这些状态。若用户明确选择的副本损坏，程序回退关键词并等待换源，不能悄悄切到另一份模型。

换源或停用先递增generation，关闭旧Worker并清除调度状态，再保存偏好。等待保存期间不启动推理。旧结果即使晚到，也无法写入新代缓存。偏好落盘失败保留可解释状态，不把内存操作误报为持久成功。

### 含模型包如何证明实际加载

先按 `tasks/bundled-model-acceptance.md` 准备固定五文件和notices、串行build/pack，选择本轮实际 `win-unpacked/RainSoul.exe`。以下命令需要替换为本轮已核对的真实路径：

```powershell
node scripts/accept-packaged-retrieval-model.mjs --executable 'E:\验收包\win-unpacked\RainSoul.exe' --report 'E:\验收包\acceptance\retrieval-model.json'
```

工具在指定EXE的主进程启动隔离Worker，仅读取包内运行库/WASM和旁树权重；固定中文夹具不读取作者知识库。前后重算hash以拒绝中途更换包，向量必须512维且归一化，阈值沿用校准结果，不按验收答案反向调分。报告展示漏召回及无相关误报，而不是只展示成功句子。

打开JSON核对范围：推理Worker拦截JS网络入口、renderer离线，不等于全系统抓包；运行库质量不等于正式UI的混合排序、分页、索引恢复和并行保存。完成后再测界面/持久化，Windows安装卸载另走十四格矩阵。没有结果时不能把该工具命令写成“已通过”。

### 安装器为什么会多出更新服务配置

electron-builder 的发布策略与更新服务配置是两条链路。`publish: 'never'` 禁止上传，但工具仍可能根据 `package.json` 的仓库地址推断 GitHub 更新服务，并在 NSIS 构建时写入 `resources/app-update.yml`。本项目尚未提供自动更新，因此在 `scripts/model-pack-policy.mjs` 中显式设置 `config.publish: null`，关闭服务推断；严格资源审计继续拒绝未知文件。

本次实践先新增回归，观察到缺少 `publish` 的失败，再设置 null，并调用锁定版本 builder 的真实 `getAppUpdatePublishConfiguration` 接口，确认返回 null。最后仍须重新生成实际安装器，因为接口测试不能证明打包后的资源目录。跟做时比较 `scripts/pack-desktop.mjs` 的发布策略与 `model-pack-policy.mjs` 的服务配置，解释它们各自控制的行为。

安装器后期还有另一条资源链路：NSIS 默认复制 `elevate.exe`，它发生在 `afterPack` 之后。普通用户安装关闭 `packElevateHelper` 和 `allowElevation`，避免加入无用的提权组件；整个 builder 完成后仍需再审计最终目录。练习：首次审计通过后追加一个未知资源，观察最终审计是否拒绝，并确认旧审计证据不被覆盖。

Windows 文件扫描也可能短暂锁住刚生成的 EXE。完整性写入只对 Windows 的 `UNKNOWN/open`、`EBUSY/open` 最多执行五次，每次仍执行原完整操作，间隔 1500ms；权限错误、非 open 错误与耗尽均原样失败。不要通过跳过完整性写入来解决文件锁。首次并行检查曾使 builder 接口测试超时，串行复验才通过；失败与复验记录分别保存，不能合并成一次成功。

## 6. 拓展练习

1. 修改测试资源一个字节，追踪准备、打包和运行各层在哪里拒绝。
2. 模拟明确选中的user资源损坏，解释自动换源为什么会违背作者选择。
3. 在索引中途停用模型，观察generation与迟到结果。
4. 列出正式权重包与无模型研究包分别可以支持哪些结论。
5. 为可选自转换方案设计可复现记录，包括输入revision、环境锁定、转换参数和hash；解释它与本轮固定公开量化源方案的区别。
6. 阅读 `tests/unit/desktop-package-audit.test.ts`：分别向构建树、ASAR 和解包旁树加入额外文件，解释三层检查为什么都需要。再修改一个解包字节，确认即使归档头没有变化，审计也会拒绝。
