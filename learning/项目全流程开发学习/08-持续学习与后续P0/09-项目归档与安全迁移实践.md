# 项目归档与安全迁移实践

设想电脑要重装，作者需要把“雨落之后”复制到移动硬盘，稍后重新打开。导出 TXT 只能带走正文，无法保存知识、剧情、伏笔证据和历史快照。本章学习如何把完整作品保存成 `.rainsoul` 文件，又如何避免导入时覆盖原稿。

**本章状态（2026-10-09）：**归档编码、数据库抽取、关系校验、导入为新作品与客户端入口已实现。单元测试验证归档篡改、危险文件名和数据库结构；真实 Electron 已验证归档导出、导入为新作品、原作品保留及重启后副本仍在。不要将一次测试通过解释为所有外部归档都兼容；目前只接受受支持的格式和数据库版本。

## 技术基础：完整性、真实性与白名单重建

### hash 证明什么，不能证明什么

SHA-256 为字节生成固定长度摘要，能核对文件是否与清单描述一致。它不是加密，拿到归档的人仍能读取内容；它不是签名，恶意发送者可以修改数据库并重算清单 hash。

ZIP 的 CRC 检查传输或存储损坏，也不是可信来源证明。完整性一致之后，仍要对数据库 schema、字段、文档和对象关系做独立校验。

### 白名单重建为何安全于直接接管外部库

外部 SQLite 文件可能含未知表、触发器或不符合业务规则的内容。项目只读取受支持的内容，并在隔离新库按本项目 schema 重建；不能把归档中的 SQL 直接执行到用户库。

```text
受限 ZIP 校验 → 清单/hash 校验 → 临时只读外部库
→ 表/字段/文档/关系/快照校验
→ 本项目 schema 新库 → 复制允许内容 → 完整性检查
→ 原子移动为新作品
```

原子移动发生在全部内容成功之后。它像资料模块的临时文件 rename，但对象是一整部作品目录；失败只能清理本次 staging，不碰原稿。

### 为什么内部 ID 可以保留

每部作品有独立库，所以导入副本可以保留章节、段落、知识的内部 ID，让书签和证据关系完整。顶层作品 ID 必须更新，快照 payload 中同一身份也要同步更新并重算 hash；否则恢复会认为历史属于另一作品。

读下面的实现时，分别标明“身份改写”“内容复制”“关系核验”。归档完整往返不是简单把 ZIP 解压到原目录。

## 1. 为什么不能直接复制 SQLite 文件

项目使用 WAL 模式。已提交的新稿可能仍在 `-wal` 文件中；只复制主数据库，会漏掉最新正文。直接把整个工作目录压缩，还可能混入操作回执、缓存与其他不应随作品分发的内容。

实现先用 `VACUUM INTO` 得到 SQLite 认可的完整副本，再重建仅含作品内容的新数据库。新的导出库保存卷章、资产、历史与快照；凭据、搜索缓存、旧操作回执和默认教材 tracking 不进入归档。

这不是对原作者库做清理。源库保持原样，导出库是临时产物。源码入口：`src/workers/database/archive-project.ts` 的 `exportProjectDatabase`。

## 2. 一份归档的契约

`.rainsoul` 是受限 ZIP，只允许两个成员：

```text
作品备份.rainsoul
├── manifest.json
└── project.sqlite
```

清单中保存格式版本、源作品 ID、数据库版本和数据库字节 SHA256。契约定义在 `src/shared/archive.ts`，ZIP 编解码在 `src/main/project-archive.ts`。

```typescript
{
  formatVersion: 1,
  projectId: sourceWorkId,
  schemaVersion: 4,
  databaseSha256: hashOfDatabase,
}
```

SHA256 能发现数据库被改动，不是数字签名，也不证明发送者可信。即使 hash 正确，导入端仍需检查 SQLite 内的表结构、正文和关系。

## 3. 从点击到磁盘

```text
写作界面“备份项目”
→ 保存门禁 flush 当前章节
→ preload.exportProjectArchive(workId)
→ ArchiveCommands → Worker 抽取作品数据库
→ 编码受限 ZIP
→ 主进程打开系统保存对话框
→ 在作者选择的位置写入归档
```

渲染层只传作品 ID，不传任意路径。原生文件选择由主进程负责。取消保存是正常结果，不能显示“备份成功”。失败应明确提示，并保留当前稿。

导入则分两步：选择文件生成临时预览 token，作者确认后才调用 `confirmProjectArchive`。token 绑定本次读取的归档，不能拿一个字符串去请求任意文件路径。

## 4. 把外部文件当作不可信输入

解 ZIP 前检查成员数量、名字、大小和压缩方法。不能允许 `../`、绝对路径、重复成员或 ZIP 中藏着其他数据文件。压缩前大小与解压后大小都需要约束，防止小文件解压成巨大内容。

数据库层进一步检查：

1. `integrity_check` 和 `foreign_key_check` 必须通过。
2. schema 版本受支持，表名、字段与关系符合预期，不执行归档自带的未知触发器或 SQL。
3. 每章正文通过受限文档校验；书签目标、分类树和资产关系可解释。
4. 每个历史快照的格式、作品身份与 hash 正确，不能只校验当前章。

导入先在隔离暂存目录重建目标库。完整验证和写入成功后，再将文件移动到最终新作品位置。中途失败清理暂存，原作品不被覆盖。

## 5. 新作品 ID 与旧快照

导入命令的 `operationId` 同时用作新作品 ID 和幂等键。未知回执后重试同一 ID，会返回已完成结果，不再创建第二份作品。

当前作品 ID 变了，历史快照里的 `work_meta.id` 也必须一致更新并重算 payload hash。卷章和知识内部对象 ID 则保留，它们是在新作品数据库里使用的稳定引用，不会与原作品的隔离库相互修改。

默认教材有增量安装 tracking。导入教材归档后获得普通作品副本，不认领系统默认教材身份；作者仍可阅读和修改，不会因课程同步被覆盖。

## 6. 跟做与验证

1. 用测试作品写两章，增加知识、伏笔、剧情关系和一个手动快照。
2. 选择“备份项目”，保存 `.rainsoul` 到自己指定目录。
3. 返回作品集，选择“导入项目”，核对预览后导入。
4. 作品集应出现两部同名但不同身份的作品。修改副本，原稿保持原样。
5. 打开副本快照，核对历史仍可预览恢复；正常退出重启后再次验证。
6. 在测试中篡改归档字节，确认导入拒绝，原作品、历史和已安装课程都保持不变。

单元测试使用临时目录。桌面测试 mock 的只有原生文件对话框返回路径；真实 IPC、Worker、ZIP、SQLite 和界面流程全部执行。相关文件：`archive-project.test.ts`、`project-archive.test.ts`、`archive-commands.test.ts` 与 `tests/desktop/p0-workflow.spec.cjs`。

## 7. 练习与检查点

练习一：为什么 hash 一致仍要检查数据库？答案：恶意发送者可以修改数据库再重算 hash；内容约束必须独立验证。

练习二：导入的教材为什么不保留默认课程 tracking？答案：它是作者的普通副本，不能与系统课程同步身份混淆。

练习三：设计测试证明归档包含 WAL 中的最新稿。

参考步骤：临时库启用 WAL，保存新正文，不人为 checkpoint；从 Repository 导出归档并通过正常导入创建副本；比较副本当前文档、知识、证据和历史，均应等于源作品已提交状态。再修改副本，断言源库不变。若只比较文件存在，主库旧稿也会蒙混过关。

检查点：你能说明保存 TXT、创建快照与备份项目三种动作分别保护什么，以及一次导入失败为何不会覆盖作者已有作品。
