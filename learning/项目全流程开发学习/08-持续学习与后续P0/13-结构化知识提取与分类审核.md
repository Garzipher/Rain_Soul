# 结构化知识提取与分类审核

AI 从“雨落之后”提取角色、事件与优美描写后，不应该直接把它们塞进知识库。作者需要看完整内容、出处、类型和分类标签建议，再决定哪些成为自己的储备。本章补充第十章的逐条审核，解释结构化结果与层级分类同名问题。

**本章状态（2026-10-09）：**结构化提取解析、非法格式降级、分类完整路径、标签选择与逐条审核已实现并接入回写流程，对应自动化通过。模型响应仍采用测试替身，不代表真实云服务已经按格式返回，也不保证提取质量。

## 技术基础：JSON 解析、整体降级与歧义消解

### JSON 合法不等于业务合法

`JSON.parse` 只检查 JSON 语法；`{"items":[{"source":"第一章"}]}` 可以成功解析，却缺 body。Zod 再检查条目数量、正文长度、分类建议和标签。解析语法与验证业务契约是两个步骤。

模型可能返回代码围栏或解释文字，当前解析器接受纯 JSON 或 JSON 围栏；整体契约失败就返回一条全文草稿。它不静默筛掉坏项，因为作者无法知道哪些信息丢失。

### 最小回归的关键断言

```typescript
import { expect, it } from 'vitest';
import { parseAiExtraction } from '../../src/shared/ai-extraction';
it('非法条目保留完整原始回答', () => {
  const raw = '{"items":[{"source":"第一章"}]}';
  const draft = parseAiExtraction(raw);
  expect(draft).toHaveLength(1);
  expect(draft[0].body).toBe(raw);
  expect(draft[0].type).toBe('待分类');
});
```

放在个人练习分支的 tests/unit 临时文件才能使用上述相对导入。保留全文并不等于“提取成功”，而是给作者一个可阅读的失败降级结果。

### 层级路径与稳定分类 ID

同名叶子不等于同一分类。路径“人物 / 外貌”和“景物 / 外貌”帮助作者区分，数据库仍保存各自 UUID。建议匹配只在完整路径或唯一名称确定时自动预选，多个匹配则留空。

父节点遍历用 visited Set 防环；展示路径不是修改关系的权限。作者勾选审核后再编辑内容、出处、分类或标签，要清除审核，因为批准应绑定最终入库对象。

## 1. 结构化结果是草稿契约

`src/shared/ai-extraction.ts` 的 `parseAiExtraction` 读取受限JSON，形成 `AiExtractionDraft[]`。类型、建议分类和建议标签都只是建议；作者确认前没有数据库写入。

```json
{
  "items": [{
    "body": "雨落在旧车站，路灯把人影拉长。",
    "type": "passage",
    "source": "第一章 旧车站",
    "category": "景物描写 / 夜景",
    "tags": ["雨夜", "紧张"]
  }]
}
```

解析器接受纯JSON或JSON代码块；对条目数、文字长度和标签数有约束。模型输出不是可信配置文件，不能由它创建类别、执行命令或指定任意作品ID。

## 2. 非法格式为什么保留全文

如果一百条中某条结构错误，逐条过滤“合法”条目可能让作者误认为所有信息都被保留。当前策略是整个结构不符合契约时，降级成一条普通候选，`body`保留模型完整原文，类型显示“待分类”。

作者可以从完整文本中整理内容，再选分类与标签。系统不把格式失败当成已经提取成功，也不静默丢弃部分输出。原始候选仍可阅读，不会自动替换正文。

练习：给解析器一个缺少body的JSON，断言返回单条全文候选；不能只断言数组非空，必须比较原文是否完整。

## 3. 层级分类不能只显示叶子名

“人物描写 / 外貌”和“景物描写 / 外貌”可以具有同名叶子。仅显示“外貌”无法让作者确认归属。

`extractionCategoryPath`从当前类别向父类别遍历，显示完整路径，使用已访问ID集合防止无限循环。`suggestedExtractionCategory`匹配完整路径或唯一名称；出现多个匹配时留给作者选择，不猜测落点。

```text
人物描写 / 外貌
景物描写 / 外貌
```

数据库仍接收稳定 `categoryId`，完整路径只是展示与建议匹配。重命名类别不会把已有条目改到另一个同名类别。

标签也是作品内已维护字典。建议中的已知标签可供选用；未知分类和标签不会自动创建。作者可以先在设置维护字典，再回来整理，不能让模型无审查地扩充本机分类树。

## 4. 一次明确的作者审核

`src/renderer/components/ai-extraction-panel.tsx`对每条候选展示完整内容、出处、类型、分类/标签建议，以及实际类别选择和标签勾选。

作者修改正文、出处、主分类或标签，审核勾选会重置。这样“审核通过”绑定的是最终内容，不是五分钟前看过的另一个草稿。只有勾选且正文非空的条目才能入库。

```text
模型候选 → parseAiExtraction
→ 每条完整草稿＋分类/标签建议
→ 作者编辑并逐条勾选
→ approveAiKnowledge(items)
→ AiCommands 校验候选身份
→ Worker校验基线与当前作品分类/标签
→ 同事务新建知识并保留AI正文来源
```

`src/workers/database/ai-apply.ts`接收最终 `body/source/categoryId/tagIds`，不覆盖已有条目。未指定分类时落到作品“未分类”，不接受其他作品的分类ID。入库同时保留来源作品、章节/段落与版本，供后续追溯。

## 5. 跟做与验收重点

1. 在测试作品设置中建立两个同名叶子类别与两个标签。
2. 用测试替身返回结构化角色/事件/描写候选，打开回写审核界面。
3. 核对类别下拉框显示完整路径；歧义建议保持未选状态。
4. 修改一条知识内容并核对审核自动取消，再选择类别和标签。
5. 逐条勾选，确认只有选中条目入库，已有知识不覆盖。
6. 模拟无效类别、过期候选或事务失败，核对原稿、已有知识与历史均保持。

真实云端模型返回格式与提取质量需要作者自己的授权配置联调。上述自动化采用隔离目录与响应替身，不会替作者发送正文。

## 6. 练习与检查点

练习一：模型建议“外貌”，当前有两个同名叶子，应自动选哪一个？答案：不自动选，让作者看完整路径后决定。

练习二：改标签后是否可以保留此前审核勾选？答案：不可以，最终入库内容改变后应重新审核。

练习三：设计测试验证未知标签不会偷偷创建。

参考步骤：候选建议“新标签”，当前字典没有它；记录 tag 数量，打开审核界面，断言只展示建议而没有新 tag 行。作者选已有标签后确认，库只新增已审核知识与关系。再让第二条入库触发失败，断言第一条也回滚、原知识和 revision 保持；不得只验证出现错误文案。

检查点：你能说明模型建议、作者选择与数据库ID各自的作用，知道结构解析失败为何保留全文，以及一次审核入库的事务边界。
## 实践补充：更新已有知识与可靠来源

### 先理解稳定身份、版本和材料来源

知识条目的 ID 表示“这是哪一条知识”，revision 表示“这是哪个时刻的内容”。正文书签关联稳定 ID，因此作者更新角色资料时应保留 ID；另建一条同名知识不会自动成为原书签的目标。

授权上下文与替换目标是两个集合。以前章衔接为例，当前章是写入目标，前章和当前章都是获准读取的材料。模型可能根据前章提取角色，不能只因为当前章是编辑目标，就把所有提取结果标成当前章的证据。

本项目记录的是**授权上下文来源**：章节、段落、当时版本、逐字摘录和 SHA256。哈希帮助核对材料是否变化，不证明模型判断正确，也不表示每条知识都逐段引用了所有材料。界面与教材必须把这一层含义说清。

### 在项目中追踪一次更新

```text
AI 返回完整候选
→ parseAiExtraction 形成待审核草稿
→ 默认“新建知识条目”
→ 作者切换为“更新已有知识条目”并明确选择目标
→ 对比更新前内容、出处、分类与标签
→ 修改候选或目标后重新勾选审核
→ AiCommands / StoreService / 数据库复用严格审核协议
→ 单一事务创建保护快照、更新条目及历史、刷新索引、推进版本、写入回执
```

`src/shared/ai-extraction.ts` 使用联合类型表达两种意图。新建不能夹带目标 ID，更新必须带有效 UUID；模型给出的同名角色、自由文本或建议名称都不能直接充当数据库目标。

```typescript
// 新建是默认行为。
{ body: '作者审核的角色摘要', source: '第一章' }

// 更新必须由作者选定稳定身份。
{ mode: 'update', targetId, body: '修订后的角色摘要', source: '第二章', tagIds: [] }
```

更新界面选目标时，先带入原分类与标签，候选正文仍保留。作者移除全部标签时，`tagIds: []` 表示明确清空；省略该字段在底层表示保留原标签。这种区别是更新接口的重要语义，不能在序列化时随意丢掉空数组。

`src/workers/database/ai-apply.ts` 的 `approveAiKnowledge` 检查目标位于当前作品库且仍有效。同一批次更新两次同一条目会整体拒绝，避免后一条悄悄覆盖前一条。正文已经变化也会拒绝陈旧候选。

事务内复用现有 `updateKnowledge`，保留条目 ID、原始跨作品来源及旧历史。新建和更新可以同批提交，任何一条失败都会回滚整批内容、安全快照、索引、版本和操作回执。相同 operationId 重试时读取原回执，不能再次更新或重复创建快照。

### 审计记录为何不能直接充当“出处”

出处回答“作者从哪里取得这段知识”；审计记录回答“哪次候选、读取了什么材料、作者据什么版本审核”。如果把整卷摘录当成出处直接索引，每条摘要都会因为同一卷中的任意词而命中。若随后把出处送给云服务，也可能再次发送不属于新请求授权章节的旧材料。

项目已有审计后缀保存在 `source` 中。直接删掉会破坏追溯，仓促增加数据库字段又需要同步迁移、历史、快照与归档。因此当前采用兼容的读取投影：`src/shared/knowledge-source.ts` 只识别末尾完整的审核结构，分出可读出处和审计记录。普通文本、无效 JSON 或未知结构都原样保留，不能仅凭字符串包含“AI 审核来源”就裁切作者文字。

界面出处、全文索引、AI参考和TXT/DOCX使用可读部分；知识卡片提供折叠的只读“AI审核记录”，查看原候选与授权章段。手工编辑时用 `replaceKnowledgeSource` 替换可读出处并拼回原审计，不重写证据。历史、快照与归档仍保存原始来源。

旧版搜索索引也必须处理，改显示函数不会让已经落库的索引自动更新。`assets-search.ts` 在首次查询中识别真正的旧审计索引，并在事务内刷新这些派生记录；第二次查询不再写入。原知识、历史、作品版本都保持原值。索引是可重建投影，不是作者的原始作品。

跟做：运行 `knowledge-source.test.ts`、`assets-search.test.ts` 和 `ai-reference.test.ts`。使用只存在于审计摘录的独有词搜索，知识摘要不应被误命中；检查后续AI参考不含该摘录。再将出处改为空，核对原审计仍可从折叠记录查看。

练习：为何不能从知识出处 JSON 中自动扩大本次模型上下文？答案：那是历史授权的材料，当前授权不能被旧记录代替。重新发送仍要按本次范围与完整预览决定。
