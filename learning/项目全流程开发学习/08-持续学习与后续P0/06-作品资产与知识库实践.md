# 作品资产与知识库实践

本章继续“雨落之后”的例子：作者准备描写一场雨，在知识库找到参考句，为人物留下“旧钥匙”伏笔，再把这些素材挂到剧情节点与正文段落。你将看到知识、剧情和伏笔如何共用一部作品的身份，又如何保留各自的职责。

**本章状态（2026-10-09）：**本地知识条目、层级分类、标签、剧情树、伏笔证据、写作特点和行内书签已实现并接入客户端。相关数据库与组件测试通过；真实 Electron 已验证知识新增/搜索、剧情关联、伏笔证据、书签详情与恢复后关系。完整 P0 最终交付门禁仍在进行；AI 接线和验证边界见本卷第十章，本章讲解手工操作。

## 1. 本章目标与前置知识

读完本章，应能区分“引用一条知识”和“从其他作品复制一条知识”；能沿界面、IPC、Worker 和 SQLite 追踪一次入库；能解释为什么删除一个段落不能悄悄把证据移到下一段。

先读第四卷的稳定段落 ID、第六卷的作品数据库隔离。还需知道外键负责对象存在，业务规则负责对象是否适合当前操作。分类成环和剧情树层级错误，不能只靠外键解决。

## 技术基础：关系建模、中文检索与证据来源

### 多对多为何需要中间表

一条知识能有多个标签，一个标签也能属于多条知识，这叫多对多。若把标签名直接拼成逗号字符串，改名、删除和精确筛选都容易出错。`knowledge_tag` 以 entry_id 和 tag_id 保存关系，标签名仅在 `tag` 表维护。

AND 筛选逐个要求标签关系存在：选“雨夜”和“紧张”，知识须同时有关联。正文段落没有知识标签，全文搜索中的标签条件只筛知识结果，不凭空给小说段落套知识标签。

### FTS5 trigram 与子串回退

三元切词把连续三个字符组成索引片段。例如“雨夜车站”产生“雨夜车”和“夜车站”。单字“雨”无法组成三元片段，所以当前 `searchAssets` 对一两字直接用 `instr(normalized_text, query)>0`；长度至少三的查询先用 FTS 缩小候选，再用同一子串条件确认。

这是一种不区分大小写、NFC 归一化的子串搜索。它支持中文短词，但不是编辑距离纠错：输入错字不会保证找到正确词。需求中的“模糊”必须解释当前精确行为，不把关键词检索吹成语义理解。

`search_document` 是可重建投影，正文和知识是权威来源。保存正文、知识、标签以及快照恢复时，都要使投影与当前稿一致。

### 原来源和当前位置

伏笔证据的 `originalSource` 保存创建时章名、摘录和版本，当前 chapterId/paragraphId 用于定位。重新关联产生新记录，并用 supersedesId 连接原记录，而不是擦掉旧出处。

知识 origin 保存跨作品复制来源。它只说明这条素材从哪里来，不让原作品修改自动改变副本；同作品书签则按 targetId 解析当前条目。两种关系的更新规则不同，不能共用“复制引用”的含糊语义。

下面按卡片、查询和证据三条链分别跟做。每次都观察稳定 ID 与版本，再对照界面文案。

## 2. 先把写作动作翻译成数据

知识条目保存内容、出处、一个主分类和多个标签。分类是树，标签是独立字典；“人物描写”属于分类，“紧张”“夜雨”属于标签。多个标签按 AND 筛选，意味着条目必须同时具有所有选中标签。

| 作者操作 | 数据对象 | 对应关系 |
| --- | --- | --- |
| 新添一段雨景参考 | `knowledge_entry` | 关联 `category`，多标签通过 `knowledge_tag` |
| 创建一章剧情计划 | `outline_node` | 卷、章、详细节点组成树，可关联正文章节 |
| 记录旧钥匙伏笔 | `foreshadow` | 保存五状态，可挂到剧情节点 |
| 标记埋设位置 | `evidence` | 保存章节、段落 ID、摘录与原始来源 |
| 固定叙述节奏 | `style_profile` | 发布新版本，作品默认与章节覆盖引用具体版本 |

实际建表语句在 `src/workers/database/assets-schema.ts`。每部作品拥有这些表；复制引用知识时，目标作品获得新的条目 ID，同时保留 `origin_json` 中的原作品、原条目和来源版本。

## 3. 实践：从卡片到 SQLite

`src/renderer/components/knowledge-workspace.tsx` 管理卡片展开与筛选；`knowledge-dictionary.tsx` 管理分类和标签维护。卡片只展示两行摘要与右下角出处，点击原位展开，数据模型仍保存完整正文。

![真实客户端中的知识卡片与中文短词搜索](images/knowledge.png)

图中搜索“雨”，卡片来自“景物描写”，出处为自写练习句。截图来自隔离测试作品，不包含作者未发表内容。

一次保存的数据流如下：

```text
卡片编辑表单 → App.manageAsset
→ preload.manageAssets → 主进程白名单
→ StoreService → database worker
→ WorkRepository.manageAssets
→ applyAsset → applyKnowledgeAsset
→ 同事务保存条目、历史、检索索引与作品revision
→ WorkDetail回执 → 界面替换已确认状态
```

命令在 `src/shared/assets-schema.ts` 严格校验。例如创建知识只允许这几个字段：

```typescript
{
  type: 'createKnowledge',
  body: '雨滴敲在窗沿，像逐渐密集的鼓点。',
  source: '自写练习句',
  categoryId, // 当前作品中的景物描写分类
  tagIds,    // 当前作品中的夜雨、紧张标签
}
```

Repository 还包装 `workId`、`expectedRevision` 和 `operationId`。作品版本变化要重新读取；回执未知时用同一操作 ID 重试，避免重复创建卡片。不能因为 React 输入框显示新内容，就认定数据库已经保存成功。

## 4. 中文短词搜索为何分两条路

`src/workers/database/assets-search.ts` 为正文段落和知识建立统一检索数据，来源类型随结果返回。SQLite FTS5 trigram 适合较长片段；中文只有一两个字时不能完全依靠三元切词，因此实现保留短词回退查询。

查“雨”应能返回包含雨景的知识与正文段落，查“夜雨”也不应因不足三个字符而失去结果。搜索框只提供查询能力，不创建分类。页面新增字典与模糊查找分别对应不同动作，不能复用一个含义含糊的输入框。

P95≤1秒是常规本地数据基线。说明算法正确与证明性能达标是两个检查步骤，具体数据集、查询集合和机器必须记录，不能在没有计时证据时承诺无限规模同样快。

## 5. 正文书签与证据的联系

书签是受限文档中的行内节点，显示标记、不计正文文字：

![剧情节点关联正文章节](images/plot.png)

剧情节点“车站发现旧钥匙”关联正文第一章，计划与正文保持独立对象。

![伏笔状态、剧情归属与段落证据](images/foreshadow.png)

伏笔记录“已埋设”状态，原出处保存章节、版本与段落 ID。选择状态与添加证据是两次明确操作。

```typescript
{
  type: 'bookmark',
  attrs: { id: bookmarkId, kind: 'foreshadow', targetId: foreshadowId },
}
```

知识书签把 `kind` 改为 `knowledge`。稳定 `targetId` 允许条目修改后显示新内容，软删除后仍可说明原对象。正文段落 ID 与证据的 `paragraph_id` 形成联系；`original_source` 保留最初摘录，不随重新关联静默重写。

读 `assets-evidence.ts` 中的 `readEvidence`：章节删除或段落 ID 不再存在时，证据变成失效状态，历史仍在。重新关联产生一条新证据，通过 `supersedes_id` 连到旧记录。证据说明出处，不证明 AI 建议必然正确。

## 6. 跟做：写作素材到正文

1. 在测试作品创建“景物描写”的雨景条目，注明“自写练习”，加入两个不同标签。
2. 用一个标签筛选，再同时勾选两个标签，核对 AND 规则；清空筛选后应显示全部。
3. 在剧情架构创建章节点，关联正文第一章；添加详细节点说明“人物发现旧钥匙”。
4. 创建“旧钥匙”伏笔，在正文指定段落插入书签，点击标记查看详情。
5. 为伏笔增加埋设证据；修改这段正文，再删除来源章节，查看证据失效提示。
6. 在设置恢复章节，核对恢复的是原对象，原段落 ID 没有换成临时新 ID。
7. 切换到全局知识汇总，确认其他作品条目只读；复用时选择复制，原作品保持不变。

跟做只在测试作品进行。书签、关联和条目操作失败时，保留输入供作者重试；未提交草稿不能在切换工作区时丢失。

## 8. 练习与检查点

练习一：给“雨景”同时标记“紧张”和“夜雨”，只选择“夜雨”时是否必须具有“紧张”？答案：不必，AND只作用于当前选中的标签集合。

练习二：为什么跨作品复用不直接保留同一个实时知识对象？答案：一部作品的恢复、删除或修改不应影响另一部作品；复制并保留来源满足隔离和追溯。

练习三：设计一条测试，证明删除证据来源不会删除伏笔。

参考步骤：先创建伏笔和埋设证据，记录原 ID、摘录和 revision；删除来源章，读 `readEvidence`，断言伏笔仍存在、证据 valid=false、invalidReason 说明章不存在、originalSource.excerpt 不变。再恢复章，核对原段落 ID；不要按相似文本新建一条假证据。

拓展：搜索“雨夜”与拼错的“雨页”，解释为何前者有命中而后者未必。答案：当前是归一化子串与 FTS 辅助，不是错字容错或向量相似；后续进阶需真实查询证据和新的验收定义。

检查点：你能画出一次知识保存的数据流，解释知识引用与证据锚点各自连接什么对象，并说明 AI 功能还需在哪些位置增加授权与审核。

## 9. 实践补充：跨作品字典映射与草稿保护

### 先理解：同名对象为什么不是同一个对象

作品甲和乙都可能有“夜雨”标签，但它们拥有不同 SQLite 数据库和标签 ID。名字描述含义，ID 表示身份。复制甲的知识时，直接把甲的标签 ID 写到乙，目标库会找不到对象；把标签全部清空虽然不越界，却丢失了可复用的分类信息。

因此复制需要一次映射：展示源内容和出处，让作者选择乙的主分类；按名称匹配乙已有标签，再让作者调整选择。没有匹配的标签明确提示，不隐式创建。副本获得新知识 ID，origin 保存甲的作品、条目和版本。甲随后修改内容，乙不会自动改变。

```text
源标签：{ id: A1, name: 夜雨 }
目标标签：{ id: B7, name: 夜雨 }
复制后关系：新知识 → B7；origin → 源作品 / 原知识 / 原版本
```

### 再追踪项目中的实现

`knowledge-copy-dialog.tsx` 的 `prepareKnowledgeCopy` 读取源专属字典，对名字做 NFC 归一化和大小写比较；`KnowledgeCopyDialog` 展示完整内容、出处、来源分类、匹配与未匹配标签。来源字典通过 `readKnowledgeScope` 读取，不能为预览而打开来源作品：打开作品会改变当前写入身份。

![真实离线窗口中的知识复制预览与目标字典映射](images/knowledge-copy.png)

图中“仅在来源”未匹配，目标已有“雨夜”和“写作参考”可明确选择。截图使用临时作品和作者自写练习句，不读取真实作者素材。

App 保留目标作品与来源版本，确认后走既有知识复制命令。数据库仍校验当前目标分类、标签和来源版本，界面预览不替代事务校验。取消不写数据；普通失败保留选择；回执未知时按原操作 ID 重试，而不是再次产生副本。

### 草稿与已保存状态是两份数据

分类编辑表单是草稿，SQLite 是已提交状态。只要两者不同，就不能通过“编辑另一分类”把当前输入替换掉。`knowledge-dictionary.tsx` 分开计算 `hasDraftChanges` 与运行中的 `busyAction`：前者锁定其他编辑、删除和排序入口，后者暂时锁定请求；当前草稿的保存和取消只受请求状态约束。

如果把保存也按 dirty 禁用，作者就无法结束草稿。这是一个典型状态机错误。保存失败后保留草稿与受阻说明，允许重试；取消明确丢弃本次表单输入并解除保护。

### 跟做、排错与练习

1. 创建甲乙两部测试作品，分别建同名“夜雨”标签，乙再建“紧张”标签。
2. 甲新增雨景知识，乙打开全局知识汇总；复制预览核对源标签与目标已有标签。
3. 选择乙的“景物描写”，保留夜雨并追加紧张；先取消，确认乙没有副本，再操作一次并确认。
4. 查看副本出处与来源；修改副本后检查甲保持原样。
5. 设置中编辑分类并输入新名称，检查其他分类编辑和删除禁用；保存失败仍保留输入，取消后恢复可操作。

练习：甲有“旧车站”标签，乙没有，复制时应直接新建吗？答案：不应。预览显示未匹配，作者可先到设置维护目标字典后重新复制，避免把来源字典无意扩散到另一作品。

练习：为何来源版本变化需要重新预览？答案：此前看到的内容不再对应将要复制的版本，必须重新核对；失败提示与目标事务校验共同保护这个边界。

### 多段书签的坐标

Tiptap 选区的 anchor/head 表示拖动方向，from/to 始终按文档顺序排列。`inline-bookmark.tsx` 比较 `$from.sameParent($to)`：同段在 to 插入，跨段在 from 插入；先折叠选区再插入，所以不会替换选中文字。

在两段正文中分别从上往下和从下往上选择，再插入伏笔书签。两次标记都应属于文档顺序首段，原文、段落 ID 和统计字数不变。标记只建立关联，不会自动生成“已埋设”的证据。
