# 作品资产与知识库实践

本章继续“雨落之后”的例子：作者准备描写一场雨，在知识库找到参考句，为人物留下“旧钥匙”伏笔，再把这些素材挂到剧情节点与正文段落。你将看到知识、剧情和伏笔如何共用一部作品的身份，又如何保留各自的职责。

**本章状态（2026-10-09）：**本地知识条目、层级分类、标签、剧情树、伏笔证据、写作特点和行内书签已实现并接入客户端。相关数据库与组件测试通过；真实 Electron 已验证知识新增/搜索、剧情关联、伏笔证据、书签详情与恢复后关系。完整 P0 最终交付门禁仍在进行；AI 接线和验证边界见本卷第十章，本章讲解手工操作。

## 1. 本章目标与前置知识

读完本章，应能区分“引用一条知识”和“从其他作品复制一条知识”；能沿界面、IPC、Worker 和 SQLite 追踪一次入库；能解释为什么删除一个段落不能悄悄把证据移到下一段。

先读第四卷的稳定段落 ID、第六卷的作品数据库隔离。还需知道外键负责对象存在，业务规则负责对象是否适合当前操作。分类成环和剧情树层级错误，不能只靠外键解决。

## 2. 先把写作动作翻译成数据

知识条目保存内容、出处、一个主分类和多个标签。分类是树，标签是独立字典；“人物描写”属于分类，“紧张”“夜雨”属于标签。多个标签按 AND 筛选，意味着条目必须同时具有所有选中标签。

| 作者操作 | 数据对象 | 对应关系 |
| --- | --- | --- |
| 新添一段雨景参考 | `knowledge_entry` | 关联 `category`，多标签通过 `knowledge_tag` |
| 创建一章剧情计划 | `outline_node` | 卷、章、详细节点组成树，可关联正文章节 |
| 记录旧钥匙伏笔 | `foreshadow` | 保存五状态，可挂到剧情节点 |
| 标记埋设位置 | `evidence` | 保存章节、段落 ID、摘录与原始来源 |
| 固定叙述节奏 | `style_profile` | 发布新版本，作品默认与章节覆盖引用具体版本 |

实际建表语句在 `src/workers/database/assets-schema.ts`。每部作品拥有这些表；复制引用知识时，目标作品获得新的条目 ID，同时保留 `origin_json` 中的原作品、原条目和来源版本。

## 3. 实践：从卡片到 SQLite

`src/renderer/components/knowledge-workspace.tsx` 管理卡片展开与筛选；`knowledge-dictionary.tsx` 管理分类和标签维护。卡片只展示两行摘要与右下角出处，点击原位展开，数据模型仍保存完整正文。

![真实客户端中的知识卡片与中文短词搜索](images/knowledge.png)

图中搜索“雨”，卡片来自“景物描写”，出处为自写练习句。截图来自隔离测试作品，不包含作者未发表内容。

一次保存的数据流如下：

```text
卡片编辑表单 → App.manageAsset
→ preload.manageAssets → 主进程白名单
→ StoreService → database worker
→ WorkRepository.manageAssets
→ applyAsset → applyKnowledgeAsset
→ 同事务保存条目、历史、检索索引与作品revision
→ WorkDetail回执 → 界面替换已确认状态
```

命令在 `src/shared/assets-schema.ts` 严格校验。例如创建知识只允许这几个字段：

```typescript
{
  type: 'createKnowledge',
  body: '雨滴敲在窗沿，像逐渐密集的鼓点。',
  source: '自写练习句',
  categoryId, // 当前作品中的景物描写分类
  tagIds,    // 当前作品中的夜雨、紧张标签
}
```

Repository 还包装 `workId`、`expectedRevision` 和 `operationId`。作品版本变化要重新读取；回执未知时用同一操作 ID 重试，避免重复创建卡片。不能因为 React 输入框显示新内容，就认定数据库已经保存成功。

## 4. 中文短词搜索为何分两条路

`src/workers/database/assets-search.ts` 为正文段落和知识建立统一检索数据，来源类型随结果返回。SQLite FTS5 trigram 适合较长片段；中文只有一两个字时不能完全依靠三元切词，因此实现保留短词回退查询。

查“雨”应能返回包含雨景的知识与正文段落，查“夜雨”也不应因不足三个字符而失去结果。搜索框只提供查询能力，不创建分类。页面新增字典与模糊查找分别对应不同动作，不能复用一个含义含糊的输入框。

P95≤1秒是常规本地数据基线。说明算法正确与证明性能达标是两个检查步骤，具体数据集、查询集合和机器必须记录，不能在没有计时证据时承诺无限规模同样快。

## 5. 正文书签与证据的联系

书签是受限文档中的行内节点，显示标记、不计正文文字：

![剧情节点关联正文章节](images/plot.png)

剧情节点“车站发现旧钥匙”关联正文第一章，计划与正文保持独立对象。

![伏笔状态、剧情归属与段落证据](images/foreshadow.png)

伏笔记录“已埋设”状态，原出处保存章节、版本与段落 ID。选择状态与添加证据是两次明确操作。

```typescript
{
  type: 'bookmark',
  attrs: { id: bookmarkId, kind: 'foreshadow', targetId: foreshadowId },
}
```

知识书签把 `kind` 改为 `knowledge`。稳定 `targetId` 允许条目修改后显示新内容，软删除后仍可说明原对象。正文段落 ID 与证据的 `paragraph_id` 形成联系；`original_source` 保留最初摘录，不随重新关联静默重写。

读 `assets-evidence.ts` 中的 `readEvidence`：章节删除或段落 ID 不再存在时，证据变成失效状态，历史仍在。重新关联产生一条新证据，通过 `supersedes_id` 连到旧记录。证据说明出处，不证明 AI 建议必然正确。

## 6. 跟做：写作素材到正文

1. 在测试作品创建“景物描写”的雨景条目，注明“自写练习”，加入两个不同标签。
2. 用一个标签筛选，再同时勾选两个标签，核对 AND 规则；清空筛选后应显示全部。
3. 在剧情架构创建章节点，关联正文第一章；添加详细节点说明“人物发现旧钥匙”。
4. 创建“旧钥匙”伏笔，在正文指定段落插入书签，点击标记查看详情。
5. 为伏笔增加埋设证据；修改这段正文，再删除来源章节，查看证据失效提示。
6. 在设置恢复章节，核对恢复的是原对象，原段落 ID 没有换成临时新 ID。
7. 切换到全局知识汇总，确认其他作品条目只读；复用时选择复制，原作品保持不变。

跟做只在测试作品进行。书签、关联和条目操作失败时，保留输入供作者重试；未提交草稿不能在切换工作区时丢失。

## 7. 根因排查与验证证据

| 问题 | 根因方向 | 回归验证 |
| --- | --- | --- |
| 中文短词搜不到 | 只使用 trigram FTS | 搜“雨”和两字词 |
| 其他作品内容被改 | 全局页面错误提供直接编辑 | 汇总只读、复制生成新对象 |
| 删除段落后证据跑到其他段 | 通过段落序号定位 | 稳定 ID 与失效状态 |
| 分类删除留下孤儿条目 | 删除前未迁移 | 要求迁移到其他分类/未分类 |
| 自动保存被手工资产覆盖 | 两种命令使用过期revision | 冲突后重新读取与幂等重试 |

## 8. 练习与检查点

练习一：给“雨景”同时标记“紧张”和“夜雨”，只选择“夜雨”时是否必须具有“紧张”？答案：不必，AND只作用于当前选中的标签集合。

练习二：为什么跨作品复用不直接保留同一个实时知识对象？答案：一部作品的恢复、删除或修改不应影响另一部作品；复制并保留来源满足隔离和追溯。

练习三：设计一条测试，证明删除证据来源不会删除伏笔。提示：比较 `foreshadow` 行数量与 `readEvidence` 的失效原因，原始摘录必须仍可读。

检查点：你能画出一次知识保存的数据流，解释知识引用与证据锚点各自连接什么对象，并说明 AI 功能还需在哪些位置增加授权与审核。
