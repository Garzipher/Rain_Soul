# 真实客户端验收与窄窗排错

单元测试可以证明“快照恢复是事务”，却不能证明作者在真实客户端里找得到恢复按钮。本章用“雨落之后”贯穿知识、剧情、伏笔、导入导出和 AI 授权，再讲一次自动化断言漏掉视觉问题的排错过程。

**本章状态（2026-10-09）：**前三条真实 Electron 业务流程已通过：作品资产与完整关系归档、手稿导入导出、AI 设置与授权预览取消。最小窗口回归先复现展开侧栏导致主区域宽度仅60px的缺陷，修复后复验通过，主区域恢复468px。最终整套交付门禁由完整测试与构建决定。本章没有向真实 AI 服务发送正文。

## 1. 为什么不能只测试网页 Demo

Demo 的内存数据与正式客户端的 SQLite 不同。正式测试启动 Electron 的 `dist/desktop/main.cjs`，通过 preload 和 IPC 调用主进程、Worker 与本地数据库，还要确认关闭门禁与重启后数据保持。

`tests/desktop/structure-helper.cjs` 用 `RAINSOUL_TEST_DIRECTORY` 隔离作品与 Electron 档案。每次只清理自己创建的 PID 与临时目录，不能结束作者已打开的客户端，也不能修改真实作品。

原生文件对话框允许用替身返回测试文件路径；这只是避免自动化等待系统窗口。TXT/DOCX解析、ZIP、数据库导入导出和 UI 仍走真实生产代码。

## 2. 把验收写成作者动作

`tests/desktop/p0-workflow.spec.cjs` 包含四条流程：

| 流程 | 关键动作 | 必须比较的结果 |
| --- | --- | --- |
| 作品资产 | 知识、剧情、伏笔证据、行内书签、快照恢复、归档往返 | 稳定对象关系、全文、资产和历史保持 |
| 文件往返 | TXT/DOCX预览导入、两种导出、归档新作品导入、重启 | 原文件与原作品保留，新作品独立出现 |
| AI 授权 | 临时模型配置、匹配知识勾选、完整预览、取消 | Key不回显，正文不变，快照不增加 |
| 最小窗口 | 720×540原生窗、侧栏收起/展开、5标签和AI面板 | 主区域宽度、控件边界、底部可滚动触达 |

第一条不能只断言“出现成功提示”。它比较恢复前后结构化正文、知识、伏笔、证据段落 ID，以及归档副本的完整 `assets`。第二条重启之后再次核对书架，避免把 React 内存状态误认成落盘成功。

AI 测试只准备预览，不点击确认发送。服务名称、模型与费用说明采用测试值；没有真实费用，也不替作者授权。网络发送和故障由独立单元测试替身验证。

## 3. 第一次测试为什么漏掉了布局问题

原生窗口720×540时，Windows边框与标题栏使网页实际尺寸为704×501。测试先记录控件的 `getBoundingClientRect()`，检查右边界不超过网页宽度，并确认 AI 请求按钮能滚动进入视口。

第一次四条测试全绿，但人工看展开侧栏截图发现：备份按钮只有41px宽、88px高，文字竖排；五个标签挤在左侧，主内容落在侧栏下方。

为什么断言没有发现？这些控件仍在网页边界内，仍能通过键盘激活；“没有超出窗口”不等于“布局合理”。测试必须增加主区域宽度断言，不能仅重复实现细节。

```javascript
const main = document.querySelector('main').getBoundingClientRect();
expect(main.width).toBeGreaterThanOrEqual(window.innerWidth - 236);
```

236px来自当前展开侧栏宽度。修复后的窄窗布局采用236px侧栏加剩余主区域；测试允许响应布局换行，却拒绝主内容缩进60px导航列。

## 4. 追到CSS Grid根因

页面布局定义两列：60px导航栏和剩余主内容。窄窗展开侧栏时，`.rail` 使用 `position: fixed` 变成浮层，脱离正常网格排布。

如果主区域只依赖自动排位，原先第二个网格子元素就会变成第一个参与排布的元素，从第二列掉进第一列。问题不是按钮字号太大，不能逐个缩小按钮掩盖根因。

修复明确主区域始终处于第二列，固定侧栏不再改变其网格身份。窄窗展开时保留236px导航列，工具栏允许换行；AI面板自身提供滚动。实现位置是 `src/renderer/styles.css`，核心样式节选如下：

```css
.main { grid-column: 2; min-width: 0; min-height: 0; }
.header-actions { display: flex; flex-wrap: wrap; }
.architecture-placeholder { min-width: 0; min-height: 0; overflow: auto; }
```

`min-height: 0`允许Flex子区域缩到可用高度，`overflow: auto`让底部操作继续可达。修复之后，重新验证收起和展开；不能只检查一个截图。

## 5. Red、修复与Green的证据

强化后的回归在旧构建上失败：实际主区域宽度60px，要求至少468px。Red证据来自真实窗口，表明新断言确实覆盖缺陷。

```powershell
npx playwright test --config playwright.desktop.config.cjs tests/desktop/p0-workflow.spec.cjs --grep "最小窗口"
```

测试把实际viewport、主区域与9个控件边界写入 `geometry-expanded.json` 和 `geometry-collapsed.json`，并保存两张截图。产物在 `test-results-desktop` 对应流程目录；每次重跑会更新，因此教材保留排错过程，发布时另保存需要长期保留的截图。

修复后还需生产构建与整套桌面流程通过。测试本身全绿之后，要再看截图，核对标题、文字方向、层级与操作区是否符合作者使用习惯。

真实复验中，展开侧栏主区域从60px恢复到468px；备份按钮恢复80×37px，DOCX导出按钮约92.86×37px。五个标签横排并保持在窗口边界内，AI请求按钮可滚动进入视口。窄窗回归复验用时10.6秒，截图人工核对与几何数据结论一致。

## 6. 跟做与练习

1. 构建正式客户端，在隔离目录运行四条流程。
2. 读取两份几何JSON，解释720×540与704×501为何不同。
3. 对照展开侧栏截图与主区域宽度，不用“按钮存在”代替可用性。
4. 临时在独立测试分支移除明确网格列位，确认回归重新失败；完成练习后恢复修复。
5. 增加一项“返回作品集可触达”的检查，同时保留截图人工审查。

练习一：为什么 `right <= width` 无法发现60px主区域？答案：内容可以挤在很小区域内，仍然不越界。

练习二：为什么重启后的断言比只读当前界面重要？答案：重启消除内存状态，只能从已提交磁盘数据恢复。

检查点：你能从作者流程选择测试边界，解释替身覆盖哪些部分，并用具体失败证据证明回归确实发现原问题。
