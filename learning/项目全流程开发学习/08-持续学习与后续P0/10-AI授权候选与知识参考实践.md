# AI 授权、候选与知识参考实践

作者希望 AI 改善雨景描写，同时参考作品知识库和“旧钥匙”伏笔。一个可信的写作助手不能直接改掉原文，也不能把所有作品悄悄发送出去。本章把“请求预览、明确授权、候选审核、版本保护”串成一条可追踪的数据流。

**本章状态（2026-10-09）：**云端适配、上下文构建、授权预览、候选正文写入、逐条知识审核、作品资料检索与主界面已接线；实现采用测试替身验证网络与故障。当前未使用作者 API Key，也未向真实云服务发送正文。真实云端服务的响应质量、账单和兼容性，需要作者之后针对自己选择的服务验证。

本卷第二、三章讲基础对象与 HTTP/token，本章沿真实实现追踪逐次授权与候选写入。包内只读教材可修订，已经安装的作者正文不会被静默覆盖。

## 技术基础：授权冻结、提示注入与乐观并发

### 授权是一份固定请求的批准

“同意使用 AI”不能代替“同意把这些正文发给这个服务”。系统先构建最终内容、服务和模型，计算 requestHash，再生成有期限的一次性 confirmationToken。确认时验证哈希、期限和配置，确保发送的仍是作者看到的请求。

token 是授权实例的身份，hash 是内容与发送条件的绑定，operationId 是候选入库幂等身份。三者不能混成一个“请求编号”。配置变化或过期，需要重新预览；网络失败不自动重发可能再次计费的操作。

### 模型材料不能越权变成指令

知识卡片、正文和参考作品可能含“忽略此前规则”等文字，这类内容叫提示注入风险。系统提示要求把它们视为材料，但单靠文本约束不能彻底保证模型服从。真正写正文、读取凭据和发送范围仍由程序边界控制。

模型输出是候选，不是可执行代码。没有作者确认，不能改稿、自动入库或生成事实证据。对于一致性建议，程序只验证章段存在与摘录匹配，文学判断仍标为建议和不确定性。

### 候选写入为什么再次核对版本

生成期间作者可能继续写。候选携带 baselineRevision 与稳定段落目标；入库时若当前版本不一致，需要重新生成或重新比较。安全快照、正文替换、revision 与回执在同一事务，避免“旧候选覆盖新稿”或“改完才保护”。

单句还需验证原句和段内起止位置；段落替换需核对连续目标。知识/伏笔书签的迁移规则要提前说明，不把引用关系悄悄丢掉。

下面按准备、发送、候选和确认四个阶段阅读。每一步要说明会否联网、会否修改作者数据。

## 1. 分清离线底座与云端能力

作品、知识、搜索、保存、快照、归档和 TXT/DOCX 导出在本机运行。AI 使用作者配置的 HTTPS 云服务，当前提供兼容 `chat/completions` 的适配层；不能据此宣称所有厂商私有 API 都能直接接入。

首版操作包含单句润色、段落润色、续写、纠错、一致性检查、剧情感受和正文回写知识。一致性和剧情感受只展示建议，正文替换由作者显式确认。自动拆书、需求会话、向量检索与本地模型仍是后续功能。

Python/FastAPI 是独立学习验证路径，当前 Windows 客户端不要求安装 Python，也不依赖额外服务才能写作。

## 2. 上下文与目标位置不是同一回事

上下文回答“AI 可以参考哪些内容”；目标段落回答“哪一段允许被候选替换”。例如参考全卷，但只润色第一章第二段，不能把整卷文本当作替换目标。

`src/shared/ai-context.ts` 提供当前章节、前章衔接、全卷、自定义章节范围。目标记录稳定段落 ID；单句润色还记录段内起止位置和原句文本。明确提供 `sentenceFrom` 时按该位置核对精确切片，重复句也可准确定位；未提供偏移时才要求原句在段落中唯一匹配，避免误改另一个同样句子。

```typescript
{
  chapterId,
  scope: 'chapter',
  targetParagraphIds: [paragraphId],
  sentenceText: '雨落在旧车站。',
}
```

这是“准备请求”的参数节选，还需要作品 ID 和操作类型。调用准备不会进行网络发送。

## 3. 知识库如何进入 AI 参考

`src/shared/ai-reference.ts` 从已选正文范围取得对应写作特点、大纲和伏笔，并推荐本作品最多五条关键词匹配知识。作者展开“知识参考 · 作者选用”，逐条勾选后，选用条目才进入发送预览。当前实现使用本作品关键词与关联信息，不是向量检索，也不访问其他作品的全部正文。

知识来源帮助作者学习和仿写，不能保证模型一定正确使用素材。角色名、原句摘录与出处是审查依据。当前版本化写作特点优先使用章节覆盖，否则使用作品默认版本。

知识存在于请求中不意味着它可以指挥助手。系统要求把正文与素材视为待分析材料，不能接受参考文本中“忽略之前规则”等指令。模型输出仍需由作者检查，不能把这条提示当成防注入的绝对保证。

## 4. 准备、确认与发送

![真实客户端的云端授权预览，使用隔离测试资料且未确认发送](images/ai-authorization-preview.png)

截图来自真实 Electron 窗口：它展示操作要求、目标、授权上下文、服务与计费说明。测试使用虚构配置，仅点击取消，取消前后的作品、版本和快照完全一致。这张图证明预览与取消流程，不表示真实模型已经返回内容。

```text
写作选区右键或右上角“AI 工具”选择操作/范围/目标
→ App 保存当前稿 → prepareAi
→ AiCommands 冻结作品，构造上下文与参考
→ AiService.prepare 冻结 endpoint 和请求内容
→ 界面显示服务、模型、全部内容及计费提示
→ 作者确认 → executeAi
→ 验证 token、hash、期限和服务配置
→ 主进程读取凭据，发送一次请求
→ 候选返回，原稿保持到作者确认写入
```

服务中保存 `confirmationToken` 与 `requestHash`，授权默认五分钟有效并且只能使用一次。配置变化、取消或过期，都需要重新预览。不能把“此前确认过一次”解释为永远允许发送未发表正文。

token 估算是保守容量提示，不等于厂商精确 tokenizer 或报价。无法估价时显示计费说明。超长范围提示缩小或分块，不能悄悄截断后声称看过整卷。

## 5. 凭据与网络边界

凭据仅由主进程通过 Windows 安全存储加密；作品 DB、归档、日志和错误提示不带 API Key。配置文件可保存服务名称和模型，不保存明文凭据供 React 读取。

`src/main/ai-service.ts` 检查服务地址为 HTTPS 公开地址，拒绝本机/私网与重定向；发送时验证 DNS 结果并固定已检查的 IP，TLS 仍验证服务域名。这样避免配置地址在解析后转向本机服务。

超时、断网、认证失败或额度不足，只给原因，作者手动重新预览重试。自动重发既可能重复计费，也可能发送作者尚未重新授权的内容。错误文本需保持可读，并避免暴露凭据。

## 6. 候选确认与来源保护

候选含作品 ID、基线 revision、目标段落 ID 与生成时间。正文变化后，旧候选不能无条件写入；要重新生成或重新对比。

正文确认写入前创建保护快照，然后在同一事务内修改目标与版本。测试应让快照或正文写入故障，验证全部回滚。不是先改正文再补一条历史记录。

正文回写知识先形成候选，作者逐条检查、编辑并勾选审核。修改候选内容后需要重新勾选。入库保存当前作品与正文来源；分析建议没有“直接替换正文”按钮。

一致性与剧情感受使用 `src/shared/ai-analysis.ts` 解析结构化建议。建议保留原因、不确定性与摘录；只有章节属于实际授权范围、段落仍存在、摘录匹配且基线未过期，才提供“定位正文证据”。位置验证通过不代表文学判断正确。模型格式非法时降级保留原始文字，不能把无法验证的摘录标成事实。

## 7. 跟做：先验授权，不产生真实费用

## 8. 练习与检查点

练习一：当前章作为目标、全卷作为上下文时，哪个范围决定替换位置？答案：目标段落 ID；上下文只决定参考内容。

练习二：作者更换服务后，为何旧授权失效？答案：此前批准的发送目标不同，继续发送会违反这次授权的范围。

练习三：给测试替身返回一个认证错误。

参考步骤：准备并确认一次请求，令受控网络依赖返回 401；断言调用次数为 1、错误提示不含 Key、当前文档和快照数量不变。作者手动重试须重新预览，不能复用已消费的 token。这里证明错误处理与授权次数，不证明厂商真实 401 格式兼容。

检查点：你能从准备请求一路追到候选写入，说明哪一步会联网、哪一步会修改正文，并区分“程序行为已验证”和“真实模型质量已验证”。

## 9. 实践补充：准确的目标与完整的剧情参考

### 先理解结构化正文如何转为模型输入

正文不是一个字符串，而是段落及行内节点组成的文档。`text` 保存文字，`hardBreak` 保存段内换行，`bookmark` 只保存关联身份。转为 AI 目标时，前两种分别映射为原文字和换行，书签不冒充正文。

```text
text("第一行") + hardBreak + text("第二行")
→ 第一行\n第二行
```

如果过滤掉除 text 外的所有节点，换行就丢失了。单句偏移也可能与界面中的原文不一致。`ai-context.ts` 现在对目标正文和授权上下文都保留硬换行；选区定位仍按原稿校验，不能在模型返回后凭相似文字猜位置。

### 剧情树的范围不能只看直接章 ID

作者通常把计划写成“卷→章→详细场景”。正文关联在章节点，详细节点不一定有独立 chapterId。只筛 chapterId 相等的节点，会丢掉详细计划及其伏笔，剧情感受和一致性检查就少了作者最具体的意图。

`ai-reference.ts` 的 `scopeOutlines` 从授权章节直接关联的节点开始：向上补所属计划，向下补详细场景；遇明确关联其他未授权章节的节点时停止该分支。父级只用来补说明，不作为新的向下扩展起点，所以不会顺带加入同卷其他章的详细剧情。

```text
第一卷（补入总体计划）
├─ 第一章（已授权）→ 找到钥匙（补入详细计划及相关伏笔）
└─ 第二章（未授权）→ 钥匙开门（排除该章分支）
```

作者在发送预览看到完整材料后才能确认。父级总体计划可能描述整卷走向，它属于本章参考，但不意味着软件读取了未授权章节正文。删除节点不纳入现行参考；循环防护避免坏数据导致无限遍历。

### 展示标签与模型容量是两种限制

范围标签用于短摘要，正文材料用于真实请求。此前全卷很多章标题拼进标签，会超过 schema 的300字符限制，即使正文仅有几行也无法预览。这属于元数据限制，不能作为限制作者写作规模的理由。

现在短标题仍直接展示，长清单改成“全卷：共 N 章（章节清单见完整发送内容）”。完整章名、章节 ID 和段落仍在材料中；主进程追加知识参考说明后继续验证整体 schema、模型上下文与容量。摘要变短不会截断正文，也不会绕过模型容量门槛。

### 跟做与拓展练习

1. 在测试章输入两行文字，用段内换行连接；预览润色目标，核对两行仍分开，不发送真实请求。
2. 创建上图剧情树，只授权第一章；预览应含总体计划、找到钥匙与相关伏笔，不含第二章详细计划。
3. 运行 `ai-context.test.ts`、`ai-reference.test.ts` 和 `ai-commands.test.ts`，观察硬换行、树范围与50章短正文回归。
4. 故意增加正文直到超过测试模型容量，确认仍要求缩小范围，而不是因摘要短就继续发送。

练习：为何先补父级再从父级遍历整棵子树不合适？答案：父级还包含未授权章的分支，会扩大参考范围；向下扩展只能从原授权节点起步。

练习：模型已读到章 ID，却漏了某个详细计划，应先检查模型还是程序？答案：先看完整发送预览和 `buildAiReferences` 输出。程序没有发送的内容，不能用调整提示词代替修复数据准备。

## 10. HTTP 成功为什么不等于候选完整

### 先认识传输状态和生成状态

HTTP 200 表示服务成功处理了这次网络请求，但模型可能因输出额度不足而只写出半句话。`finish_reason` 记录生成如何结束；当前兼容协议中，`stop` 表示正常结束，`length` 表示到达输出上限，`content_filter` 表示内容被过滤。工具调用返回的是另一个处理步骤，也不能当作正文直接交给作者应用。

```json
{
  "choices": [{
    "finish_reason": "length",
    "message": { "content": "他推开门，发现房间里" }
  }]
}
```

这段响应有文字、有 JSON、HTTP 也可能为200；三个条件都无法证明它是完整改稿。若将它展示成可应用候选，作者可能用半句话替换一段完整原稿。

### 项目怎样拦住不完整结果

阅读 `src/main/ai-service.ts` 的 `send`：先检查网络状态、响应体容量与 JSON，再检查显式拒绝、结束原因、正文有效性及凭据回显，最后才构造候选。`AiCommands` 只登记成功返回的候选，因此失败结果没有可用于正文写入的候选身份。

首版明确拒绝截断、过滤、工具调用、未知结束状态和显式拒绝。某些兼容服务没有 `finish_reason`，当前保留兼容；这是一项适配取舍，不能保证该服务一定完整生成，也不能据此宣称支持所有厂商接口。采用这类服务时应在真实联调中额外核对其协议。

错误提示由本机程序生成，不照搬厂商返回字段，避免错误内容夹带 Key。失败不自动重发，已消费的授权也不能复用。作者缩小目标范围、检查模型配置后重新预览，才可能再次发送。

### 实验：验证失败没有留下可应用候选

```powershell
npx vitest run tests/unit/ai-service.test.ts --pool=threads --maxWorkers=1
```

先阅读测试中的 `setup`：网络由 `fetch` 替身提供，凭据也是测试字符串，不会访问作者密钥或向真实服务发请求。让替身依次返回 `stop`、`length`、`content_filter`、未知状态及拒绝字段，比较执行结果。每次失败都应只发送一次，同一授权再次调用会被拒绝。

练习：把响应文字从半句话改成看起来完整的一段话，但保留 `length`，是否应允许应用？答案：仍不允许。不能凭文学外观代替服务的明确截断状态。

拓展：为一个有正式协议的厂商适配器设计结束状态映射表。先列出正常、拒绝、截断、工具调用四类，再写对应测试；不要把所有不认识的状态默认归为成功。
