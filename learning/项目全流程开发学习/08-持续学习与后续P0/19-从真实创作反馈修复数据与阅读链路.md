# 从真实创作反馈修复数据与阅读链路

## 本章目标

读完本章，你应能解释三个问题：为什么数据库中的 AI 改稿正确，作者继续输入却把它覆盖了；为什么知识库保存了手法，搜索和 AI 仍用不到；为什么净稿导出应是同一份作品的不同呈现，而不是另一份正文。

本章对应 2026 年 10 月 21 日的真实创作旅程评审与后续修复。评审样稿为原创测试数据，发现记录在 `tasks/author-journey-review-2026-10-21.md`。这里讲实现与推理，不把一篇短样稿的体验推断为所有作者的效率或文笔提升。

## 一、先理解技术：React 状态与编辑器状态

React 组件可以由父级传入状态；Tiptap 则在内部维护 ProseMirror 文档、光标、选区和撤销历史。把文档传入 `useEditor` 的 `content` 参数，主要是在创建编辑器时提供初始内容，它不会替应用处理所有外部更新。

因此，界面可能同时有三份互相关联的数据：

| 位置 | 责任 | 容易发生的问题 |
| --- | --- | --- |
| SQLite | 已提交的作品内容与版本 | 不能代表尚未保存的输入 |
| React draft | 当前章节的应用草稿 | 外部 AI 采用会更新它 |
| ProseMirror state.doc | 编辑器真正显示和修改的正文 | 未同步时继续向外发送旧文 |

旧问题的顺序是：作者确认 AI 候选 → 数据库和 draft 更新 → 编辑器仍显示旧文 → 作者键入一字 → 编辑器的 onUpdate 把旧文加一字写回。数据库没有凭空丢失数据，错误发生在编辑器与应用草稿的同步边界。

### 本项目怎样修复

阅读 `src/renderer/components/chapter-editor.tsx` 的 `useLayoutEffect`。实现先通过 schema 把传入文档转换为 ProseMirror node，再比较真实结构：

```ts
const incoming = editor.schema.nodeFromJSON(document);
if (editor.state.doc.eq(incoming)) return;
```

内容相等时不重置编辑器，避免每次正常输入都破坏选区和撤销。内容确实来自外部更新时，用 transaction 替换文档；`preventUpdate` 防止产生一轮重复保存，`addToHistory: false` 避免把同步动作当成普通键入。`closeHistory` 切开此前的撤销分组，光标再用 `TextSelection.between` 调整到新文档的合法文本位置。

这里使用 `useLayoutEffect` 是为了在作者看到下一帧并继续输入前完成外部正文同步；它不代替数据库事务或保存失败处理。不要用一个无条件 `setContent` 解决全部问题，否则每次父组件渲染都可能干扰编辑。

### 跟做与观察

1. 在隔离测试作品写两章不同的短文。
2. 用候选采用流程修改第一章，采用后立即再键入一字。
3. 等待自动保存，切到第二章再返回。
4. 核对可见正文、保存后的正文和字数都包含已采用内容。
5. 再检查普通键入的撤销与光标没有被每次渲染重置。

对应回归是 `tests/unit/chapter-editor-sync.test.tsx` 与 `renderer-ai-editor-sync.test.tsx`。后者走实际 App 和隔离 SQLite，覆盖采用、继续输入、保存和切章返回，不能只用一个组件 mock 证明整条链路。

## 二、知识入库不等于知识可用

数据库表、前端对象、卡片、搜索索引和 AI 上下文是不同环节。某个字段只写入表却没有被查询和传递，就会形成“保存成功，但没有人能读到”的功能缺口。

RainSoul 的学习单元分为：摘录原文 `body`、来源 `source`，以及 `learningNotes`。每条注释包含写作手法 `technique`、适用场景 `usage`、仿写练习 `exercise`。原文属于来源证据，注释属于作者审核的讲解，两者不能混为原句。

### 本项目中的完整路径

```text
拆书候选 / 作者编辑
  → learning_annotation 持久化
  → readAssets 批量读回 learningNotes
  → 卡片展开阅读 / 编辑草稿
  → 关键词索引、本机语义索引
  → 选作参考时构建 AI 上下文
```

`src/workers/database/assets.ts` 批量读取注释，避免每张卡片再单独查数据库。`assets-knowledge.ts` 的更新有三种含义：不传注释保留现有值；传 `[]` 明确清空；传列表替换为作者确认的内容。缺省和清空必须区分，否则只改标签也可能无意删除教学内容。

`knowledge-learning-notes.tsx` 负责阅读与编辑。修改先留在界面草稿中，点击取消丢弃草稿，不调用持久化。作者选择参考时，界面提示会附带学习注释；`src/shared/ai-reference.ts` 给实际请求加上“知识原文”和“作者审核学习注释”标签。

例如下面的讲解是本章的原创教学示例，不是引用某本小说：

```text
原文：她把信折好，又重新展开。
手法：重复一个微小动作，用动作的反复表现犹疑。
场景：人物已经做出决定，却仍不能离开。
练习：换成钥匙或船票，写三句，不直接使用“难过”。
```

检索“重复动作”可以依靠注释找到这个知识单元，但灰字补全仍只能引用可核对的原文。AI 可借鉴手法生成不同表达，是否采用由作者判断。

## 三、原文身份与搜索身份为什么不同

语义检索通常把文本分块，计算向量，再缓存到本机索引。缓存必须知道文本何时变了；否则作者改了手法讲解，检索仍沿用旧向量。

`src/shared/knowledge-learning.ts` 提供两种组合：`learningNoteText` 给教学字段加标签；`knowledgeSearchText` 合并原文与教学说明，作为派生检索文本。检索实现保留两种身份：

| 字段 | 变化条件 | 用途 |
| --- | --- | --- |
| bodyHash | 原文变化 | 追溯原句和来源身份 |
| searchHash | 原文或学习注释变化 | 索引缓存的失效与重建 |

`src/workers/retrieval/engine.ts` 用 `searchHash` 检查索引新旧，并对 `searchText` 分块。检索命中教学段时，展示的引用仍返回知识原文，不把讲解伪装成作者摘录。不要为了让缓存失效而直接改原文哈希，那会破坏证据链。

关键词与语义检索都包含学习注释，不代表所有模糊意图都会命中。真正的质量核验还需要“读信后犹疑”“重复动作”等查询集、相关条目和不相关条目的对照，不能只看接口返回了几条结果。

## 四、伏笔的状态和证据不是同一个事实

“已埋设”“已回收”表示作者管理的剧情状态；“证据需复核”表示当前正文与已有证据的对应关系。修改正文中的蓝船票为红船票，不应该由系统擅自把伏笔从已回收改成未埋设，但必须提醒作者原摘录已失配。

`src/shared/evidence-status.ts` 统一计算证据有效性：章节是否存在、段落是否存在、存储证据是否有效、摘录是否仍在当前段落。列表、详情、正文书签和规则检查复用同一判断。书签接收当前未保存草稿，以免作者改完句子后仍看到旧的健康状态。

选章、选段时自动带出段落文本，作者仍需确认提交。自动填充减少重复录入，不等于自动产生“埋设成功”的证据；旧摘录继续保留，供作者比对和追溯。书签文字本身不算进正文摘录和写作字数。

## 五、一份数据，两种导出呈现

作者给读者看的手稿与自己保存的创作资料有不同信息需求。新增导出模式是表达层的决定，不应删除数据库中的书签、伏笔或来源。

`src/shared/manuscript.ts` 定义 `ManuscriptExportMode = 'clean' | 'full'`。主进程 IPC 对枚举做校验，省略模式时仍使用原来的 `full`，第三个参数依旧是历史快照 ID，模式放在第四个参数，保持已有调用兼容。

| 模式 | 导出内容 |
| --- | --- |
| 正文净稿 clean | 作品名、卷章标题、正文和换行；隐藏知识编号、伏笔标记和资料清单 |
| 含创作资料 full | 保留原来的知识编号、引用清单、伏笔标记和证据清单 |

`src/main/manuscript-export.ts` 先验证冻结数据，再按模式产生输出块。同一份输出块用于 TXT 与 DOCX，减少两种格式含义不一致的问题。净稿仍校验书签关联，不用隐藏错误来制造“导出成功”。当前作品和历史快照导出均先经过保存门禁，快照导出只读取历史，不执行恢复。

## 六、减少视觉噪声，也要保留键盘能力

出处默认去掉系统生成的完整哈希，点击“来源校验详情”仍可读完整可追溯信息；作者自由输入的普通来源不按这套规则盲目删改。同句不同来源的知识，在书签目标中显示原句加出处，作者才能选对。

新增 `<details><summary>` 后，旧弹窗只遍历 button 的焦点循环漏掉了 summary。这个问题说明视觉改动也会改变交互结构。修复应包含折叠标题、排除不可交互元素和收起的内容，并覆盖 Tab、Shift+Tab 与首尾循环；只用鼠标点开一次不足以证明可访问。

## 七、拓展练习与验收思路

1. 画出 AI 采用后数据库、React draft、ProseMirror 文档之间的时序图，指出禁止旧内容回流的位置。
2. 给知识编辑增加一个可选教学字段，列出需要更新的读写、卡片、参考预览、关键词和语义索引，而不是只修改表结构。
3. 写回归：只改学习注释，bodyHash 不变，searchHash 改变；取消编辑时数据库和索引都不变化。
4. 设计三组检索任务，分别只匹配原文、只匹配手法、完全无关；记录命中身份，不能把无关召回当成功。
5. 对同一快照导出净稿和完整稿，比较正文是否一致，确认净稿没有管理标记且作品数据未改变。
6. 只用键盘打开书签、阅读来源详情并退出，观察焦点是否回到打开它的位置。

运行顺序从小到大：定向回归、类型和静态检查、完整单元覆盖率、后台桌面及 Demo 测试、生产构建、独立代码复核。具体通过与失败以本轮执行记录为准；真实云质量、干净 Windows 安装矩阵和长篇写作表现需要分别验证。
