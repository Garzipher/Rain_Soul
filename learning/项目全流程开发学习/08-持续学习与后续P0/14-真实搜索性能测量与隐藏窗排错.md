# 真实搜索性能测量与隐藏窗排错

作者输入“雨”后需要及时看见相关正文和知识。SQL 查询很快，只能证明其中一个环节快；本章跟做一次从真实搜索框输入到结果渲染的性能验收，并解释为什么测试窗口的状态会改变测量结果。

**本章状态（2026-10-09）：**正式 Electron 的离线搜索完成固定种子性能验证。100章、100万统计字、1000条知识，20条查询各10次，共200个正式样本，nearest-rank第190个得到P95 **113.90ms**，通过既有≤1秒门槛。测试使用生产构建的开发入口，不表示安装器或其他机器已经验收；没有向云端发送任何正文。

## 1. 先说明测量起点和终点

本次起点是实际搜索输入框收到 `input` 事件的时刻，终点是正确结果出现在真实DOM中、搜索状态结束，再经过两帧渲染。输入通过Playwright操作真实控件，不替换搜索API，也不直接调用Repository来计时。

完整路径如下：

```text
搜索框input → React状态/搜索effect → App.searchWork
→ preload白名单 → 主进程StoreService → DatabaseClient
→ SQLite Worker/searchAssets → IPC回执 → React结果DOM → 两帧渲染
```

计时前调整搜索范围和标签属于准备工作，不混入正式样本。测试的DOM核对和双帧等待属于测量成本，记录时明确包含。P95代表95%的样本不超过这个值，并不保证所有未来设备、作品或冷启动都同样快。

## 2. 构造可复现的一百万字作品

夹具位于 `tests/fixtures/search-performance.cjs`。测试先从客户端创建一部真实空作品，正常关闭，随后只向本次临时目录中的新作品库定点填数据，再启动客户端读取。作者的原作品库和正在运行的旧程序不参与测试。

| 数据 | 固定生成方式 |
| --- | --- |
| 章节 | 100章，每章20段 |
| 正文 | 每段500个统计字，合计100万字 |
| 知识 | 1000条，每条120个字，保留唯一测试出处 |
| 标签 | 甲按偶数下标、乙按3的倍数；下标0拥有两标签 |
| 搜索索引 | 2000段正文＋1000条知识，共3000行 |

固定种子为 `1382115694`；对象ID由种子、类型和下标散列生成，填充正文用确定性序列。主题覆盖雨夜、月光、雪、灯塔、人物神态和英文词。每次生成的文本与标签关系相同，便于比较改动前后。

```javascript
const seed = 0x5261696e;
// 每个正文段落都是汉字、ASCII字母或数字，实际重新统计确认总数。
const totals = db.prepare('SELECT COUNT(*) AS chapters,SUM(word_count) AS words FROM chapter').get();
if (totals.chapters !== 100 || totals.words !== 1000000 || counted !== 1000000) {
  throw new Error('性能夹具统计字数不匹配。');
}
```

上述节选中的 `counted` 来自逐字符重新统计，不仅信任数据库里手写的 `word_count`。一百万字用于验收性能，软件不限制作者只能写这个长度。

夹具把正文写入受限文档，知识写入条目和历史表；`search_document`插入触发现有FTS5索引触发器。没有另造比正式产品更快的查询实现。填充结束执行外键检查，失败不启动测量。

## 3. 选查询并独立核对结果

20条查询包括中文单字“雨、月、雪”、双字“灯塔、车站、内心”、长词“紫色海岸线、人物神态描写”、英文大小写、数字、无结果，以及单标签和双标签AND组合。

测试在独立的JavaScript穷举中计算应出现的知识全文/出处和正文摘要，不调用产品SQL来生成预期结果。正式客户端每次返回后，把真实卡片和正文结果逐项比较。知识卡片按最新条目展示，SQL回执按ID排序，所以知识比较先按唯一出处整理；正文结果保持严格顺序核对。

这个夹具中，“雨”命中63条知识与125段正文；知识限定标签甲仍为63条，标签乙为21条，甲AND乙为21条。另一个双标签查询没有结果，能检出误用OR的实现。

每次正式查询前，先搜唯一出处 `性能夹具参考0000`，它稳定命中一条知识。随后正式查询必须产生不同结果DOM，空结果也不能沿用上一次空页面。220次准备查询单独排除统计，20次预热单独排除，只有随后200个正式样本进入P95。

## 4. 三个测量器错误怎样排查

第一个问题是点击“打开作品”后立刻点击侧栏。百万字作品的读取还没结束，产品的busy门禁拒绝切换，测试实际上留在写作页。修复测试的同步点：等真实作品标题出现、章节标题可编辑，再进入知识库。

第二个问题是强制要求看见“正在搜索”。很快的空查询可能把React的搜索中与完成状态合并，DOM从来没有出现这个短暂提示。不能因此判定产品卡死。改为要求输入之后发生真实DOM变化，且结果与独立预期一致；准备查询固定命中一条，让正式空结果也必须变化。

第三个问题是隐藏窗口。开发测试入口默认不显示窗口，最初即使关闭后台节流，双 `requestAnimationFrame` 仍受到隐藏窗条件影响；trace中单次等待约1.8秒，整轮测试因总预算超时。这个条件没有模拟作者实际阅读界面，不能据此宣布正常搜索失败，也不能直接删掉渲染等待美化数据。

```javascript
const window = BrowserWindow.getAllWindows()[0];
window.webContents.setBackgroundThrottling(false);
window.showInactive(); // 显示隔离测试窗，不抢作者当前窗口的焦点。
```

只调整测试隔离窗口，不改产品窗口行为。报告记录 `visible=true` 与 `backgroundThrottling=false`。修正后20次预热落在39.70–168.60ms，正式样本完整跑完。所有失败都发生在测试准备/测量条件，修正时保持原P95≤1秒门槛。

## 5. 计算P95并核对机器

```javascript
const sorted = samples.map(sample => sample.durationMs).sort((a, b) => a - b);
const rank = Math.ceil(0.95 * sorted.length);
const p95Ms = sorted[rank - 1];
```

200个样本的rank为190；数组从0开始，所以取 `sorted[189]`。本次P95为113.90ms，中位数75.90ms，最大值147.80ms。无需放宽阈值或删除慢样本。

| 实际测试环境 | 记录值 |
| --- | --- |
| 系统 | Windows 10 Pro，build 19045 |
| CPU | Intel Core i5-4460，3.20GHz，4物理核/4逻辑核 |
| 内存 | 8GB，报告保留实际字节值与测试开始可用内存 |
| 临时作品盘 | C盘，GLOWAY YCT256GS3-S7 Pro，256GB SATA SSD |
| 其他磁盘 | 本机还有WDC机械硬盘，未把它当作此次临时作品盘 |
| 页面视口 | 1280×840，可见且不抢焦点 |
| Electron | 44.7.0，生产构建开发入口 |

存储介质用 `Get-Partition`→`Get-Disk`映射临时目录所在卷，再与 `Get-PhysicalDisk`核对，不因机器“有SSD”就假定测试作品一定在SSD。Windows 11和安装包路径仍需要各自验证。

## 6. 跟做步骤与检查点

1. 关闭其他重型测试，保留作者程序；确认依赖已经安装。
2. 在项目根目录执行 `npm run build`，让测试读取当前生产构建。
3. 执行下面的专用命令；窗口会显示但不抢焦点，测试只清理自己的临时目录。
4. 阅读报告中的200条 `samples`，确认20查询各10次。
5. 核对 `methodology.rank=190`、预热20次、准备220次以及机器和viewport。

```powershell
npx playwright test --config playwright.desktop.config.cjs search-performance.spec.cjs --workers=1
```

报告在该用例的 `test-results-desktop`目录内，文件名为 `search-performance.json`，同目录保存截图；运行下一批桌面测试可能清理这些产物，因此发布证据应另行归档。本教材记录2026-10-09的已验证成绩，新运行应读它自己的报告，不把书中数值当固定预期。

练习一：为什么不能把Repository查询耗时直接叫“UI搜索P95”？答案：它漏掉输入到effect、IPC与渲染，不能代表作者等待的完整过程。

练习二：如果20个预热样本非常快，能代替正式200样本吗？答案：不能；统计方法固定，预热另计，每种查询还需要10次正式样本。

练习三：为什么不能在隐藏窗失败后直接删除两帧等待？答案：那改变了测量终点。应先复现并纠正窗口条件，保留真实渲染范围与原阈值。

练习四：未来P95变成1050ms应怎样处理？答案：先核对机器、窗口、数据与样本方法，定位真实慢环节；不能删除慢样本、改分位算法或放宽1秒门槛。性能不达标就记录失败并修复。

检查点：能解释数据规模、UI计时边界、独立结果核对、nearest-rank与机器介质验证，并区分测试条件错误、应用缺陷和发布外部验收。
