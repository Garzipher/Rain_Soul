# 整部作品快照实践

“第一稿很好，修改后想回到第一稿，但也不想丢掉今天的改动。”这个场景需要保存整部作品的关系图。仅复制一个章节文本，会让知识、伏笔证据和大纲停留在另一个时间点。

**本章状态（2026-10-09）：**手动快照、只读预览、恢复前保护与恢复为新版本已实现；单元、Repository、Worker、渲染与真实 Electron 测试通过。桌面验收已验证正文、知识、伏笔与书签关系恢复，并在正常退出重启后读取历史。完整 P0 最终门禁仍在进行，项目归档详见本卷第九章。第五卷的自动保存解决当前稿落盘，本章解决明确时间点的历史保存，两者都需要。

## 技术基础：关系图快照与事务恢复

### 快照不是只保存一段文字

状态快照记录一个明确时间点的完整内容关系。例如正文里的书签指向知识 K，伏笔 F 的证据指向段落 P；如果只恢复正文却不恢复 K/F/P 关系，读者看到的材料来自多个时间点。

项目将选定内容表序列化为 JSON payload，并记录 hash、来源 revision 和格式版本。其他快照和操作回执不递归纳入 payload，否则一次创建会反复嵌套整个历史，膨胀且破坏幂等语义。

### 内容版本和写入版本不同

恢复旧内容不等于恢复旧并发版本。当前 revision 继续增长，代表一次新的有效修改；source_revision 保留“这份内容当时来自哪稿”。若把 revision 倒退，旧请求可能再次满足 CAS，从而覆盖刚恢复的作品。

### 延迟外键检查的含义

恢复会先移除当前内容再插入旧关系，中间瞬间可能出现暂时不完整的关联。`defer_foreign_keys=ON` 将检查延迟到事务完整状态，但提交前仍核对所有外键。它不是关闭关系约束。

```text
当前稿 B
→ 同事务保存 B 为安全快照
→ 校验并恢复 A 的完整关系
→ 重建搜索、核对外键
→ 捕获恢复后新状态、提交
```

因此创建安全快照失败、正文插入失败或外键失败，都必须回滚整个恢复。下面用失败触发器证明“发生错误”同时意味着“原稿与历史保持”。

## 1. 先理解三种版本

`work_meta.revision` 是并发写入校验版本，每次有效修改向前增长。快照 `source_revision` 表示捕获时的作品版本；快照 `schema_version` 是快照格式版本，目前为1。作品数据库 `user_version` 当前为4。它们回答三个不同的问题，不可混作一个数字。

| 字段 | 回答的问题 | 恢复后行为 |
| --- | --- | --- |
| 作品revision | 当前写入基于哪一稿 | 继续增长 |
| 快照source_revision | 当时捕获的是哪一稿 | 保留历史值 |
| 快照schema_version | 如何解释JSON关系图 | 按支持格式校验 |

文件 `src/shared/snapshots.ts` 定义界面可见摘要和命令；`src/workers/database/snapshots.ts` 保存和恢复关系图。

## 2. 快照包含什么

快照包含 `work_meta`、卷、章、知识、标签关系、剧情、伏笔证据、写作特点和资产历史。默认学习作品还包含课程跟踪映射，用于在同一作品恢复后继续保护作者删除状态。

快照不包含搜索索引、操作回执、其他快照、作者头像或 API Key。搜索索引可以从正文重建；操作回执用于当前数据库幂等，不能跟随旧稿回退；作者身份与模型凭据不属于小说内容。

```typescript
const payload = JSON.stringify(capture(db));
const payloadHash = createHash('sha256').update(payload).digest('hex');
```

这是实现原理的节选。完整存储还带快照 ID、名称、类型、时间、来源快照和源版本。SHA256验证内容是否与记录一致，不证明来源可信，也不能代替文档与关系校验。

## 3. 创建与预览数据流

```text
写作右上角“版本历史” → 快照面板 → createSnapshot请求
→ App保存门禁等待当前稿 → preload与IPC
→ StoreService串行命令 → Worker → WorkRepository
→ 校验expectedRevision与operationId
→ SQLite事务capture + snapshot行 + 操作回执
→ 新WorkDetail与快照摘要回到界面
```

`src/renderer/components/snapshot-panel.tsx` 将创建、列表、预览与恢复分开。点击预览只能读取摘要、卷章、字数和素材规模；不能创建新快照、恢复正文或修改作品版本。

## 4. 恢复为什么产生两份保护记录

设当前稿是B，选择旧快照A。恢复事务先捕获B为安全快照，再把A的正文与资产替换到当前工作区，最后创建一份“恢复后”快照。A、B和原历史都还在。

```text
当前B + 历史A
→ 校验A格式/hash/作品身份/文档字段
→ 捕获B（恢复前安全快照）
→ 替换A的关系图，稳定对象ID保留
→ 重建全文搜索，检查外键
→ 当前revision增加，捕获恢复后状态
→ 一次事务提交
```

关键步骤在同一事务中。`defer_foreign_keys=ON` 允许事务内先删除旧关系再完整插入新关系，但提交前仍必须通过外键检查。这里延迟的是检查时机，不能取消正确性检查。

原章节、知识、伏笔 ID 稳定，恢复不是按标题重新匹配对象。快照恢复后当前 revision 不能下降，否则此前写入命令可能错误地再次被接受。

## 5. 跟做：保存、修改、恢复、再回到修改稿

1. 创建测试作品，正文写“雨落在旧车站”，增加一个雨景知识条目与“旧钥匙”伏笔。
2. 点击写作右上角“版本历史”，为当前关系图创建“第一稿”。
3. 修改正文、知识内容和章节标题，再查看“第一稿”预览，确认预览仍显示当时章名。
4. 点击恢复并在对话框确认，核对第一稿正文、知识和伏笔一起恢复。
5. 列表中应保留“第一稿”，并新增恢复前、恢复后记录。
6. 预览恢复前安全快照，再恢复它，核对修改稿可再次读到。
7. 正常退出重启，确认历史列表仍保留；头像和名称始终没有随小说变化。

预期：预览不修改内容，恢复后字数与搜索结果和恢复稿一致；历史不会因回到旧稿而被清空。失败保护测试在隔离目录运行，不要手改真实作者的 snapshot 表。

`tests/unit/snapshots.test.ts` 用真实 SQLite，创建失败触发器模拟恢复过程中插入章节失败。测试要求当前稿、历史数量和搜索索引整体回滚。


## 7. 问题根因与修复方法

| 现象 | 常见根因 | 正确处理 |
| --- | --- | --- |
| 恢复旧稿丢掉当前稿 | 替换前没有安全快照 | 同事务先捕获当前状态 |
| 正文恢复但搜索仍显示新稿 | 搜索作为独立历史保存 | 恢复内容后重建索引 |
| 一部作品恢复另一作品快照 | 未检查payload作品ID | 严格身份校验 |
| 恢复失败仍留下一条保护记录 | 创建与替换不在同一事务 | 失败全部回滚 |
| 快照预览变成写入动作 | 读取与恢复共享处理入口 | 保持预览只读 |

调用方应保留同一 operationId 供未知回执重试。快照按钮不能绕过自动保存失败门禁，也不能在作者输入法组合过程中捕获不完整正文。

## 8. 练习与检查点

练习一：恢复A以后，为什么作品revision不能改回A的source_revision？答案：并发写入版本必须单调增长，否则旧命令可能被当作新命令接受。

练习二：为什么快照不打包搜索索引？答案：索引是可重建缓存，历史保存应该以正文和关系为准。

练习三：给损坏 hash 测试增加断言，证明没有创建安全快照、没有修改正文。

参考步骤：创建 A，修改当前稿为 B，记录 B 的文档、revision、快照数量；在临时库中损坏 A 的 payload_hash，调用恢复，断言抛错后三项完全不变。再做只读预览，断言数量与版本仍不变。测试必须比较状态，不能只写 toThrow。

检查点：你能解释一次恢复的事务边界，并证明任何一步失败都不会留下半份旧稿或丢掉当前稿。
