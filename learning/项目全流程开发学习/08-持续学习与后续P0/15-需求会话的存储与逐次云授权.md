# 需求会话的存储与逐次云授权

你在“雨夜来信”下面开启一个会话，讨论主人公为何返回旧站。写了一段问题后关闭程序，第二天应当能继续读到草稿。点击发送时，必须先看清发给哪个模型、带了哪些消息、是否计费。回答到来时如果已经修改问题，也不能把旧回答挂到新问题下面。

本章学习怎样把这些要求落实到 React、Electron、SQLite 和 HTTPS。2026-10-09 的实现已经加入会话存储、授权服务和对应测试；网络用隔离替身验证。本章没有用真实云模型返回结果证明服务可用，正式发布结论仍看验收记录。

## 1. 从对象、关系和版本开始

作品是一个创作项目，会话是作品下面的一段讨论，消息是讨论中有顺序的记录。作品标题和会话标题可以重复，持久关联使用 UUID，不靠名称匹配。

SQLite 是进程内关系数据库。表用列约束记录的形态，外键约束消息必须属于已存在的会话，事务把多个改动一起提交或一起回滚。`src/workers/database/conversations.ts` 建立三张表：

| 表 | 保存的内容 | 为什么需要 |
| --- | --- | --- |
| conversation | 标题、草稿、独立 revision、创建/更新时间、删除标记 | 离线写问题、改名、软删除与冲突检测 |
| conversation_message | 消息 ID、会话 ID、user/assistant、文本、顺序、请求哈希 | 重启后保留对话及回答对应的授权请求 |
| conversation_operation | 操作 ID、输入哈希、紧凑回执 | 同一次保存重试不会重复写入 |

`revision` 是修订计数，不是软件版本。正文的修订和会话的修订独立：修改会话草稿不会让正在写的章节发生正文版本冲突。会话中的消息按 `sort_order` 排列，时间戳用于显示，不能只凭同一毫秒的时间确定顺序。

读取后得到的 `ConversationDetail` 包括摘要字段、draft 和 messages。接口定义在 `src/shared/conversations.ts`；它让界面和数据库共享同一种数据形态，Zod 在真正跨进程时验证输入，TypeScript 类型本身不能验证运行期的未知数据。

本地历史不删除，默认一次读取最近100条，`messageCount`仍是全部消息数量；`hasMore`与`nextBeforeMessageId`指明还有更早消息。用本会话的游标读取前一页，避免随历史增长一次加载所有消息。界面读了更早历史也不自动扩大云授权：云端重新从数据库取默认最近100条，预览和实际系统提示明确“最近N条/共X条；早期未发送”。

## 2. 为什么保存要带预期版本与操作 ID

乐观并发的意思是“先读再编辑，提交时检查读到的版本是否仍然有效”。例如读取修订 2，保存时带 `expectedRevision: 2`；如果另一个操作已把它改成修订 3，这次旧内容就被拒绝，不能静默覆盖。

```typescript
const request = {
  workId, operationId: crypto.randomUUID(),
  action: { type: 'saveDraft' as const, id: conversationId,
    expectedRevision: detail.revision, draft: text },
};
await api.manageConversation(request);
```

这是 `ConversationWorkspace.saveDraft` 使用的协议。修改保存内容时创建新操作 ID；同一次保存发生未知回执时保留原请求并重试。仓储 `mutate` 先核对 operationId 的输入哈希；同 ID 同输入返回最新会话，同 ID 不同输入拒绝。回执只存会话身份，避免每次输入都把完整消息历史再复制一遍。

失败时界面保留本地文本和待重试请求，不把“没有收到成功”当作“数据库一定没写入”。`StoreService` 串行处理请求，限制只访问当前作品；数据库再核对作品所属和删除状态。前端隐藏按钮不能替代这些检查。

## 3. 从点击发送追踪到数据库

```text
ConversationWorkspace保存草稿
→ prepareConversationAi({workId, conversationId, expectedRevision})
→ ConversationAiCommands读取数据库中的真实会话
→ ConversationAiService构建最近100条以内历史＋草稿＋会话系统要求
→ 界面显示服务、模型、全部材料、计费提示
→ 作者明确确认executeConversationAi
→ 主进程验证一次性token、hash、配置和会话修订
→ DNS公开地址检查，读取安全凭据，再次核对会话
→ HTTPS发送一次，完整回答才返回
→ 再核对修订 → appendConversationTurn单事务写入两条消息
```

会话没有默认附作品正文、知识、伏笔或大纲。这是本次明确的发送范围。分页范围是可见设计，不声称模型看过未发送的更早历史。会话回答也没有自动改稿权限，不走 `paragraphPolish` 操作，不进入正文候选应用接口。后续如果增加“把某段正文附给会话”，必须把它加入真实预览和新授权，不能暗中复用之前的同意。

## 4. 读源码中的四个保护点

第一处是 `src/main/conversation-ai-service.ts` 的 `prepare`。它把消息和草稿解析成独立副本，计算完整请求的 SHA-256，再生成随机确认 token。哈希绑定服务地址、请求正文、作品、会话和修订；token 默认五分钟有效，只允许发送一次。准备时不读取密钥，也不联网。

所有消息文字合计最多 200000 字符，这是单次云请求保护，不是限制一本书能写多少字。超长或超过配置的模型容量，明确要求缩小范围或新建会话，当前不会偷偷截掉开头。token 数是保守估算，不是服务商 tokenizer 或账单。

第二处是 `src/main/ai-transport.ts` 的 `sendAiCompletion`。正文 AI 和会话复用公开 HTTPS 地址校验、DNS结果检查、固定 IP 连接、TLS域名验证、2MB响应限制、完整响应解析及凭据回显保护。私网或重定向不能成为授权云服务的替代目标；上游错误原文也不能带着密钥出现在界面。

第三处是 `ConversationAiCommands.validate`。DNS查询和密钥读取都是异步操作，这段时间草稿可能变化。因此 `beforeSend` 在真正发出请求前再次检查会话和配置；发送完成后再检查一次。`requestHash`不能代替版本检查，它只说明发了什么，不说明当前草稿还与它一致。

第四处是仓储 `appendConversationTurn`。它在单一事务内确认会话修订、精确草稿文本，写入 user 和 assistant 消息，清空草稿并将会话修订加一。第二条消息失败时，第一条消息及清稿一起回滚。两条消息有各自稳定 ID 和相同请求哈希；operationId防止持久化重放产生第二对消息。

取消/超时/网络失败都不自动重发。晚到完整回答遇到草稿变化时保留到恢复缓存，不写入新草稿对应的会话；作者可对照、复制或明确放弃后再决定是否发起新请求。云端生成已经发生时，取消本机处理不意味着服务商必然未计费。

## 5. 回答已生成，保存却没有确认怎么办

云生成和SQLite事务无法合成一个跨服务事务。模型已返回完整文字，数据库可能因磁盘错误没写入，也可能已写入但IPC回执丢失。此时自动重发云请求既可能再次计费，也不能解决“到底保存过没有”的问题。

`ConversationAiCommands`收到完整回答立即保留回答、原草稿、两条消息ID、expectedRevision、operationId与requestHash，再做发送后的状态核对和数据库写入。后验变更或存储回执失败时返回 `CONVERSATION_REPLY_PENDING`，界面保持草稿并提供“重试保存回复”。`retryConversationReply`重复原数据库请求，绝不再次调用模型；如果第一次实际已成功，仓储幂等回执返回当前会话，不增加第二对消息。

```text
完整回答 → 本次主进程的回复缓存 → appendConversationTurn
                                      ↓ 保存未确认
同requestHash → retryConversationReply → 同operationId原请求
```

若版本冲突仍不能保存，可用 `readPendingConversationReply`读取原问题、回答与当前草稿对照，作者先选取复制保留。明确确认放弃后，`discardConversationReply`只丢本次内存中的恢复记录，不删除任何已入库消息。取消网络token不等于放弃已生成的回答。

执行IPC本身也可能丢回执。界面先锁为“待核对”，按requestHash查询本机记录；还在网络或保存流程中的hash返回 `CONVERSATION_IN_PROGRESS`，不能当作“没有回答”，也不能同时丢弃或重试保存。请求结束后再核对本机结果，不自动重发云请求。

恢复缓存只在本次主进程运行中存在，不是额外持久化消息表。处理完成前不要强制杀进程；界面必须保护未决保存状态。未知hash不能恢复，重新启动后应先读取会话核对是否已经入库，不能把“缓存没有了”解释为“服务没生成过”或直接自动重发。

这些恢复接口同样经Store校验当前作品，不能用另一个作品的requestHash读取未发表内容。完成记录可限量淘汰，尚未确认的回答不能因为新请求挤入缓存就被静默丢弃。

## 6. 跟做一次离线保存与授权取消

1. 在隔离测试作品中新建会话，改名为“主人公动机”。输入“他为何在雨夜返回旧站？”并等候草稿保存。
2. 切换到另一个会话后返回，再退出并重启。问题仍为草稿，没有伪造的 AI 回答。
3. 未配置云服务时点击准备，应提示先配置，不读取其他工具的凭据。
4. 配置专门测试服务后点击准备。检查预览只包含所披露的最近消息和草稿，服务、模型、计费提示均显示，再点击取消。
5. 返回会话检查草稿还在，消息数量和正文版本没有因取消变化。

## 7. 归档、正文快照和数据库升级

整部作品归档包含会话和消息，导入时作品命名空间、会话与消息身份一起转换，复制出的作品独立。现行数据库为 schema v5，旧 v4 项目启动前先创建一致备份，再事务建会话表，完整性检查成功才更新 schema。

正文快照保存写作资产，不回滚当前会话。恢复旧稿后仍能查看“为什么决定这样修改”的当前讨论，这与“恢复整部归档生成新作品”的复制语义不同。`tests/unit/conversations-archive.test.ts`覆盖归档往返、旧v4归档和快照保留会话；`conversations-migration.test.ts`覆盖迁移备份及失败回滚。

## 8. 失败实验与检查方法

先运行 `npx vitest run tests/unit/conversation-ai-commands.test.ts tests/unit/conversation-ai-service.test.ts tests/unit/conversations.test.ts`。这些测试不会向真实云服务发送作者内容。

| 实验 | 操作方式 | 应当观察到 |
| --- | --- | --- |
| 授权后改草稿 | 在命令测试中预览后调用 changeDetail | 不发送旧请求，提示重新预览 |
| 凭据读取期间变更 | credentials.read替身在返回前改会话 | 最后检查拒绝请求，fetch调用0次 |
| 晚回答 | fetch替身返回前改变revision | 草稿保留，不写入回答 |
| 截断结果 | 返回finish_reason='length'和非空文字 | 非空也不能当作完整回答 |
| 第二条消息失败 | 数据库测试用临时trigger拒绝assistant | 两条消息都不提交，草稿不清空 |
| 完整回复保存失败 | commands测试让第一次append失败，再retry | 原operationId与回答不变，fetch仍只有1次 |
| 实际写入后回执丢失 | commands替身提交后抛错，再幂等retry | 返回已保存会话，不产生重复消息 |
| 执行IPC未知回执 | 在fetch尚未返回时读同hash恢复记录 | 返回进行中，拒绝丢弃或重复保存，不重发云请求 |

不要在作者数据库安装测试 trigger。每个实验使用测试框架新建的临时目录，关闭连接后清理。

## 9. 拓展练习与答案要点

练习一：给会话增加摘要压缩。先写出作者预览应包含什么、原历史如何保留、摘要怎样标为AI建议，再设计测试。答案要点：不能把摘要当完整原历史，也不能悄悄改变已经批准的请求；摘要生成和后续发送各需要清晰边界。

练习二：解释为什么两条消息同事务仍需要operationId。答案要点：事务防部分成功，operationId防成功后回执丢失导致重复写入，它们处理不同故障。

练习三：画出“用户取消时数据库已经提交”的处理流程。答案要点：取消不能伪造已撤销；读取最新会话展示已保存结果，保留实际提交证据，而不是强行恢复旧草稿或自动再发送。

练习四：在隔离的旧v4归档中新增会话后再次导出。答案要点：检查新归档带会话，导入新作品的ID独立；正文快照恢复不能把会话回到旧状态，云凭据不随归档迁移。
