# 第一章 用测试证明行为而非猜测

本章状态：现有核心逻辑采用测试先行并完成阶段验证；全P0、长篇性能与安装升级验收尚未完成。

学习目标：区分单元、集成、组件和真实桌面测试各自能证明什么，学会把一个缺陷转成能先失败的回归用例。

开发流程是Red-Green-Refactor：先写描述真实行为的失败测试，运行确认失败原因，再实现最小修改，最后在全部相关测试通过后整理代码。仅因为缺少导入文件而失败，不能证明业务缺陷已被复现。

阅读 `tests/unit/save-coordinator.test.ts` 学习可控计时与Promise；阅读 `tests/unit/repository-structure.test.ts` 学习真实临时SQLite；阅读 `tests/unit/renderer-structure.test.tsx` 学习菜单、取消和保存失败交互。

一个例子：删卷确认框显示旧章名。回归测试先修改标题、故意阻止保存，再打开确认框；断言显示新标题、数据库仍是旧标题、取消后草稿保留。它检查的是用户风险，而非内部函数调用了几次。

实践步骤：

1. 从需求写一句可观测结果，例如“同一请求重试不新增第二章”。
2. 建立独立临时目录，不复用真实作者数据库。
3. 明确安排导致缺陷的时序，先运行测试看它确实失败。
4. 修复后运行同模块测试，再执行完整门禁。

常用命令按用途理解：

```text
npm run typecheck       检查静态类型
npm run lint            检查代码规则
npm run test:coverage   运行单元/组件/Worker测试与核心覆盖率
npm run test:desktop    构建后运行真实Electron验收
npm run test:demo       验证Demo参考交互
```

`vitest.config.mts` 指定覆盖率统计模块与80%门禁。某批核心模块覆盖率较高，不意味着所有界面或尚未实现的P0都有同样覆盖；交付记录应同时说明统计范围。

桌面测试在 `tests/desktop/`，必须等待真实状态和回执，不用force点击或JS点击掩盖不可交互问题。临时设置LOCALAPPDATA、APPDATA与Electron档案避免改动用户数据。

证据：上一批卷章管理记录在 `tasks/structure-management.md`，包括103项单元/组件/Worker、69项Demo、开发版与目录包各6项桌面测试。它是当时基线，本轮新增学习作品和Logo要重新跑验证。

练习：选择“恢复卷不恢复先前单独删除的章”，分别写出仓储测试、组件测试和桌面测试要关注的不同断言，避免三个层级重复检查同一实现细节。

边界：测试通过只对实际执行的版本、环境和案例成立；未测的Windows11干净安装与断电恢复不能因现有测试为绿而宣布完成。
