《雨落之后》能打开不等于没有丢稿风险。
本章把保存、数据库、界面、真实桌面分成不同测试层。
完成后，你能为一个功能选择合适的证据，而不是只追求测试数量。

## 技术基础：可测试设计与故障注入

### 为什么测试要先失败

先看到有效失败，可以证明测试确实能发现目标缺陷。若实现和测试同时写完，测试全绿也可能只是断言太弱或测试了错误对象。TDD 将“缺失行为”“实现行为”“整理结构”拆成三个可观察步骤。

好的 Red 是业务断言失败，例如同一操作重试生成了两卷；导入路径拼错导致模块找不到只是环境错误。先修环境，再确认真正缺失行为失败，不能把任何红字都记录为测试先行证据。

### 依赖注入为何有助测试

依赖注入把网络、时钟、传输或文件选择从核心逻辑中传入。`StoreService` 接收 `Transport`，测试可统计危险请求是否越过边界；`SaveCoordinator` 接收 save 回调，测试可以暂停第一批回执再模拟新输入。

```typescript
// 与保存协调器测试相同的控制思想；不是完整生产保存器。
let release!: () => void;
const delayed = new Promise<void>(resolve => { release = resolve; });
async function fakeSave() { await delayed; }
// 测试先调用 fakeSave，再产生新输入，最后 release() 放回执。
```

这比随机延迟更可重复。故障注入还可以令事务某一步抛错，断言 revision、正文和日志一起回滚。注入位置决定测试回答的问题，必须写清楚。

### 单元、集成与端到端不是按文件名区分

调用一个函数但用了真实 SQLite，已经包含集成边界；在 jsdom 点按钮仍不是实际 Electron。测试层次取决于哪些依赖真实执行，而不是扩展名 `.test.ts` 或 `.spec.cjs`。

本项目测试金字塔将大量纯逻辑边界留在 Vitest，把少数关键作者闭环留给真实 Electron。下面的表格会明确每层已经证明的事实和仍需补的事实。

## 1. 前置知识

认识函数输入与输出，知道测试失败会让命令返回非零状态。
断言是把预期写成可执行条件。
测试不能证明没有任何缺陷，只能为被覆盖的行为提供证据。
核心行为需同时考虑正常、边界和失败路径。

```powershell

```

已有依赖无需每次验证重新安装。

## 2. Red、Green、Refactor是什么意思

Red：先写能暴露缺失行为的测试，运行并确认有效失败。
Green：做足够的实现，让该测试通过。
Refactor：整理代码，再运行测试确认行为不变。

“测试因为导入路径拼错失败”不是有效Red。
它没有检验需要实现的业务行为。
“先写完整实现，最后补一条通过测试”也不是测试先行。
你应能说明初次失败来自哪条业务断言。

## 3. 保存功能怎样分层

| 层 | 项目例子 | 主要回答 |
| --- | --- | --- |
| 单元 | save-coordinator.test.ts | 时钟和迟到回执是否正确 |
| 仓储集成 | repository.test.ts | 真SQLite事务与幂等是否正确 |
| 主进程/Worker链路 | database-worker.test.ts | 消息和持久化是否连接 |
| 组件 | renderer.test.tsx | 作者编辑、失败与门禁是否呈现 |
| 桌面 | writing.spec.cjs | 真Electron正常关闭重启是否保留稿件 |

单元测试便宜、定位快，适合大量边界。
真实桌面测试成本高，用于少量关键闭环。
不需要把每个纯函数边界都重复成一条Electron用例。

## 4. 跟做：读一个有因果的测试

```powershell
npm run test:unit -- tests/unit/save-coordinator.test.ts
```

找到“旧回执不能把正在写的新内容标为已保存”。
先用Promise暂停第一批保存。
随后模拟作者继续输入，再释放第一批回执。
最后flush并核对提交数组与clean状态。

```typescript
coordinator.update('旧');
await vi.advanceTimersByTimeAsync(500);
coordinator.update('新');
resolveFirst();
await coordinator.flush();
expect(saved).toEqual(['旧', '新']);
```

这是安排、执行、断言的完整链条。
若错误实现把第一批回执直接设clean，该场景就可能暴露问题。
测试关注行为，不要求内部私有字段与实现逐字相同。

## 5. 跟做：检查真实数据库证据

```powershell
npm run test:unit -- tests/unit/repository.test.ts tests/unit/migration.test.ts
```

测试目录由mkdtemp建立，结束后清理本次临时目录。
不要让测试写到%LOCALAPPDATA%下的真实用户作品。
验证内容不仅包括返回值，还包括重开库后的正文与版本。
保存成功但重开丢失，说明只测内存状态还不够。

临时目录失败时应保留必要日志与截图，方便定位。
不要为了“让测试变绿”把真实性能或持久化断言删掉。

## 6. 覆盖率怎么看

```powershell
npm run test:coverage
```

vitest.config.mts对列入coverage.include的核心文件设80%阈值。
lines是执行过的行；branches是条件分支覆盖。
覆盖率不是代码正确率。
某行被执行过但断言无关，也可能形成虚假的安心。

例如保存失败分支需要验证：

1. 状态变failed。
2. 草稿仍在。
3. 不自动重复发送。
4. 作者显式retry后能恢复。

仅断言“不抛异常”无法证明这四个性质。

## 7. 跟做：完整验证流程

```powershell
npm run typecheck
npm run lint
npm run test:coverage
npm run test:demo -- --workers=2 --reporter=line
npm run test:desktop
```

按顺序执行，不在桌面测试运行时覆盖dist。
类型检查发现契约错误；lint发现规则问题。
Demo测试验证参考原型，不能代替正式客户端验收。
桌面测试会先执行build，验证真实Electron。
每条命令都应等待最终退出，不能把session仍运行当作成功。

## 9. 常见失败诊断

| 现象 | 先看 | 下一步 |
| --- | --- | --- |
| 单个断言失败 | 实际值与预期值 | 检查需求还是实现错了 |
| 测试卡住 | 假时钟、Promise、句柄 | 找未释放的等待 |
| SQLite原生模块错误 | Node/Electron ABI与锁文件 | 用项目环境，不随意换包 |
| 桌面用例随机超时 | 窗口可用状态与并发资源 | 顺序跑、等待可见可用 |
| 覆盖率不足 | 未覆盖分支 | 补有意义的失败场景 |

修超时前先判断是不是没有等待保存门禁完成。
固定sleep很长只是掩盖同步条件，不能构成稳健测试。

## 10. 练习与答案提示

练习一：测试“空标题不能保存”需要哪些断言？
答案：失败原因明确、版本不变、原正文不变、修正后可再次保存。

练习二：为何一百个组件测试不能替代正常关窗重开？
答案：组件环境没有完整Electron进程生命周期与磁盘收尾。

练习三：为新建卷设计Red测试。
提示：先断言新增卷稳定ID、重启保留与空名拒绝，不只断言按钮存在。

## 延伸实验：从数量转向质量

对一条测试逐一问：失败时能否定位、断言是否观察用户价值、是否清理隔离数据？
再问：删除核心保护条件之后，这条测试是否真的会失败？
例如去掉迟到回执的代数比较，如果所有测试仍绿，就需要补更有力的场景。
不必在真实作者作品里故意制造损坏，使用临时目录和受控假服务即可。
最后把相关源码与测试路径写进学习记录，让读者自己运行核对。
