# 根因排查、代码评审与提交

“无法访问”和“点击后没反应”只是现象，不是根因。
本章用项目经历过的回执、草稿标题与Windows文件锁解释排错。
完成后，你能写出带证据的修复记录，并把相关改动提交成独立一步。

**状态说明（2026-10-08）：**以下代码入口真实存在。
历史问题的说明用于理解方法，不宣称你当前必然能再次复现这些故障。

## 技术基础：假设验证与 Git 的三份状态

### 现象、假设和根因

现象是可观察结果，假设是待验证解释，根因是被证据支持的最早错误条件。“标题旧了”是现象；“确认框读数据库缓存而非草稿”是假设；找到错误读取位置并用回归复现后，才能写成根因。

每次只改变与假设有关的最小条件。若同时清缓存、删数据、加延迟和改版本，就算恢复也无法知道哪一步有效，更不能保证没有伤害作者数据。

```text
复现 → 沿输入/草稿/请求/数据库/回执找最早分歧
     → 写失败回归 → 修对应边界 → 重跑回归
     → 核对相关层与完整门禁 → 独立评审 → 提交
```

### 工作树、暂存区与提交

工作树是你正在编辑的文件；暂存区是下一次提交的候选内容；提交是带父版本和说明的持久快照。`git diff` 看未暂存差异，`git diff --cached` 看即将提交的差异，`git status` 看两者概况。

“原子提交”表示一次提交表达一个独立的、验证通过的变化，例如修某个保存失败回归。它不要求代码只有一行，也不允许为了少行数拆出无法编译的半功能。

### 评审如何补足测试

测试验证列出的场景；评审检查遗漏的场景、信任边界和数据流。例如导出测试可能只检查正文，评审还应问引用是否用了同一历史版本。审查发现应能指向触发条件、后果和最小修复，而不是泛泛说“建议优化”。

接下来的案例用这个方法记录错误，而不是把提交日志当作教学正文。先说明为什么错，再说明哪条验证能阻止它回来。

## 1. 前置知识

能读命令退出状态和测试断言。
理解本项目的renderer、main、worker三个边界。
知道Git提交保存版本，不能代替测试和评审。
处理问题前先记录工作区已有修改，不覆盖作者未提交文件。

```powershell
Set-Location E:\soulrain
git status --short
git log -5 --oneline
```

预期你看到当前分支最近提交与未提交清单。
若已有无关修改，后续只暂存本次明确相关路径。

## 2. 先写复现而不是先猜实现

把问题写成可以重复执行的步骤。
例如“编辑卷内章标题后立即删卷，确认框应使用最新标题”。
记录原状态、动作、预期、实际与发生频率。
如果只写“标题错了”，就无法区分缓存、草稿或数据库问题。

| 记录项 | 小说示例 |
| --- | --- |
| 初始状态 | 旧站台位于第一卷 |
| 动作 | 改标题为雨后的站台，马上删卷 |
| 预期 | 确认使用当前草稿信息 |
| 实际 | 若显示旧站台，记录截图与时序 |
| 证据 | 测试名、输出、截图、相关revision |

## 3. 顺数据流寻找最早分歧

编辑器显示的是draft，数据库保存的是已确认版本。
这两个对象不一定在同一时刻相等。
检查确认框取的是draft还是缓存work，是可检验的假设。
不要先把所有缓存删除再看看是否恢复。
那会销毁关键证据。

建议画出：

```text
用户改标题
→ Hook draft更新
→ 保存尚未确认
→ 结构对话框读标题
→ flush后提交结构动作
```

最早不符合预期的边界，就是优先调查的位置。
代码评审也应沿数据流看，而不是仅逐行挑格式。

## 4. 跟做：查看相关实现与测试

```powershell
Get-Content .\src\renderer\hooks\use-structure-menu.ts
Get-Content .\src\renderer\components\structure-dialog.tsx
Get-Content .\tests\unit\renderer-structure.test.tsx
```

搜索测试中的草稿标题和保存失败场景。
确认用例不仅核对打开对话框，还核对实际删除范围。
若一个修复只改显示文字，却错误删除了另一章，仍然不合格。
回归断言应贴近真正的错误影响。

## 5. 另一个案例：Windows打包文件锁

打包工具写入EXE资源时，Windows可能短暂返回UNKNOWN/open。
如果所有错误都重试，缺文件、无权限或工具版本变化会被掩盖。
本项目把重试限定在已观察的特定错误上。

实际入口：

```powershell
Get-Content .\scripts\windows-file-retry.mjs
Get-Content .\tests\unit\windows-file-retry.test.ts
```

源码条件是Windows、code为UNKNOWN、syscall为open。
最多尝试五次，间隔1500ms。
其他故障保持原样抛出，最后一次失败也必须报错。
这属于有限恢复，不是忽略错误。

## 6. 跟做：运行目标回归

```powershell
npm run test:unit -- tests/unit/renderer-structure.test.tsx tests/unit/windows-file-retry.test.ts
```

预期命令成功退出。
单条失败时记录断言与堆栈，不把整个测试套件重跑十次代替诊断。
修复后再运行相关层、完整测试和构建。
通过一次充分验证后，无新变化无需无目的重复同一批检查。

## 7. 评审应问的八类问题

代码质量：职责是否明确，有无重复或失控变更范围？
安全：renderer是否获得任意文件访问，日志是否泄露正文和密钥？
性能：是否把同步数据库放到UI线程，是否复制整书到日志？
可访问性：键盘、焦点、错误提示是否可用？
可观测性：错误能否定位且不暴露敏感内容？
测试：回归是否覆盖原问题与边界？
Git：是否把多个无关功能塞进一次提交？
文档：行为、限制与学习内容是否和实现一致？

项目规章要求主动使用review技能进行二次检查。
评审不是“测试全绿所以不必看”，而是补充测试未覆盖的推理。

## 8. 跟做：检查提交范围

```powershell
git diff --stat
git diff --check
git diff -- src/renderer/hooks/use-structure-menu.ts
```

diff --check用于发现空白问题，不证明代码逻辑正确。
stat帮助判断是否应按独立功能拆分。
本项目200行是软指标，超过500行必须拆分。
不要为了行数把无法编译的半功能提交出去。

在本次路径验证和评审都完成后，精确暂存：

```powershell
git add -- src/renderer/hooks/use-structure-menu.ts tests/unit/renderer-structure.test.tsx
git commit -m 'fix(writing): 修正卷章确认信息' -m '保留最新草稿标题，并增加对应回归验证。'
```

这是修复涉及这两个文件时的示例；本次没有对应改动就不要执行提交。
不要运行git add .把作者其他修改一起带入提交。

## 10. 诊断与练习

| 误区 | 为什么无效 | 更好的证据 |
| --- | --- | --- |
| 只增加sleep | 没有等待业务条件 | 控件可用、回执完成 |
| 把所有异常吞掉 | 不知道是否真成功 | 分类错误与明确失败状态 |
| 先清用户数据 | 销毁复现现场 | 隔离测试样本 |
| 只改测试预期 | 可能迁就错误行为 | 先核对需求与原始证据 |

练习一：为“旧回执清空新草稿”写一句根因描述。
答案要点：成功回执没有区分冻结代数与当前代数，错误确认后续输入。

练习二：为什么文件锁重试需要限定工具版本？
提示：内部接口可能随版本变化，原适配不再可信。

本章检查点：提交前能拿出复现、修复、回归、评审与范围五项证据。
