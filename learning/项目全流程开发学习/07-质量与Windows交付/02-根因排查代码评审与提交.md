# 第二章 从复现到可回退交付

本章状态：已有独立代码评审、真实回归与中文原子提交记录；本章总结已使用的方法，不声称项目没有任何未知缺陷。

学习目标：先用证据定位原因，再修复；把评审发现、验证结果和Git提交连接为能追溯的开发过程。

真实案例：Windows打包时electron-builder刚重命名RainSoul.exe，写ASAR完整性资源出现 `UNKNOWN/open`。独立输出目录也能复现，稍后同一文件又能打开，说明需要调查短暂文件占用，而不是立刻关闭完整性校验。

查看 `scripts/pack-desktop.mjs` 和 `scripts/windows-file-retry.mjs`。实现核对锁定的工具版本，仅在Windows、UNKNOWN、open这一组合上重试原操作，最多5次、间隔1500ms，其余异常原样抛出。

实践步骤：

1. 保存原始错误码、调用位置与复现环境，避免只留下“打包失败”。
2. 用独立输出目录验证是否由旧产物导致。
3. 写 `tests/unit/windows-file-retry.test.ts` 先复现受限重试需求。
4. 检查其他平台、其他错误和最后一次失败仍正确抛出。
5. 实际执行完整打包，确认适配确实修复真实入口。

例子：权限不足不是短暂UNKNOWN/open。若把所有错误都重试，会延迟报错并掩盖真实问题；若捕获后直接返回成功，会交付缺少完整性资源的产物。

独立review要沿数据流检查权限、事务、回执、输入法、焦点和未知状态。只看代码格式不足以发现“数据库成功但调用方失败”或“取消删除却丢草稿”等问题。

项目规范在 `AGENTS.md`。核心修改必须有测试；交付前运行完整验证并使用review技能；验证通过后立即小步commit，不把互不相关模块塞在同一提交里。

提交格式示例：

```text
fix(pack): 重试Windows完整性资源的短暂文件占用

- 保留原始完整性写入并限制错误范围
- 增加非目标错误与重试耗尽回归
```

一次源码增删超过500行需拆分。拆提交不能制造不可编译的中间状态；必要时导出暂存快照，分别验证前置提交的类型、构建和相关测试。

证据入口：`tasks/structure-management.md` 记录打包故障、目录包发现的旧章名问题、独立复审和阶段提交；`git log --oneline` 展示实际历史。

练习：针对“保存回执丢失”写一份缺陷记录，包含触发步骤、预期、实际、根因、回归与修复边界。不要只写“添加try/catch解决”。
