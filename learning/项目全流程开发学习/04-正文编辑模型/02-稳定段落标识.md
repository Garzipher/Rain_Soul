## 技术基础：对象身份与编辑位置

### 下标为什么不稳定

数组下标表达当前位置，ID 表达对象身份。假设段落顺序是 `[P1, P2, P3]`，在开头插入 P0 后变成 `[P0, P1, P2, P3]`。原“第三段”现在是 P2，而 P3 的身份未变。引用如果只保存下标 2，就会悄悄指到另一段。

UUID 是足够低碰撞概率的身份值，不包含“第几段”的意义。项目用 `crypto.randomUUID()` 给新段落分配 ID，普通文字修改保留 ID，复制产生的新对象不能重复使用原身份。

### 为什么编辑器需要自动修复

Enter 拆段、粘贴和撤销都通过编辑器事务产生节点，手工只在“新建段落”按钮中赋 ID 覆盖不了这些入口。`stableParagraphIds` 用 ProseMirror 的 `appendTransaction` 观察文档变化，遍历段落与书签，为缺失或重复 ID 补新值。

`appendTransaction` 在原事务之后追加一条修正事务。只有发现变化才返回新事务，否则返回 null；这样避免修正不断触发自身。源代码用两个 Set 分别记录段落与书签，保持两类对象独立去重。

### 编辑后的证据为何可能失效

ID 能证明“还是那一段”，不能证明“还是当时那句话”。段落内容变了，伏笔原摘录仍应保留，但定位和分析必须核对当前内容。段落被删除后，原 ID 不应自动挪给邻段。

跟做时，不只观察文字顺序：先记录 P1、P2，插入一段后重新检查 ID，再删除目标段验证系统不会错误定位别处。这是对身份语义的检验。

## 1. 为什么“第三段”不是稳定身份

“雨落之后”原本第三段讲来信，作者在前面插入一段景物描写。
原第三段立即变成第四段。
如果伏笔或引用只记“第三段”，它会错误指向新段落。

稳定ID把内容对象与显示位置分开。
排序改变不自动改变身份，普通修改文字也不应分配新身份。
它像书中一条记录的身份证，而不是页码。
页码会随排版变化，身份证用来追踪同一条记录。

稳定不意味着永不变化。
拆段产生新对象，新段需要新ID。
复制一段也产生新对象，不能继续冒用原段ID。
合理定义生命周期，才能保持后续证据可靠。

## 3. 三种操作对应三种身份规则

| 操作 | 左侧/原段 | 新段/被合并段 |
| --- | --- | --- |
| 修改文字 | 保留原ID | 不产生新段 |
| Enter拆段 | 左段保留ID | 右段新ID |
| 复制段落 | 原段保留ID | 副本新ID |
| 合并两段 | 保留合并后主体ID | 被合并对象不再是独立段 |

这张表描述当前实现与测试的主要规则。
当前引用对对象消失或证据失效给出占位与复核提示，专用关系见第八卷。
不能只因为有ID，就假定所有锚点迁移问题已经解决。

## 4. 找到自动修复插件

```powershell
Set-Location E:\soulrain
Get-Content .\src\renderer\lib\paragraph-ids.ts
```

插件给paragraph增加id属性。
`parseHTML: () => null`避免从外来HTML信任其段落ID。
`renderHTML: () => ({})`避免把内部身份当可任意复制的网页属性输出。

当事务确实改文档，插件遍历所有段落。
它用Set记录已见ID；缺失或重复时才生成新UUID。
然后通过 `setNodeMarkup` 修改attrs，正文文字仍保留。

这是一种结构维护，而不是保存数据库。
新的合法文档会通过editor.onUpdate进入常规保存流程。
因此ID修复仍受版本与自动保存保护。

## 6. 阅读一个完整拆段示例

以下代码可作为独立练习测试，放入 `tests/unit/` 时导入路径才正确。
不要覆盖现有测试文件；先阅读，再在个人练习分支运行。

```ts
// @vitest-environment jsdom
import { Editor } from '@tiptap/core';
import Document from '@tiptap/extension-document';
import Paragraph from '@tiptap/extension-paragraph';
import Text from '@tiptap/extension-text';
import { expect, it } from 'vitest';
import { stableParagraphIds } from '../../src/renderer/lib/paragraph-ids';
import { emptyDocument, validateDocument } from '../../src/shared/document';

it('雨落之后拆段保留身份', () => {
  const doc = emptyDocument();
  doc.content[0].content = [{ type: 'text', text: '雨夜来信' }];
  const editor = new Editor({
    extensions: [Document, Paragraph, Text, stableParagraphIds],
    content: doc,
  });
  try {
    editor.commands.setTextSelection(3);
    editor.commands.splitBlock();
    const next = validateDocument(editor.getJSON());
    expect(next.content).toHaveLength(2);
    expect(next.content[0].attrs.id).toBe(doc.content[0].attrs.id);
    expect(next.content[1].attrs.id).not.toBe(doc.content[0].attrs.id);
  } finally {
    editor.destroy();
  }
});
```

正文节点位置从文档结构计算，不等同于界面“第几个字”的人类编号。
示例选位置3，将四个字拆成两段。
预期左段“雨夜”、右段“来信”，ID不同。
`finally`销毁编辑器，避免测试之间残留资源。

## 7. 重复ID为何必须拒绝

复制时如果原ID被保留，两个段落会争用同一锚点。
一次AI候选可能错误替换另一个段落，引用也可能跳到错误位置。
插件应在编辑阶段修复，shared schema还要在保存边界拒绝重复。
两层保护分别面向编辑行为与外部请求。

只用数组索引作为ID同样会出错。
删除前面一段，后面全部身份随之改变，历史证据无法稳定追溯。
确定性教学章ID依据发布key，与普通新段UUID属于不同场景。

## 常见问题与排查

| 现象 | 检查 | 处理 |
| --- | --- | --- |
| 每次打字都换ID | 插件分配条件 | 仅缺失/重复时新增 |
| 复制后ID相同 | appendTransaction是否执行 | 检查真实编辑器事务 |
| 测试无法建立Editor | jsdom环境注释与扩展 | 使用完整测试设置 |
| 锚点随插段变化 | 是否仍用数组索引 | 改成稳定对象身份 |
