# 第一章 用受限结构保存正文

本章状态：段落、文本和硬换行已实现；知识/伏笔书签节点还需后续扩展。

用户确认所有正文采用一套固定样式，标题单独放大加粗。实现没有保存任意 HTML，而是保存受限结构化文档：doc包含段落，段落有 UUID，内部只允许 text 与 hardBreak。这样正文内容与视觉样式分离，避免粘贴进来的复杂格式污染数据，也为未来引用、导出和证据定位留下明确结构。

一个可读例子如下，实际 ID 必须是合法 UUID：

```json
{
  "type": "doc",
  "content": [{
    "type": "paragraph",
    "attrs": { "id": "191f53ac-d50c-4d3c-a37e-382dcedf5df6" },
    "content": [{ "type": "text", "text": "雨落在窗外。" }]
  }]
}
```

实践步骤：先读 `src/shared/contracts.ts` 理解可保存的形状，再读 `src/shared/document.ts` 中的 strict schema。它拒绝未知节点、额外字段、空文本节点和重复段落 ID；至少保留一个段落，空作品也有可编辑位置。`emptyDocument` 创建空段落，而不是返回 null。

编辑器产生的内容在进入主进程和仓储时再次验证。不要只依赖前端插件：未来归档、导入或测试适配器也可能构造文档。共同验证函数是“每个入口遵守同一正文合同”的实现方式。

取舍：受限结构更容易稳定导出和定位，但必须明确加入新节点的规则。未来增加知识书签时，需要同步 schema、编辑器渲染、字数、快照和导出；不能只让界面出现一个图标，却让仓储把节点拒绝掉。

证据：`tests/unit/document.test.ts` 检查正文形状与统计；`renderer.test.tsx` 检查真实 Tiptap 输入；仓储测试确认保存读取往返。Git `fb71844` 建立正文契约，`454ff70` 构建编辑组件。

练习：设计一个不计字数的知识书签节点，列出需要哪些稳定 ID、删除占位和导出信息。这里只写提案，等待正式知识模块实现，避免扩展出未经确认的任意富文本。
