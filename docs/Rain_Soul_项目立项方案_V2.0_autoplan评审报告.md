# Rain_Soul V2.0 立项与实现方案评审

- 日期：2026-09-29
- 评审对象：[立项方案 V2.0](E:/soulrain/docs/Rain_Soul_项目立项方案_V2.0.md)
- 基线：[已确认首版设计](E:/soulrain/docs/superpowers/specs/2026-09-28-rain-soul-mvp-design.md)、[原型需求梳理](E:/soulrain/docs/soulrain-原型需求梳理.md)
- 方法：按 `/autoplan` 的 CEO → Design → Eng → DX 顺序评审，并核对 GitHub 仓库元数据、README、许可证和发布记录。当前仓库没有 Rain_Soul 应用源码；本报告评的是方案可实施性，不是运行中的产品质量。

## 结论

**有条件通过产品探索；V2.0 暂不能作为“已确认、可排期的最终开发基线”。** 首版目标仍是让真实作者在 Windows 10/11 64 位上，离线完成一部由作者自行确定终点的作品，可靠保存、引用知识、恢复版本并导出 DOCX/TXT。作品字数和章节数不设产品上限；性能测试样本不构成写作上限。

V2.0 的写作愿景有价值，但把已确认的技术栈换掉，重新把学习卡放入 P0 发布门槛，还使 P0 作者流程依赖 P1 大纲和分类树。数据模型尚不足以实现无卷章节、稳定行内引用及跨作品知识快照。先修复这些冲突，再讨论排期、预算和 P1/P2。本文的技术建议是待实现时验证的方案，不表示用户已经同意改动既有基线。

## 3. Design：P0 作者旅程与交互

V2.0 [第 161 行](E:/soulrain/docs/Rain_Soul_项目立项方案_V2.0.md:161)把“点击作品”接到 P1 大纲页；[第 169、270 行](E:/soulrain/docs/Rain_Soul_项目立项方案_V2.0.md:169)让 P0 引用选择依赖 P1 分类树；[第 180、380 行](E:/soulrain/docs/Rain_Soul_项目立项方案_V2.0.md:180)又把 P0 项目归档藏在 P1 高级模式。应改为下列可独立完成的路径：

```text
作品列表（新建作品 / 导入项目归档）
  → 作品工作区（可选卷/章树 + 当前章节编辑器）
  → 插入引用（知识搜索 + 标签 + 条目列表）
  → 版本历史（创建 / 比较 / 恢复为新版本）
  → 备份项目 .rainsoul 或导出成稿 DOCX/TXT
```

P0 导航只展示可用的作品、知识库、设置；P2 需求会话在可用时加入。创作集若保留，首次创建作品应自动归入默认集合，不要求作者先设计集合层级。头像下方显示笔名；编辑、上传和身份联动单独决策。基础引用应有可见“插入引用”命令和键盘入口，以光标所在段落为目标，不能只靠“不选中时右键”。

| 场景 | 初始/进行中 | 失败与恢复必须可见 |
| --- | --- | --- |
| 无作品或章节 | 直接显示“新建作品/导入项目”或“新建章节”；卷可选。 | 删除章节前自动快照并确认；非空卷不能直接删除。 |
| 编辑与切换 | 每章实时字数；“保存中/已保存”及最后保存时间。 | 保存失败保留当前输入、提供重试；阻止切换、快照、归档、导出与关闭。 |
| 搜索与引用 | 结果标明“章节/知识”，显示片段、来源、高亮及跳转；弹窗保留焦点。 | 无结果可清除筛选；已删除知识显示占位和最后来源。 |
| 版本 | 可按章节比较，恢复前预览旧版本。 | 失败不改变当前稿；恢复前状态和全部历史仍可访问。 |
| 交稿与备份 | 区分“导出成稿”和“备份项目”，显示目标、格式与进度。 | 错误显示目标路径与重试，不显示虚假的成功。 |

设计完备度评分仅针对**方案文本**：信息架构 4/10、交互状态 2/10、作者旅程 4/10、设计系统 2/10、桌面可访问性 1/10。需要补最小窗口、125%/200% 缩放、窄窗口侧栏、键盘卷章排序、对话框焦点恢复和非颜色保存提示；仓库尚无 `DESIGN.md`。视觉效果不能在没有应用时评分。

## 4. Eng：P0 推荐实现与数据约束

### 4.1 架构选择

V2.0 [第 429、551 行](E:/soulrain/docs/Rain_Soul_项目立项方案_V2.0.md:429)把 Tauri 2 + FastAPI + SQLModel + sqlite-vec 称为“已确认”，与[已确认首版技术设计](E:/soulrain/docs/superpowers/specs/2026-09-28-rain-soul-mvp-design.md:42)的 Electron + React/TypeScript + SQLite 冲突。

| 路线 | P0 判断 | 必须验证的代价 |
| --- | --- | --- |
| **Electron + React/TS + SQLite** | 沿用既有决策；主进程负责文件/数据库，受限 preload 暴露业务命令。编辑器候选为 Tiptap 开源核心。 | 原生 SQLite 模块重编、主进程阻塞隔离、安装包体积和 Windows 安装升级。 |
| Tauri 2 + Rust + SQLite | 可作为新 ADR 的备选，前端和受限命令边界仍可保留。 | Rust 开发/维护、WebView2 依赖、插件兼容、实际包体和性能。 |
| Tauri 2 + FastAPI/Python sidecar | P0 暂无必须引入 Python 服务的需求。 | Python 打包、启动/退出、端口鉴权、崩溃恢复、杀毒误报、升级同步；“包体小”需实测。 |

建议先按既有 Electron 决策做一条“安装 → 离线写一章 → 保存/异常恢复 → DOCX/TXT → 升级”的 Windows 纵向验证。若提出换栈，先用同样样例比较安装、冷启动、内存、导出和故障恢复，再由负责人批准 ADR。P1 是否需要 Python 应由具体 AI 能力证明；云 API 或 Ollama 接入本身不必预先绑定 FastAPI。

```text
React/受限编辑器 → preload 业务命令 → IPC 参数与路径校验
                    → 单写入队列/SQLite 事务 → 提交 revision 回执
                    → UI 显示该 revision 已保存
快照/导出/归档 → 先 flush 待保存内容 → 一致读 → 临时产物 → 校验/替换
```

### 4.2 各功能的最小可靠实现

| P0 功能 | 推荐实现与关键边界 | 验收证据 |
| --- | --- | --- |
| 作品、卷、章 | 每项目目录与稳定 UUID；`chapter.work_id NOT NULL`、`volume_id NULL`，约束卷与章同作品；根章和卷内章分别排序，移动/删除整事务。V2.0 [第 398 行](E:/soulrain/docs/Rain_Soul_项目立项方案_V2.0.md:398)缺 `chapter.work_id`，无法归属无卷章节。 | 不建卷也可增章、移动、排序、归档和恢复；错卷引用被拒绝。 |
| 固定编辑器 | Tiptap/ProseMirror 限定标题外置、段落、纯文本和引用原子节点；章节结构化 JSON 是正文唯一事实源。段落/引用各有稳定 ID，搜索文本和引用关系为事务内派生数据，避免 `paragraph.content` 与位置 `anchor` 双写漂移。 | 输入法、粘贴清洗、撤销、拆段/合段/移动/复制后的 ID 与引用正确。 |
| 字数、自动保存 | Unicode 码点规则计汉字、字母、十进制数字，排除引用节点、标点、空白与标题；约 500ms 停顿保存，连续输入最长 5s 落盘；按递增 revision 串行提交。WAL/同步级别用断电测试决定。 | 即时字数与落盘值一致；旧保存回执不能覆盖新状态；磁盘满/只读时保留输入并阻断旧稿导出。 |
| 知识与搜索 | 知识条目稳定 ID、软删除与最后标题/来源；标签用关系表。正文和知识共用来源标注搜索结果。可先验证 SQLite FTS5 trigram 对三字以上连续串的候选能力，一/二字走确定的短词路径并精确复核；未达到延迟基线再加一/二元索引。标签 AND 用关联表聚合，非知识结果在有标签筛选时不显示。 | 汉字单字/双字/长词、无结果、筛选、高亮跳转正确；固定样本 UI P95≤1s。 |
| 行内引用 | 引用节点保存 `citation_id + knowledge_id`，编号导出时按首次出现顺序生成；随节点拆合与移动，删除仅影响当前正文，快照保留历史。条目编辑显示最新值，软删除显示可追溯占位。 | 拆分、合并、复制粘贴、移动、删除及重复引用后无悬空/重复 ID。 |
| 手动快照与恢复 | 同一事务保存作品结构、正文、引用和知识的一致不可变版本；恢复前 flush 且保存当前状态，再复制旧状态为新当前版本和新快照，失败整体回滚。用 SQLite backup API/一致读生成归档，不能直接复制 WAL 模式主 DB 文件。 | 可比较两版；恢复旧版后当前前态及原历史均可访问；注入中断后原稿不变。 |
| 项目归档 | `.rainsoul` 包含格式版本、校验信息和项目依赖；先临时生成再发布。导入校验格式、校验和、条目大小、ZIP 路径与解压总量，迁移后创建**新项目 ID**，不覆盖旧项目。 | 往返核对正文、知识、引用、快照；损坏包、旧版包和路径攻击均可解释地失败。 |
| DOCX/TXT | 从同一导出中间结构按卷章顺序渲染；DOCX 固定中文字体/标题样式，TXT UTF-8；正文保留引用编号，文末按首次出现生成清单，已删除条目标状态；临时文件成功后再替换目标。 | 用 Word 和纯文本阅读器打开，核对排序、样式、编号、清单；失败不损坏源数据和旧目标。 |
| Windows 发行 | 固定 `%LOCALAPPDATA%\RainSoul\Projects`，单实例锁、版本化前向迁移与升级前备份；普通账户离线安装。卸载默认留数据，删除需明确选择；发布前决定签名与分发渠道。 | 干净 Win10/11 x64 安装、重启、升级、卸载留数和断网验收。 |

知识库作用域是[第 400、403 行](E:/soulrain/docs/Rain_Soul_项目立项方案_V2.0.md:400)的真正未决项：V2.0 既让作品快照包含知识，又没有说明知识条目属于作品还是作者全局。**暂推荐 P0 按项目拥有知识条目**，条目使用全局唯一 UUID 并记录归属，当前作品的归档/恢复可闭合；全局入口可按作品查看。此设计须保留进阶路径：P2 跨作品复用先用“复制到目标项目”，生成新 UUID 并记录来源项目、原条目 ID/版本，旧引用和快照保持不变；若作者确实需要跨作品实时同步，则另做全局库和不可变版本，引用明确指向全局条目及其显示策略，恢复 A 不得回滚 B 依赖的版本。不能靠修改 `work_id` 将现有条目原地搬走。V2.0 [第 413 行](E:/soulrain/docs/Rain_Soul_项目立项方案_V2.0.md:413)“所有实体都有类型、状态、版本、来源”应改为逐实体约束，不给每张表添加无意义字段。

### 4.3 P0 验收门槛与故障注入

[已确认设计](E:/soulrain/docs/superpowers/specs/2026-09-28-rain-soul-mvp-design.md:54)已有可测门槛，V2.0 [第 509–517 行](E:/soulrain/docs/Rain_Soul_项目立项方案_V2.0.md:509)应继承：

1. 干净 Windows 10/11 x64 普通账户、断网安装并完成创建、编辑、引用、快照、DOCX/TXT、归档往返；原位升级后已保存数据不变。
2. 保存失败时保留未保存内容，阻止切换、关闭、快照、导出和归档；异常退出仅保证恢复到最后一次成功落盘，并显示时间，不承诺未落盘输入零丢失。
3. 搜索固定样本为 100 章、100 万统计字、1000 条知识；四核/8 GB/SSD Windows 机上，预热一次、20 条固定查询各 10 次，UI 发起到结果显示 P95≤1s。覆盖单字、双字、长词、无结果、标签 AND；样本**不是**作品大小上限。
4. 引用在拆/合/移动段落后仍指向正确知识，软删除可追溯；恢复旧快照生成新版本且保留恢复前状态；归档导入为新项目。
5. 至少一位真实作者在试用前自定作品终点，独立完成并导出；记录放弃、丢稿、迁稿、搜索和导出问题。资源排期前还要明确负责人、人力、预算与周期。

测试分层：单元测字数、排序、标签和引用编号；数据库集成测 revision 竞争、迁移、知识隔离、磁盘满、快照回滚；文件集成测 DOCX/TXT、损坏/恶意归档；Windows E2E 覆盖安装到交稿。项目尚无应用源码、构建与这些测试，不能把文档评审视为产品验收。

## 5. P1/P2：何时进阶、怎样实现

所有 P1/P2 功能都要有单独问题陈述、使用证据和退出条件；阶段标签不是开发承诺。优先修复真实作者在 P0 遇到的阻碍，未观察到需求的功能不因竞品已有就提前实施。

| 功能与阶段 | 进入条件 | 推荐实现与禁止的捷径 |
| --- | --- | --- |
| P1 写作特点、大纲 | 作者需要跨章保持风格或计划与正文的对应关系。 | 版本化 StyleProfile，明确作品默认与章覆盖；大纲树用同作品、无环约束，节点与章节用关系表。点击作品仍先能直接写作。 |
| P1 伏笔 | 作者实际需要追踪埋设和回收。 | 在状态机外记录埋设/触发/回收事件及章节/段落证据，规定可达转移；不要只存一个 `status`。 |
| P1 AI 润色、续写、纠错 | P0 写作闭环可靠，作者明确要求辅助。 | 候选保存原文 revision、选择范围、上下文清单与模型参数；预览差异后确认，原文变更则拒绝旧候选覆盖；确认时保存前态。第 266 行的“相似度≥90%直接取用”无校准依据，改为显示来源与候选，由作者决定。用户选择当前章/前章衔接/全卷/自定义范围；超模型窗口时先提示并预览分块或缩减范围，禁止无提示截断，结果标出所用证据章节。 |
| P1 语义检索 | 黄金查询集证明关键词搜索在真实查询中不足，且向量确有可测增益。 | `sqlite-vec` 仅作为可重建派生索引，记录文本 hash/模型版本；关键词与向量融合并校准，模型缺失时仍可关键词搜索；测包体、CPU 延迟与重建时间。 |
| P1 分类、手动拆文、正文回写 | 已有足够知识条目，人工管理成为真实阻碍。 | 分类先定单/多归属及删除迁移；拆文先支持粘贴/TXT、预览来源和逐条确认；PDF/EPUB/DOCX 分别验证解析质量。回写只经“候选→审阅→发布”，带来源 revision 与去重，避免循环污染。 |
| P1 EPUB/PDF | 作者有实际分发或打印场景。 | 沿用同一导出中间结构；EPUB 用兼容阅读器验证，PDF 验中文字体、分页和可读性。 |
| P2 需求会话、跨作品分析 | 单章操作不足，且 P1 的证据追踪和权限边界可信。 | 默认只读分析，按章节分块，引用证据及 revision；仅生成明确变更提案，作者确认后才写库；可取消，不给 Agent 任意数据库权限。 |
| P2 剧情感受 | 作者反复需要判断大纲偏离、上下文衔接或主观合理性。 | 将可核验的时间/人物/事件矛盾与主观阅读感受分开；按选定上下文给出原文证据、置信说明与建议，不自动改稿。先由作者样本评估误报和帮助程度，再决定是否产品化。 |
| P2 自动拆文、URL 输入 | 有授权的来源和分类标注集，人工审核负担显著。 | 全部先入候选区；第 329 行“≥80% 自动入库”未经校准，且与后续人工审核矛盾。网页仅限可导入内容，不承诺突破反爬；限制协议、私网地址、重定向、大小和时间，保留出处。 |
| P2 XMind 导入、由大纲生章 | 大纲已被作者稳定使用。 | 指明支持的 `.xmind` 格式版本；解析、限额、预览与冲突检查先于单事务导入；生章先预览、去重、确认，不默默改写已有章节。 |
| P2 一致性检查 | 伏笔/人物/时间数据足够结构化且存在实际漏检。 | 先规则与有证据的关系检查；LLM 只给建议，知识图谱在标注集上证明增益后再引入。 |
| P2 AI 风格规则、全局知识库配置 | 作者确实需要跨作品复用规则或资料。 | 空风格规则可生成带来源的候选供作者确认，不能默默改写作品风格；知识复用优先复制到目标项目并保留来源，若需实时共享再引入不可变全局版本及引用策略，不能改变旧快照语义。 |

AI 发送前应显示内容范围、模型服务与预计费用；默认不配置云端服务。密钥用 Windows Credential Manager 或 Electron `safeStorage`/DPAPI 保存，不进入归档、日志或错误上报。渲染进程禁 Node、启用上下文隔离和 CSP，所有 IPC 命令校验参数与文件路径。V2.0 [第 458 行](E:/soulrain/docs/Rain_Soul_项目立项方案_V2.0.md:458)“密钥存在本地配置、不外泄”不是可验证的安全方案。

**进阶门槛：** P0→P1 先通过上述离线、保存、归档、导出、检索和真实作者试用；P1→P2 先证明 AI 旧稿冲突不会覆盖原文、语义检索相较关键词有增益、伏笔/大纲被真实使用。自动入库还需标注数据校准误收率；没有这些证据时保留人工确认。

## 6. DX：开发与交付体验

Rain_Soul 的用户是作者，不是 SDK 或 API 使用者；DX 只评价开发团队能否稳定构建、迁移、调试和交付。当前 `package.json` 仅有 Playwright 浏览器配置测试，没有应用启动、Lint、类型检查、数据库迁移或 Windows 生产构建。学习卡应是内部知识产物，不能替代运行手册、ADR、可复现开发环境和发布验收。

建议在 P0 开工时建立：固定 Node/包管理器版本和锁文件；`dev`、单元/集成、Lint、类型检查、Windows 打包命令；测试数据库和示例作品；SQLite schema 版本化前向迁移、升级前一致备份与失败恢复演练；Electron 原生模块重编、安装升级与签名检查；错误日志记录阶段、错误码和项目 ID，排除正文与密钥。学习卡可解释实现和实验，但不作为作者验收门槛。当前测试只检查 Chrome 启动及访问百度，不能验收离线写作；开发首次启动时间在应用出现前不可测。
